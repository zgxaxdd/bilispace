# A. 缺陷清单（12 条，全部静态可证）

## D1 —— 四个 `LaunchedEffect` 全部以整个 `pages` List 为 key，每次补货整组重启

- **文件:行** `PortraitSwipePager.kt:197 / :238 / :252 / :330`
- **判据**
  ```
  grep -n "LaunchedEffect(.*pages)" PortraitSwipePager.kt
  → 197:  LaunchedEffect(pagerState, pages)
  → 238:  LaunchedEffect(pagerState, pages)
  → 252:  LaunchedEffect(currentId, pages)
  → 330:  LaunchedEffect(currentId, pagerState.currentPage, pages)
  ```
  而 `pages` 的构造是 `:178  val pages = remember(anchor, queue) { listOf(anchor) + queue }`
  —— `queue` 每追加一批就是**新 List 实例** ⇒ 四个 effect 全部取消并重启。
- **为什么会坏**
  1. `:197` 的 `snapshotFlow { pagerState.currentPage }.distinctUntilChanged()` 在重启后
     `distinctUntilChanged` 的**内部状态归零**，会立刻用当前页重放一次 → 重放那一刻
     `entry.id != requestedKey` 若因时序成立，就**重复派发 `onSwipeTo`**（`:212`）。
  2. `:252` 的对齐 effect 同样重启，它会走 `else -> onSwipeTo(entry)`（`:268`）。
     两个 effect 都能在"补货落地的同一帧"各发一次 `onSwipeTo` —— 这是 `openSwipeTarget`
     短路之外的**第二条竞态路径**（短路只挡"同一目标"，挡不住"两次不同目标"的交叉派发）。
  3. 队列越长、补货次数越多，重启次数 = 补货次数 × 4，掉帧与重复请求随会话时长增长。
- **修法** key 里**移除 `pages` 整个 List**，改用 `pages.size` + 内容身份（`currentId` /
  `pagerState.settledPage`）；同时把"翻页派发"与"对齐派发"合并进**一个** effect，
  用统一的 `requestedKey` 去重，让"同一页只派发一次"由**单一出口**保证。

## D2 —— `onPrefetch` 有两个触发源，且 `lastPrefetchPage` 与 effect 的 key 语义冲突

- **文件:行** `PortraitSwipePager.kt:231-233`（源 A）与 `:238-251`（源 B）
- **判据**
  ```
  :231  LaunchedEffect(pages.size, pagerState.currentPage) { onPrefetch(pagerState.currentPage) }
  :238  LaunchedEffect(pagerState, pages) { snapshotFlow{...}.collect{ ... onPrefetch(target) } }
  ```
  两处都调 `onPrefetch`；`:234  var lastPrefetchPage` 只被源 B 读写，**源 A 完全不看它**。
- **为什么会坏** 源 A 在 `pages.size` 变化时必定发一次 `onPrefetch(currentPage)`，
  而源 B 的去重表 `lastPrefetchPage` 对此**无感知** → 同一次补货会打两次预取请求
  （VM 侧 `prefetchEntry` 有 aid#cid 去重，所以症状不是"重复网络"，而是
  **预取额度被空跑消耗 + `lastPrefetchRequest` 被覆盖**，进而让
  `SwipePrefetchPolicy.isPrefetchRequestStale` 的取消判据读到错误的上一次口径）。
- **修法** 合并成一个预取 effect，`lastPrefetchPage` 提升为**唯一**的去重闸门，
  两个触发条件（页数变化 / 偏移跨阈值）都先过它。

## D3 —— 五个布尔互相推导，状态机不闭合（用户"全是bug"的结构性根因）

- **文件:行** `VideoScreen.kt:239 / :243 / :372 / :376 / :458 / :463`
- **判据**
  ```
  :239  var isFull by rememberSaveable { mutableStateOf(storyMode) }
  :243  val effectiveStoryMode = storyMode && hostExpanded
  :372  var swipeSessionActive by rememberSaveable { mutableStateOf(storyMode) }
  :376  var swipeModeRequested by rememberSaveable { mutableStateOf(false) }
  :458  val portraitSwipeActive = swipeSessionActive || effectiveStoryMode
  :463  var swipeLandscape by rememberSaveable { mutableStateOf(false) }
  ```
  同一件事（"现在处于哪种播放页模式"）由 5 个可变布尔 + 2 个派生 val 表达。
- **为什么会坏**
  1. `isFull` 与 `swipeSessionActive` **各自**用 `storyMode` 初始化（`:239` / `:372`），
     但一个会被 `exitFullscreen()` 改（`:326`）、另一个只会被 `:377` 的 effect 改。
     `:377 LaunchedEffect(fullOn, videoState.detail)` 在 `!fullOn` 时把
     `swipeSessionActive = false`，于是存在合成态 `isFull=true, swipeSessionActive=false`
     （对齐 effect 尚未跑完的那一拍）—— 此时 `:595 swipeSessionActive && anchor != null`
     为假，pager 分支塌回 `VideoPlayerPane`（`:639`），**画面从刷视频流跳回单视频**。
  2. `:538 val pagerActive = swipeSessionActive && swipeAnchor != null` 与
     `:1159` 的**同一表达式重复写了两遍**（守卫要求两处逐字一致，本身就是脆弱信号）；
     story 引导期 `swipeAnchor == null` 时 `pagerActive` 为假 —— 但 `swipeSessionActive`
     已为真，于是"会话已激活、pager 未渲染"这个中间态没有任何类型约束。
  3. `swipeModeRequested`（"这次进全屏的来路"）与 `portraitSwipeActive`（"现在锁不锁竖屏"）
     是两种不同生命周期的东西，却并列参与 `DisposableEffect` 的 key（`:467-475`）——
     任一翻转都会重建方向 effect 并在 `onDispose` 里把 `requestedOrientation` 复位成
     `UNSPECIFIED`（`:498`），表现为真机上**先横屏再切回**的闪跳。
- **修法** 收敛为一个 sealed 状态 `PlaybackPageMode`，提供纯函数迁移方法；
  `isFull` / `swipeSessionActive` / `swipeModeRequested` / `swipeLandscape` 全部成为
  该状态上的**只读派生属性**，页面不再各自推导。

## D4 —— `onToggleFull` 一个回调承担三种语义，且 story 下与 `onBack` 行为重叠

- **文件:行** `VideoScreen.kt:610-621`（pager 分支）、`:644-651`（pane 分支）、
  `:345-357`（`handleBack`）
- **判据** `:610` 的 `onToggleFull` lambda 体内同时有 `effectiveStoryMode` / `fullOn` /
  `onExitStoryMode` / `onBack` 四条分支；而 `:345 handleBack` 也有
  `effectiveStoryMode -> onBack()`、`fullOn -> exitFullscreen()`。
- **为什么会坏** story 态下"全屏按钮"（pager 传给 pane 的 `onToggleFull`）实际做的是
  "退出 story 模式"，与"退出全屏"完全不是一回事；同一个回调名在两条链路上语义不同，
  任何一处判据写错都表现为"点全屏却退出了页面"或"点还原没反应"。
  这正是用户说"完全无法正常使用"最容易命中的一条。
- **修法** 由 `PlaybackPageMode` 提供 `onPrimaryExit(mode)` 单一入口，三处分支收敛为
  一次 `when (mode)`。

## D5 —— `swipeQueue` 无界增长（有界策略已接线，但**取流侧**没有经过它）

- **文件:行** `SwipeSessionController.kt:119`（`mergeRelates` 里有界）vs
  `VideoViewModel.kt:882 / :951`（`mergeRelates` 调用方）与
  `SwipeSessionController.kt:95-107`（`enterReady` 的 `_queue.value = appendSwipeEntries(...)`，**无** bound）
- **判据**
  ```
  grep -n "SwipeQueueBoundPolicy" SwipeSessionController.kt
  → :5 import / :119 _queue.value = SwipeQueueBoundPolicy.bound(...)
  ```
  只有 `mergeRelates` 一处收口；`enterReady`（起步批次）直接赋 `_queue.value`，未过 bound。
  起步批次 `SwipeSourceRegistry.REFILL_LIMIT` 远小于 200，**实际不越界**，
  所以这条的严重度是"结构缺口"而不是"现在就会爆"——但它是**同一份不变式有两处写入口**
  的直接证据（下次有人改 `REFILL_LIMIT` 或给起步加多批就会越界）。
- **为什么会坏** `currentPage` 在 `bound()` 里是会话页号，而 `enterReady` 时 `page` 还是
  初始值；若将来起步批次变大，截断会以错误的 `currentPage` 计算保留条数。
- **修法** 把 `_queue` 的**所有**写入口收进一个私有 `boundAndPublish()`，`enterReady` /
  `mergeRelates` / `restore` / `removeQueueEntry` 四路共用；并在报告里明确
  `SwipeQueueBoundPolicy` 的定性 = **已接线，本轮补全写入口**。

## D6 —— `prefetchSwipeQueue` 对 `page` 不做范围校验，负值/越界会算出反向目标

- **文件:行** `VideoViewModel.kt:971-1017`（尤其 `:1012 SwipePrefetchPolicy.targetPages(page, pages.size, count)`）
- **判据** `:973 val pages = listOf(anchor) + swipeSession.queue.value`；
  `:979-983 PrefetchRequest(page = page, ...)` 直接把入参 `page` 塞进去，
  全程没有 `page in 0..pages.lastIndex` 的守卫。
- **为什么会坏** `pages` 在**调用瞬间**被重新拼出来，而 `page` 来自 pager 的异步回调。
  队列被 `removeQueueEntry`（不感兴趣）收缩后，回调带来的旧 `page` 可能 > `lastIndex`：
  `targetPages` 内部虽然 `getOrNull` 兜住（`:1013`），但 `PrefetchRequest.page` 已带着
  越界值进了 `lastPrefetchRequest`，污染下一次的 `isPrefetchRequestStale` 判据。
- **修法** 在 VM 入口处早退（`page !in pages.indices -> return`），并把 `pages` 的构造
  收进 `SwipeSessionController`（单一真源），避免"pager 一份、VM 一份"两处拼。

## D10 —— `waitingKey` / `waitingSinceMs` 两个状态分别由两个 effect 写，存在中间态

- **文件:行** `PortraitSwipePager.kt:359-388`
- **判据**
  ```
  :359  var waitingKey by remember { mutableStateOf<SwipeId?>(null) }
  :361  var waitingSinceMs by remember { mutableStateOf<Long?>(null) }
  :362  LaunchedEffect(currentId) { waitingKey = currentId; waitingSinceMs = ... }
  :372  LaunchedEffect(firstFrameRendered, waitingKey, playbackFailed) { ... waitingKey = null }
  ```
- **为什么会坏** 两个 effect 都以 `waitingKey` 为链路的一部分，而 `:372` 的 key 含

  用 `waitingSinceMs` 算延迟，重启后 `nowMs` 重算、延迟随之漂移 —— 在
  `MIN_VEIL_VISIBLE_MS_DEFAULT > 0` 时表现为遮罩停留时间不确定（当前默认 0，
  所以是**潜伏缺陷**：一旦按 KDoc 说的"真机确认闪后调大常量"就会显形）。
- **修法** 合并成一个 effect + 一个状态对象（`VeilState(key, sinceMs)`），去掉自重启。

## D11 —— `pages` 在 pager 与 VM 各拼一份，两处口径随时可能分叉

- **文件:行** `PortraitSwipePager.kt:178`（`listOf(anchor) + queue`）vs
  `VideoViewModel.kt:973`（同样的 `listOf(anchor) + swipeSession.queue.value`）
- **判据** 两处表达式**逐字同构**，但一个读组合期参数、一个读 `StateFlow.value`。
- **为什么会坏** pager 侧 `queue` 是 `collectAsStateWithLifecycle` 的快照，
  VM 侧是 `StateFlow.value` 即时值 —— 二者在"补货刚落地、组合尚未重组"的那一帧不同步。
  `prefetchSwipeQueue` 用 VM 侧的 `pages` 算目标、pager 用自己那份渲染页，
  于是**预取的索引与用户看到的页可能差一**。
- **修法** `SwipeSessionController` 暴露 `pages()`（anchor + queue 的唯一拼法），
  两边都调它；pager 侧仍用组合期快照（那是 Compose 的正确做法），
  但**索引语义**由同一函数保证。
