## 3. 未做项与理由（**不做沉默省略**）

### U1 · PB-05（sidx 分段表解析 + 公开化）：按任务书自身口径未启动

任务书 §2 写明「**PB-05 只在将来要做「DASH 分段预取」时才启动**」，且 §3-PB-05 标题即
"**前置专项，不直接产出功能**"。本轮没有 DASH 分段预取的立项，启动它等于**先造一个没有消费者的
公共 API**（还要把 3 个 `internal` 类型扩成 `public`）—— 与本仓"不新增无消费者 API 面"的取向相反。
**结论：不做，保持登记**（三条阻塞项 `SingleFileDashIndexParser` 无分段表 / 类型 `internal` /
无 `frontierPositionMs` 仍原样，将来启动时任务书 §3-PB-05 的步骤仍然有效）。

### U2 · PB-04 验收① 的"端到端计数"降级为纯函数 + 结构断言

任务书要求「纯 JVM 单测（注入假缓存/假网络）：Wi-Fi 下 `preloadPlayUrl` 成功 → 触发 2 次预热
且区间正确」。实现时 `preloadPlayUrl` 的端到端路径要跨 `VideoPlayerRepositoryImpl`（gRPC/Web 两条取流）
+ 缓存 + OkHttp，注入假件需要为 `BiliGrpcClient`/`VideoWebPlaybackResolver`/`OkHttpClient` 各造一套桩，
**成本高于被验的行为本身**。改为：目标表与门控用**纯函数**断言（区间、顺序、空 URL 跳过、蜂窝空表），
"何时调用/调用后结果如何"用**结构断言**（取流之后、返回类型不变、失败被吞、门控输入是网络类型）。
**如实登记这条降级**；真机上的实际收益本来就属于 L4-105/L4-106。

## 4. 与上游的差异点（本系列强制项）

| 项 | 上游做法 | 本仓做法与理由 |
|---|---|---|
| **PB-01** | 没有"重试前失效缓存"这个概念（它的 playurl 缓存层语义不同） | 新增 `invalidateByPrefix` **能力**；按 `aid#` 前缀覆盖所有 flavor（用户切了清晰度再重试也要生效），而不是只删精确键 |
| **PB-02** | **设置项** `seekFastEnabled`（默认 true）→ **所有** seek 都吸附关键帧 | **不引入设置项**，按 **seek 意图**分档：只有"用户拖拽松手"吸附；SB 跳段/自动片尾/续播全部精确。理由是 §5-a 的发现 |
| **PB-03** 键 | `scheme://host + rawPath`（丢 query）→ **换 host 不命中** | `media:<path>`（连 host 一起丢）→ 用户切 `VideoCdnMode` 的 20+ 镜像 host 后仍命中。代价：理论上"不同 host 同 path 却是不同内容"会误命中 —— B 站 `upgcxcode` 的 path 内容寻址，不成立 |
| **PB-03** 闸门 | 只挂在点播链上（默认不缓存直播） | 显式闸门 `PlaybackCacheGate`：**只缓存点播**（DASH/Progressive），直播与 file:// 都不缓存 |
| **PB-04** 预热实现 | `CacheWriter`（要求上游是 CacheDataSource 实例） | **通过缓存链做一次有界读取**（读多少=预热多少，读完即弃）：只用标准 DataSource API，行为可预期；`CacheWriter` 的契约在无真机时无法验证 |
| **PB-04** 门控 | `PortraitVideoLoadPolicy` 的"仅 Wi-Fi" | 同口径；判据收在实现内部（调用方只传网络类型），避免某个调用点漏判 |

## 5. 闭环判定有变化的部分（**任务书假设与源码不符之处**）

### a) **SponsorBlock 与用户拖拽共用 `seekTo`** —— PB-02 的决定性发现

任务书 §3-PB-02 风险栏写「本项不改 SB 路径即不受影响」，前提是 SB 有自己的 seek 通路。
**实际不成立**：`VideoViewModel` 里 SponsorBlock 跳段（`:379 seekTo(autoEndMs)` / `:404 seekTo(seg.endMs)` /
`:429 seekTo(seg.startMs)`）与用户拖拽（`VideoPlayerPane:2256` → `viewModel.seekTo`）**调的是同一个方法**。
若按上游做"全局吸附"，会有两个实际后果：
1. 跳段被吸到关键帧 → **向后吸附会重新落进片段内** → 依赖 `skippedUuids` 才没死循环（一次重入）；
2. 续播位置被吸成粗值 → 被 `LocalPlaybackHistoryRecorder` **写回历史**。

→ 落地方式改为**按意图分层**（新增 `seekUserInitiated`，只给 UI 拖拽用；SB/续播/恢复保持精确），
并对"精确 seek 每次重断言 DEFAULT"（媒体3 的 `setSeekParameters` 是**保持状态**，会残留）。

### b) **media3 1.11 的 `CacheKeyFactory.buildCacheKey` 返回非空 `String`** —— PB-03 的闸门位置

任务书前置条件 4 的写法（"scheme 闸门"）暗示可以在取键处"返回 null 即绕过缓存"。
实测编译失败：接口声明是非空 `String` → **没有"返回 null"这条路**。
→ 闸门改落在"**包不包 `CacheDataSource`**"，并抽成纯函数 `PlaybackCacheGate`（可 JVM 测）。
**语义与任务书一致**（file:// 不进缓存），额外收窄：**直播也不缓存**（流式边缘，缓存下来的是过期分片）。

### c) PB-02 提到的"5 个 seek 落点"已经漂移

任务书依据的是旧行号（`StreamPlaybackSessionImpl` 的 `:225/:245/:283/:310/:392`）。
当前源码里**会话层只剩 1 个 `seekTo`（`:277`）**，其余三个在引擎层
（`Media3PlayerEngine` 的 `setSource` 续播 / `play()` 的 ENDED 复位 / `stopForReuse` 复位）。
→ 按"意图"重新归类后落地（`W29` 的又一例：任务书给的是"哪一类问题"，不是事实认定书）。
