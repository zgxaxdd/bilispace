# B 组未接线符号：现状、不接线理由与接线步骤（2026-10-18）

> 本文是 `core/designsystem` 里"已实现但无生产消费者"符号的收口记录。所有结论都可被
> `grep` 复核；接线属于跨模块改动（`app/`、`feature/`），本轮（B 组）**不改 feature**，
> 因此只登记，不硬接。

## 1. 玻璃前景自适应（`LiquidGlassReadability` + `PixelCopyLuminanceSampler`）

**现状**：纯逻辑（迟滞 0.58/0.42、保守值 Light）、状态持有者、PixelCopy 采样器全部就绪，
单测覆盖；**全仓无调用点**，采样器默认 `enabled = false`（`sample()` 恒 null）。

**为什么不接**：
1. 消费点全在玻璃 chrome 上——顶栏（`feature/home/HomeScreen.kt` 的 `glassEffect`）、
   底栏 Dock（`app/.../LinkedBottomDock.kt`）、播放器浮层（`feature/video/.../VideoPlayerPane.kt`）。
   这些文件的玻璃挂载点被 `GlassMountRegistryTest` 行号钉死，跨模块接线会同时牵动
   行号登记表与观感，必须单独一轮。
2. 迟滞是否抖**只能真机验证**：滚动停止/转场结束各采一次是低频，但采样值来自上一帧
   回读，背景里一段亮字幕经过时就靠 0.58/0.42 的中间带挡住闪烁。无设备时改默认值
   属于凭感觉。
3. 默认零回读是硬约束：`PixelCopy` = GPU→CPU 回读 + Bitmap 分配，绝不能进默认路径。

**接线步骤（底栏 Dock 优先，常驻、bounds 稳定）**：
1. 宿主侧（`app/` 的 Dock 组合内）：
   ```kotlin
   val activity = LocalContext.current as? Activity
   val visuals = remember {
       PixelCopyLuminanceSampler(
           activityProvider = { activity },
           sampleBoundsProvider = { dockBoundsInWindow },  // 玻璃片在窗口里的 bounds
           enabled = true,
       )
   }
   val readability = remember { LiquidGlassReadabilityState(visuals) }
   LaunchedEffect(dockVisibility) {
       snapshotFlow { dockVisibility }.collect { if (it.visible) visuals.requestSample() }
   }
   // 下一拍读结果（采样是异步的）
   val tone = readability.refresh()
   ```
2. 消费：`GlassContent` 的前景色按 `tone` 取「白 / onSurface」，**不要**新增
   `MaterialTheme.colorScheme` 直取（`ColorRoleAdoptionRatchetTest` 冻结了 22 文件/72 处）。
3. 采样时机：只在**滚动停止、转场结束、折叠态切换**各一次；禁止 `frame` 级采样。
4. 失败路径：`sample() == null` 时 `update()` 已保证不覆盖历史；首次失败取 Light。
5. 验收：真机录屏看"亮画面经过 Dock 时前景是否闪烁"；若抖，先把中间带拉宽
   （0.62/0.38）再评估，不要直接换单阈值。
6. 顶栏（`HomeScreen.kt`）作为第二步：采样时机接在 `GlassSourceRefresher` 的门控上
   （顶栏完全滚出时 gate=false，此时不应采样），并且 `collapsed` 与 `expanded` 用同一
   采样点，避免切换态跳色。

## 2. `MatchedLiquidIndicatorGeometry`（当前 23 处引用，均在测试/内部）

**现状**：纯逻辑（壳高 → 指示器高度 = 87.5%、按压缩放封顶 78dp、角半径 = 半高、
矩形插值）。底栏指示器**没有用它**：`AppNavHost` 里指示器尺寸是
`itemSize - innerPad*2`（48dp − 4dp×2 = **40dp**），圆角是 `RoundedCornerShape(BiliRadius.dockChip)`，
按压缩放是 `LiquidIndicatorMotion.PressedScale`（1.18）。

**为什么本轮不接**：上游几何的前提是"56dp 静止 / 78dp 按压的胶囊泡"，而本仓 Dock
指示器是**40dp 的 tab pill**。若接管高度：`resolve(shellHeightDp=64)` → 56dp，尺寸
直接变大 40%；若只接管圆角：半高 20dp 会替换 `BiliRadius.dockChip`，形状变"两端全圆"。
两者都是可见观感变更，且无设备可 A/B。

**接线步骤（等你拍板再做）**：
1. `AppNavHost` 指示器两行改：`.size(itemSize - innerPad * 2)` → `.size(width = itemSize - innerPad * 2, height = MatchedLiquidIndicatorGeometry.resolve(shellHeightDp).indicatorHeightDp.dp)`；
   `.clip(RoundedCornerShape(BiliRadius.dockChip))` → `.clip(RoundedCornerShape(MatchedLiquidIndicatorGeometry.cornerRadiusDp(heightDp).dp))`。
2. `shellHeightDp` 取 Dock 的实际壳高（`LinkedBottomDock` 里有壳高/内边距常量），
   不要写死 64。
3. 行号：`LinkedBottomDock 421` 与 `AppNavHost 830` 的挂载点不在指示器代码处，但改动
   若与它们同文件，须同步核对登记表。
4. 验收：指示器在折叠/展开 Dock、平板左对齐工具栏下是否与图标格同心；按压膨胀是否
   被 78dp 物理上限削平（小窗）。

## 3. `MotionTierPolicy.glassStrengthCap`（0 调用，`LiquidBackdrop` 显式传 1f）

**现状**：`Low → 0f / Medium → 0.6f / High → 1f`；`LiquidBackdrop` 与
`LiquidGlassTuningPolicy.resolve(glassStrengthCap = 1f)` 显式传 1，等于没接。

**为什么本轮不接**：
1. 现有降级已经是**实测驱动**：`GlassGuardTracker` 用 JankStats 滑窗（jank ≥ 7.5% 连续
   2 窗 → `MotionTier.Reduced` + 低预算），而 `isGlassActive` 在 Reduced 档直接
   `return this`（不挂玻璃）。也就是说"真卡"的机器已经会自动退玻璃。
2. 设备分档的阈值（3GB/6GB）是**产品判断**，不是实测结论（`MotionTier.kt` KDoc 原文）；
   用它硬性关玻璃 = 用猜测覆盖测量，与用户"先测量后改"的要求冲突。
3. 保守策略（仅 `DeviceMotionTier.Low` **且** 系统省电模式时生效）技术上成立，但要新增
   `PowerManager.isPowerSaveMode` + `ACTION_POWER_SAVE_MODE_CHANGED` 监听（新文件 + 新
   receiver），且在 `LiquidBackdrop` 里读设备档会让 `remember(strength, ...)` 的 key 多
   一项；无设备无法验证"低端机 + 省电"的观感，收益（只影响极少数机型）不抵风险。
   **如果以后要接**：`glassStrengthCap` 已经接受 cap 参数，接线点只有 `LiquidBackdrop`
   的 `glassStrengthCap = 1f` 一行 → 改成 `MotionTierPolicy.glassStrengthCap(tier)`，
   并保持 `defaultsMatchCurrentRendering` 测试的默认档不变（High 仍是 1f）。

## 4. `SeedPresetColors` vs `ThemeConfig.PresetColors`（去重结论：**不合并**）

两份列表**不是重复数据**，不能互删或互相 alias：

| | `PresetColors`（`theme/ThemeConfig.kt`） | `SeedPresetColors`（`theme/scheme/SeedPresetColors.kt`） |
|---|---|---|
| 可见性 | `public` | `internal` |
| 数量 | 20 | 19 |
| 内容 | 哔哩粉 `0xFFFB7299` + 哔哩蓝 + 18 个 Material 色 + 黑 | 默认绿 `0xFF5CB67B` + 粉 `0xFFFF7299` + 18 个 Material 色 |
| 名称 | 短名（"琥珀"/"靛蓝"） | 长名（"琥珀色"/"靛蓝色"） |
| 契约 | **持久化主题色的下标索引**（改顺序会错位已保存主题） | **种子预设的下标契约**（`SeedPresetColorsTest` 钉住 19 色与首尾值） |

差异点：粉的红通道不同（`FB` vs `FF`）、Seed 多默认绿/少黑、名称长短不同。
⇒ 合并任何一份都会改动其中一侧的**持久化语义或测试契约**。本轮只做交叉引用注释
（两侧 KDoc 互指），不做数据合并。若后续要统一，必须写成"迁移 + 版本号"而不是
简单 alias。
