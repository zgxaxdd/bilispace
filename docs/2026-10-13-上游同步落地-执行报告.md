### 1.1 A16 —— 本区间唯一「会发错请求」的缺陷

**缺陷原文**（`VideoViewModel.kt:1409`，改前）：

```kotlin
val target = !(state.userState?.liked ?: false)
```

`req_user` 只在服务端愿意回时才出现在详情回包里（`VideoDetailRepository.mapUserState`
在 `!reply.hasReqUser()` 时返回 `null`）。点赞是**取反**操作 ⇒ 未知态下 `?: false`
恒折叠成「未点赞」⇒ `target` 恒为 `true` ⇒ **无条件发出 `setLike(true)`**。
若服务端本来已赞，用户这一下本意是取消，实际却变成**重复点赞**。

**修法**（对齐上游 `a614d2eba` 的 `likeStatusKnown`）：

1. 模型加**显式**字段 `likeStatusKnown`（**刻意不写成 `userState != null` 的派生属性**：
   本文件多处乐观写回写作 `(it.userState ?: VideoUserState()).copy(...)`，会在未知态下
   **凭空造出** `userState`，派生写法会把门重新打开 —— 这是我在实现中途发现并改掉的，
   见 §3「自我纠错」）；
2. 三个写入口全部先过门：点赞、投币带赞（`withLike`）、三连（降级分支会补发
   `setLike(aid, true)`）。投币/收藏**不整块拒绝** —— 它们是单向写，未知时最坏是
   "多加一币"，且上游 `doCoin` 也只门 `alsoLike`；
3. 读侧改**可空三态**：详情页三个 chip（未知 → 同尺寸中性占位、不可点、退成灰）、
   竖屏互动栏（未知 → 描边图标 + 暗灰 tint + "待确认"）。
   **不隐藏**：隐藏会让同行 4 个 chip 的 `weight(1f)` 重新分配，状态到达时横向跳一下；
4. `InteractionResetKey` 并入 `likeStatusKnown`：它和 `userState` **不同源**，
   少了这一位，「未知 → 已知」这次跳变可能被 `distinctUntilChanged` 吃掉。

**为什么这条值得做**：它是本区间 16 个 A 级项里**唯一一处"用户点一下、服务器状态被改错"**
的缺陷。其余要么是观感、要么是性能、要么是基础设施。

### 1.5 C1f —— 亮度与音量手势 HUD 无法区分（真实 UX 缺口）

**缺陷**（`VideoGestureController.kt`，改前）：亮度与音量共用 `Color.White` ——
同样的黑底、同样的白字、同样的白色填充条，**只有一行"亮度/音量"文字不同**。
左侧滑（亮度）与右侧滑（音量）是两块**肌肉记忆区**，配色一致时用户没法靠余光确认
自己滑的是哪一个。清单里判它是"真实 UX 缺口"，本轮核对**成立**。

**修法**（对齐上游 `bbf0587f9` 的思路）：亮度用**固定暖黄**（`BrightnessAccentColor`，
与主题解耦 —— 亮度是**设备物理量**，跟主题变色没有道理）；音量继续走主题主色
（它是**内容相关的媒体状态**）。三处上色（label / 轨道底 / 填充条）统一走 `accent`。

**与上游的一处有意分歧**：上游把亮度色做成 `player_brightness_accent` **资源色**
（`values/colors.xml`）。本仓**不引入资源色** —— `core/designsystem/src/main/res/` 下
只有 `font/` 与 `raw/`，全仓 `colorResource`/`R.color.` **0 命中**，配色方向是**跟随主题**
（`theme/BiliColorRoles.kt` + 三条颜色棘轮），引入并行资源色有踩
`ColorRoleAdoptionRatchetTest` / `DesignTokenLintTest` / `ColorContrastTest` 的风险。
改用与 `VideoPlayerPane.FavStarColor` **同一套**的"语义色常量"做法（本仓既有先例）。

**守卫写成"正反一对"**，并且**刻意把扫描范围收窄到亮度/音量那一块**：
同函数里的**快进**提示（`dragType == Seek`）本来就该是白字黑底 —— 它跟亮度/音量不是
同一组、也没有"另一个长得一样的手势"需要区分。扫全函数会把那条合法用法误判成违规
（我第一版就是这么写的，跑出来红了才发现）。所以断言先按
`Brightness||Volume` 到 `Seek && seekLabel` 两个锚点切出子区间，**切不出区间就直接失败**
（防止退化成"扫空列表 ⇒ 反向断言假绿"）。

### 1.6 B7 —— 直播协议三项上限（含一处**无限递归**）

清单 §1.2 B7 判它是"本仓缺 3 项"，本轮逐条核对**全部成立**：

| 缺口 | 缺陷后果 |
|---|---|
| **压缩深度无上限** | `unpackNestedPackets` ↔ `unpackBusinessPayload` **互相递归且无深度参数** ⇒ 每层再套一层压缩、每层都合法时递归**无限展开** → `StackOverflowError` |
| **每帧包数无上限** | 一个 2MB 帧可塞进几十万个小包，逐个 JSON 解析长时间占用 IO 线程 |
| **损坏压缩包会冒泡** | `inflate` 抛异常一路冒到 socket 读取的 catch ⇒ **整条连接重连**，用户丢掉整个弹幕流 |

**第 1 条的可怕之处**：既有校验（`packetLen` 区间、`headerLen` 区间）与**嵌套深度无关**，
所以恶意包的每一层都能**合法通过**所有校验 —— 这不是"理论上的可能"，是能穿过现有
防线的一条真实路径。

**修法**（对齐上游 `004f00ef4`）：`MAX_COMPRESSION_DEPTH = 2`、
`MAX_PACKETS_PER_FRAME = 4096`、损坏压缩包 `runCatching` 后丢弃该包（兄弟包继续）。
捕 `Exception` 而非 `Throwable` —— `StackOverflowError`/`OutOfMemoryError` 属 `Error`，
必须继续冒泡。

#### 顺带做的一件事：把协议逻辑从 Hilt 类里抽出来

这段逻辑原本是 `LiveRoomMessageRepository`（一个 `@Inject` 类）的 private 方法，
于是**完全不可测**：输入是字节流、输出是 JSON，没有任何 Android 依赖，却只能靠
"扫源码"式结构守卫看着 —— 而那种守卫**证明不了"恶意包不会打崩解析器"**。

上游 BiliPai 早就把它放在独立的 `DanmakuProtocol` object 里，并配了
`DanmakuProtocolLimitsTest`。本轮抽出 `LiveDanmakuProtocol`（`internal object`），
于是第一次能写**真字节级**测试：造 200 层嵌套压缩包、造 MAX+100 个包的一帧、
造损坏的 zlib 字节流，直接断言解析器不崩。

**抽取的附带收益**（都是"单一真值源"）：
- `LiveRoomMessageRepository` 的 `HEADER_SIZE`/`MAX_PACKET_SIZE`/版本号/opcode
  **全部转发**到 `LiveDanmakuProtocol`，不再各留一份字面量（改上限忘改校验的漂移风险消失）；
- `readInt32`/`readInt16`/`parseJsonOrNull` 也委托同一个 object —— 两份字节序实现漂移会让
  "包长校验"与"解包"对同一段字节给出不同结论；
- `sendPacket` 改用 `LiveDanmakuProtocol.encode`，**测试与生产共用同一份字节布局**，
  不会出现"测试里手写一份、生产里另一份"；
- 删掉 3 个已无调用者的方法（`inflate`/`decodeBrotli`/`readAllBytes`）与 6 个死 import。

**有意保留的差异**：本仓 `headLength > totalLength` 时 `break`，上游 `continue` ——
本仓更保守（头部一旦非法就停止解析该缓冲，不冒险按可疑长度跳位）。**这是取舍不是缺陷**，
已在 KDoc 写明。

#### 测试里我自己踩的两个坑（都修了）

1. **`org.json` 在 JVM 上是未实现的桩**：`Method optString in org.json.JSONObject not
   mocked`。加了 `testImplementation(libs.org.json)`（`org.json:json:20240303`，
   已在本地缓存）才能断言"解出来的 JSON 内容对不对"。
2. **入口版本选错**：`VERSION_PLAIN` 的顶层包体会**先被当作单个 JSON 试解析**，
   走不到嵌套扫描。要测"从字节流里扫出多个包"，必须从 `VERSION_ZLIB` 进入
   （用 `zlib(frame)` 包一层）。我第一版 7 条测试里有 5 条因此假红 —— 这也顺带说明
   **协议形状本身需要写进测试注释**，否则下一个人还会踩。
3. 最内层必须是 **PLAIN 帧包着 JSON**，不是"ZLIB 帧包着裸 JSON"——后者是协议里
   不存在的形状，解包器会去把裸 JSON 当帧解析。

### 1.7 B12 —— playurl 在途请求合并（真实重复往返）

**缺陷**：竖屏连播有两条**独立发起**的取流路径 —— 预取
（`VideoViewModel.prefetchEntry()` → `preloadPlayUrl`）与开播（用户滑到该页 →
`fetchPlaybackSource`）。两者共用 `PlayUrlCache`，但缓存只在**请求成功之后**才写入
⇒ "预取在途、用户已经滑到"这个窗口里两条路径**都 cache miss**，
**同一个 key 发两次完整 gRPC 往返**。快速连滑时这个窗口很常见
（预取的就是滑动方向上的下一支，用户滑得快就追上了）。

而真机读数里 **`t1 建源` 占首帧的 ~72%（中位 271ms）** —— 重复一次就是白等一整个往返。
这不是"感觉慢一点"，是在首帧最关键的那一段上翻倍。

**修法**（对齐上游 `OnDemandRequestCache`）：
- 同 key 的并发调用共享**同一个 `Deferred`**，只发一次请求；
- **等待者计数取消**：最后一个等待者离开且请求未完成 ⇒ 取消它（预取失去意义就别占带宽）；
- **失败永不缓存**（`canCache = { it.isSuccess }`）；
- **代际守卫**：`clearCompleted()` 之后，在途旧请求不得把结果写回。

**接线位置刻意保守**：合并层放在 `PlayUrlCache` **下面**、只包住真正的网络段
（新抽出的 `loadPlaybackSource`），`maxAgeMs = 0` 让它**不做结果缓存**。于是
`PlayUrlCache` 的 TTL / LRU / 前缀失效语义、命中计数、以及钉住它们的三个测试
（`PlayUrlCacheTest` / `PlayUrlCacheInvalidationTest` / `RetryInvalidationGuardTest`）
**全部不变**，只有"并发同 key 会重复发请求"这一件事被修掉。

#### 一处**主动加固**（本仓相对上游的改进）

上游写 `val value = load()` —— 加载失败时 `async` 就**失败**。但 `async` 失败会把异常
**同时**送到两处：`await()` 的调用者（我们要的），以及**所属 scope 的
`CoroutineExceptionHandler`**（我们不要的）。后者在真机上意味着一次取流失败可能被上报成
"未捕获异常"，而调用方其实已经妥善处理了它。

本仓把失败**收成值**（`LoadResult.Ok/Err`），`Deferred` 只以"成功"或"取消"两种方式结束
（`CancellationException` 原样上抛 —— 取消不是失败），调用方再把 `Err` 展开成异常。
对外语义完全等价，scope 永远看不到未捕获的失败。**这条有专门的测试断言
（`loadExceptionPropagatesToCallerButNotToTheScope`：异常到达调用者、且
`uncaught.size == 0`）—— 它同时也是"加固真的生效"的证据。**

#### 测试里我踩的两个坑（都修了）

1. **scope 自建 scheduler ⇒ `advanceUntilIdle` 驱动不了它**：第一版给缓存传
   `CoroutineScope(SupervisorJob() + StandardTestDispatcher())`，那是**独立的** scheduler，
   18 条测试全部干等到 `runTest` 超时（各挂 1 分钟，整轮 17 分钟）。
   改用 `runTest` 的 `backgroundScope`（同一 scheduler、测试结束自动取消）后全部通过。
   **这不是被测代码的问题，是测试脚手架的问题** —— 记下来免得重踩。
2. 第一版还有一条 `assertTrue(started.isCompleted)` 在 `advanceUntilIdle()` 之后仍为 false，
   加 `runCurrent()` 先跑一轮队列即解决。

### 1.8 A12 —— 评论首页进程级 LRU + stale-while-revalidate

**上游**：`33d7f6e54` —— `VideoCommentLoadPolicy.kt`（键函数 / 快照类型 / 手写 LRU /

`core/comment` / `feature/comment` grep `cache` / `LRU` = **0 命中**（清单结论复核实成立）。

#### 移植的部分

- `commentPageCacheKey(oid, type, sort, filter, viewerMid)`；
- `CommentPageSnapshot` + `CommentPage.toSnapshot()`；

  四个目的地可能同时持有不同主体，并发是真实路径。

#### 比上游多做的两件事（都是本仓特有的）

**① 键里多拼 `selectedFilter`。** 上游的筛选项只在 UI 层做本地过滤；本仓的
`CommentUiState.selectedFilter` 是**请求参数**（`CommentRepository.buildReq` 的

另外空串归一到 `COMMENT_FILTER_ALL`，与 `mapPage` 的
`filterTag.ifBlank { COMMENT_FILTER_ALL }` 对齐 —— 否则"传空串"与"传全部"
会裂成两个桶，缓存永远打不中。

**② 写入受 mid 比对保护。** 上游不比对（它的 `currentMid` 来自 `TokenManager.midCache`）。
本仓 `_uiState.currentMid` 会被 `authRepo.currentMidFlow` **异步**更新，而 `cacheKey` 是按
`refresh()` 开始时的 mid 算的 ⇒ 请求在途时换账号，直接写就会把**旧账号的点赞态**
（`CommentReply.liked` / `disliked`，gRPC `reply_control.action`）存进旧 mid 的桶，
而下次同账号重进照样命中 ⇒ 用户看到自己没点过的赞。所以写入是
`if (mid == currentMid) { put(...) }` —— **宁可不缓存，不泄漏**。

#### 没有移植的部分（如实记录，不是遗漏）

- **`VIDEO_COMMENT_PAGE_SIZE` 20 → 30：不适用。** 上游是 `page` + `ps` 分页；
  本仓 `buildReq` 只发 `FeedPagination.setOffset(offset)`（gRPC 游标），
  **请求里根本没有页大小字段**，无处可改。
- **`cachedAtMs`：不加。** 上游的快照带这个字段但**没有任何 TTL 消费方**
  （它的过期策略就是 LRU 条数）。本仓照做 LRU，加一个没人读的时间戳就是死字段。

#### 接线：`CommentPanel.kt` 一行未改

`refresh()` 里三处改动，全在 ViewModel：

1. `CommentUiState(... loading = true)` 之后、`viewModelScope.launch` **之前**：
   读缓存，命中就 `_uiState.update { it.copy(...) }` 把首屏字段铺上；
2. `onSuccess` 里：照旧整体覆盖（`page.toUiState`），随后按**同一个键**写入；
3. 写入受上面的 mid 比对保护。

之所以不用碰 UI 层，是因为本仓现成的两个判据刚好就是 stale-while-revalidate 需要的形状：

- `isInitLoading = loading && items.isEmpty()` —— 此刻 `items` 非空 ⇒ **骨架本来就不会出来**，
  用户看到的是旧内容而不是转圈；
- `shouldLoadMore` 含 `!uiState.loading` —— 保持 `loading = true` 顺带阻止了
  **列表底部的自动翻页在刷新途中抢跑**、把这次首页请求的 `reqId` 顶掉。
  这正是上游注释里"刻意保持 `isRepliesLoading` 为 true"的那件事，本仓不用额外写代码就拿到了。

**只缓存首页**：`loadMore()` 不写（缓存整段会让内存迅速膨胀，且重进时从首页 +
`nextOffset` 继续翻就能补齐）。

#### 一处**自己引入的新情形**，以及它的收尾

A12 之前，`refresh()` 失败时 `items` 必然为空 ⇒ 错误卡一定显示。A12 之后多了一种情形：
**缓存已把旧内容铺上，随后这次刷新失败**。此时 `CommentPanel.kt:361` 的错误卡
（`!error.isNullOrBlank() && items.isEmpty()`）**不会渲染** —— 用户看到旧内容，
没有任何刷新失败的提示。

这不影响"内容不被清空"（`onFailure` 走 `copy`，不碰 `items`），但留了一个暗雷：
`error` 字段被写进去却看不见，哪一天 `items` 变空，这次早已过期的失败会突然冒出来。
上游同场景的做法是**显式置空**（`repliesError = if (cached != null) null else …`），照做：
`error = if (cachedSnapshot == null) UserFacingError.messageOf(err) else null`。
**无缓存命中时行为与 A12 之前完全一致**（错误照旧写入并显示）。

这一条有专门的守卫断言（`staleContentRefreshFailureSuppressesStaleError`）与专门的反证
（把条件改成 `if (true)` → 断言变红）。

#### 已知的取舍（未验证，不作收益声明）

缓存**不会**因为本地的点赞/点踩/翻译/删除/发布而失效 —— 这些只改 `_uiState.items`。
上游同样如此。后果：用户点完赞立刻退出，重进会先看到刷新前的旧态，直到后台刷新落地
（一次 gRPC 往返）。这是 stale-while-revalidate 的固有代价，不是缺陷；
真要消掉它得给每次本地动作都写一次缓存，那是另一笔账。

同理，**缓存命中后刷新失败是静默的**（见上一小节：错误卡不渲染、`error` 置空）——
用户看到的是旧内容，没有"刷新失败"的提示。上游同样如此。

**命中率与首屏观感未经真机验证**（设备仍未连接），本节不声称任何收益数字。

### 1.10 A2 机制证明 —— Lint 链路跑通，但只搬了 1 条零基线规则

A2 在清单里是 **L 级、收益最大、工作量最大**（上游 `5fa90deda` / `c8fe9d671`：
新建 `ci-lint` 模块、3 个检测器各带 300~420 行测试、`lint.xml` 按路径豁免、
删掉 20 个扫源码型测试共 −1861 行）。本仓是这套痛点的重度受害者：20+ 个
「扫源码 + 钉行号/钉调用次数」的守卫，本轮改一行 `Spacing.kt` 就要连带改守卫。

**本轮没有试图搬完 A2**，只做**机制证明**：把链路打通、跑响一条规则、确认不破坏现有构建。
既有守卫**一条都没动**。

#### 做了什么

| 文件 | 内容 |
|---|---|
| `ci-lint/build.gradle.kts` | `java-library`；`compileOnly("com.android.tools.lint:lint-api:32.4.1")`；`tasks.jar` 写 `Lint-Registry-v2` manifest |
| `ci-lint/.../CiIssueRegistry.java` | 登记 1 条 Issue；`getApi()` = `getMinApi()` = `ApiKt.CURRENT_API`（= 16） |
| `ci-lint/.../NoPrintlnDetector.java` | `Detector.UastScanner`；只认 `kotlin.io.ConsoleKt.println` |
| `settings.gradle.kts` | `include(":ci-lint")` |
| `build.gradle.kts` | `subprojects` 里对 `com.android.application` / `com.android.library` 两个插件各加 `dependencies { add("lintChecks", rootProject.project(":ci-lint")) }` |

**三个坐标/API 决策**（清单 §5 第 4 条预告过 lint-api 要对齐 AGP）：
- lint-api 取 **32.4.1** 而非上游的 32.3.2 —— 上游对齐的是 AGP 9.3.2，本仓是
  **AGP 9.4.0**。`IssueRegistry.getApi()` 与 `CURRENT_API` 不匹配时检测器会被
  **静默跳过**（不报错、只是不跑），这是最危险的失败模式。
- `ApiKt.CURRENT_API` 是 **static final int 字段**而不是 getter（已 `javap` 核实），
  照上游的 `ApiKt.getCURRENT_API()` 写会直接编译失败（本轮第一次编译就踩到）。
- `visitMethod` 在 lint-api 32.x 已 **deprecated**（实测编译警告），改用同签名的
  `visitMethodCall` —— 不留 deprecated 调用。

#### 为什么第一条规则选 `BbspaceNoPrintln`

**零基线**：本仓 main 源码对 `println(` 的命中为 **0**（已 grep 实测）。
零基线意味着 lint 报告除了故意种下的样本外应当是干净的 —— 这给"检测器真的跑起来了"
一个**无噪声的信号**。换成「硬编码 dp」那种 957 处命中的规则，就得先做 baseline /
路径豁免（上游 `lint.xml` 有约 50 条 `<ignore path=...>`），噪声会把机制问题埋掉。

这条规则本身也是真规则：`println` 在 Android 上直接写 stdout，没有 tag、不过项目的
Logger 管道、release 包里看不见。本仓有 `Logger`（`core/common`，带 tag 与级别）。

#### 判据是类型解析，不是名字匹配

只认 `kotlin.io.ConsoleKt.println`。自定义的同名函数、`System.out.println`、
别的库里的 `println` 都不归我们管。**这正是 Lint 相对"扫源码数次数"的核心优势**：
数文本的守卫分不清这些，只能误报或漏报。

#### ⚠️ 踩坑：Kotlin 的**尾随 lambda 不在 `getValueArguments()` 里**

第一版按实参表递归（`runBlocking` 的实参 → lambda → 体内找带界调用）。结果
`:app:lintDebug` 把**现存两处全部误报**：

```
Lint found 6 errors ...   （基线是 4 个 error）
MainActivity.kt:309: Error: runBlocking 必须在外层套 withTimeoutOrNull(...) …
VideoDetailActivity.kt:217: Error: …
```

原因是 `runBlocking { … }` 这个**尾随 lambda 不进入 `getValueArguments()`** ——
所以"从实参表递归"这条路在 `runBlocking` 上第一步就断了，`withTimeoutOrNull` 永远找不到。
`withTimeoutOrNull(TIMEOUT) { … }` 同理，它的 lambda 也不在实参表里。

修法：改用 UAST 自带的深度遍历 `element.accept(new AbstractUastVisitor() { … })`，

> **这是连续第四轮踩到"API 形态/遍历形态与直觉不符"的坑**（§1.11 facade 名、
> §1.12 facade 迁移、§1.13 构造器 vs 顶层工厂、本节的尾随 lambda）。
> 四次的症状**完全相同**：编译通过、lint 跑完、报告"看起来正常"。

> 这也说明**等价性证明不能省**：如果这次直接删棘轮再跑，我会看到 lint 红了、

### 1.16 B8-b —— 下拉刷新「内容跟随指示器」（12 个界面共用一处）

#### 为什么优先做它

用户在本轮明确要求「**把可以看得见的、最有用的先移植过来**」。按这个口径重排剩余项后：
A2（Lint 机制）虽然收益最大，但它**恰好是最看不见的一项**（前四轮我把它当主战场）；
A1 需先复现崩溃（无设备）；A5/A7/A8/A9/B8-c 经核对**本仓无宿主**（§5 已逐条记账）。
剩下**既能离线验证、又每次使用都看得见**的，是 `BiliPullToRefreshBox`：
它被 **12 个界面**共用（首页/收藏/历史/稍后再看/动态/消息/关系/兴趣/收藏夹详情/网格…），
改一处、处处可见。

#### 缺口原文

改造前只有指示器那个圆点在下降，**正文钉在原地** —— 读作"转了个圈"，
没有"把整页拉下来"的物理感。上游 `HomePullRefreshUiPolicy.resolveMd3PullContentOffsetPx`
正是解这个。

#### 位移量必须与指示器**同源**（不是照抄上游的常量）

从 material3 字节码里读出指示器的实际落点（`PullToRefreshDefaults.IndicatorBox`
的 `graphicsLayer`）：

```
translationY = distanceFraction * roundToPx(maxDistance) − size.height
```

⇒ `translationY + height == distanceFraction * maxDistancePx`，即**指示器底边**
落在 `distanceFraction * maxDistancePx`。内容要贴着它，位移就必须用**同一个** `maxDistance`。

**与上游的刻意分叉**：上游用 M3 的固定常量 `PullToRefreshDefaults.PositionalThreshold`
（字节码 `<clinit>` 实证 = 80dp）。本仓**不能用**它 ——
`BiliPullToRefreshBox` 的 `maxDistance` 传的是 `LocalPullRefreshThreshold`
（用户可在设置里改的「下拉刷新距离」），若内容按恒定的 80dp 位移，
用户把刷新距离调到 40dp 时**内容会跑到指示器下面去**。
故本仓把 `indicatorThresholdPx` 作为参数传入，两者始终同一个数。
这条差异由测试 `位移跟随指示器底边_同一个基准` 钉住，并已反证（见下）。

#### 两个实现约束（都写进了代码注释）

① **`distanceFraction` 只能在 `graphicsLayer { }` 里读。** 它每帧随手指变化；
在组合期读会让**整屏内容**（12 个调用点，每个里面都是 `LazyColumn`/
`LazyVerticalStaggeredGrid`）每帧重组。这是本仓 `FrameBudgetLintTest` 记录过的
同一模式（`AppNavHost:805`、`BiliCardSurface:68` 两处合规写法）。

② **包裹内容的 `Box` 不给任何尺寸修饰符。** 我的**第一版写了 `fillMaxSize()`，
回读时自己推翻了**：`Skeleton.kt:244` 记着一次真实事故（"用 Box 包住列表把首页搞成
只渲染前几条、后面白屏"，成因是约束/测量链被切断），而 `fillMaxSize` 会把尺寸定成
**入参最大值** —— 12 个调用点里 `modifier` 是由宿主决定的参数（如 `MsgFeedPane`），
此处无法穷举其约束；一旦某宿主给的是无界高度，内层就会拿到 `Infinity`（崩溃，不是观感）。
改成**透传约束**后在所有约束下都与原行为一致。安全依据是 `graphicsLayer` 测量透明
（同约束测量、同尺寸上报，只加一个绘制层）。

| **咬合力反证 ①（同源这条）** | 把 `indicatorThresholdPx` 换成硬编码 `80f` → `expected:<20.0> but was:<40.0>` **FAILED**（正是"刷新距离调小后内容跑到指示器下面"那个缺陷） |

### 1.17 播放页液态玻璃适配（用户点名优先）

用户第二轮指示：「可优先移植视频播放页液态玻璃等可以看见的内容，并做好优化和适配工作」。
本仓播放页玻璃**早已是自家实现**（`playerControlGlass` + 9 个调用点 + miuix `drawBackdrop`），
所以这一轮不是"搬一个新系统进来"，而是**按控件尺寸做适配**——这正是"适配"二字的关键：
上游的参数是给 Dock 调好的，直接套到播放控件上是错的。

#### 适配 ①：拖动滑块放大（脱离"静止 16dp 圆点"）

上游 `PlayerControlGlassThumb` 有 `pressScale`（拖动 1.18、松手回 1.0）。
本仓原状是**完全静止**的 16dp 圆点 —— 在 6dp 细轨上，手指按住它时**视觉上没有任何
"我抓住了"的反馈**（连白环都不动）。这是播放页最常用的手势，每次拖进度都看得见。

实现要点：

- 缩放值经 `Animatable` 驱动，**只在 `graphicsLayer` 里读**（与 `smoothFraction` 同一口径）；
  在组合期读会让整条进度条在拖动期间按帧重组。
- 动效设为「关」（`reduceMotion`）时走 `snapTo` 而不是继续跑动画（无障碍口径，
  同 `ProvideSkeletonShimmer`）。
- **不写死弹簧参数**：本仓 A2 迁移后 `BbspaceHardcodedAnimationDuration` 检测器会
  命中硬编码时长，故用默认 spring（这也顺带避免了新增长度字面量）。
- 刻意**不**放大命中区：手势由外层 32dp 高的 `Box` 承接，此值只影响绘制。

#### 适配 ②（回读时才发现的连带缺陷）：玻璃层与白环层**必须同倍率**

滑块是**两个独立绘制节点**：3) 玻璃 `Box`、4) 白环 `Canvas`（半径按 `thumbPx` 算死）。
只放大玻璃、不放大白环 ⇒ 拖动时**玻璃会撑出白环之外**，破相。
两处现在读同一个 `thumbScale`，半径与描边宽度都按同倍率缩放，始终同心。
`thumbGlassAndRingScaleTogether` 钉住这一对（含"倍率必须在绘制期取"）。

#### 适配 ③：高光边档位按控件尺寸自适应

miuix 的 `Highlight` 三档**唯一差异是 `BloomStroke` 的描边宽度**
（反编译 `<clinit>` 实证：Big = **3.5dp**、Middle = 2.8dp、Small = 2.6dp）。
`playerControlGlass` 原本对所有尺寸一律用 `GlassStrokeBigLight`，而它的宿主从
**6dp 的进度条轨道**到 72dp 的中央播放键都有 —— 3.5dp 的 bloom 描边套在 6dp 轨道上
占其高度 **58%**，等于糊满整条轨道（只剩 2.5dp 可读芯线）。
这解释了"液态档下进度条读不清"。

改为按控件短边分档（≤20dp → Small、≤40dp → Middle、否则 Big），
与既有的 `refractionDp` 自适应**同一思路**（它也是按 `shapeHeightPx` 算的）。
`highlight` 已进 `remember` 的键，否则换到不同尺寸控件上不会重建玻璃链。
