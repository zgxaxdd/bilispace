| 铁律 | 原因 |

| **绝不用 PowerShell 改文件内容** | 曾用 `Set-Content -Encoding UTF8` 把中文写成乱码，仍是合法 UTF-8、能编译、极难发现。一律用 `edit`/`write` 工具 |

## T4 · UI/UX 质量收口（全部可做）

### T4.1 dp/sp 收敛的**正确**做法

**背景**：上一轮**刻意拒绝**做全局替换，理由是「语义不同的尺寸塞进同一 token = 制造回归」。
例如 `12.dp` 可能是卡片内边距、也可能是图标尺寸、也可能是分隔线粗细；全塞进
`BiliSpacing.md` 只是把字面量换成 token，**语义反而更模糊**，以后改 token 会误伤一片。

**你要做的**

1. **先测量，再判断，最后才动手**。写一个一次性的统计脚本（可以放在 `scripts/`），
   输出：
   - theme 包外 `\d+\.dp` / `\d+\.sp` 字面量的**完整清单**（文件:行号 + 值 + 该行代码片段）
   - 按值聚合的**频次分布**
   - 已知高频值：`6.dp`（约 111 次）、`10.dp`（约 80 次）—— 这两个值 `BiliSpacing`
     没有对应档位（现有 4/8/12/16/20/24/32）
2. **对 `6.dp` 与 `10.dp` 做语义归类**：把每一处按上下文分成
   内边距 / 图标尺寸 / 分隔线或描边宽度 / 其他。**给出归类依据**（贴出代表性代码行）。
   - 只有当某一类**确实同语义且占比显著**时，才考虑加档位。
   - **不许因为"出现次数多"就加 token。**
3. 对**语义明确同源**的那批做收敛（例如上一轮已做的：7 个 feature 文件各写一份
   `RoundedCornerShape(topStart = 28.dp, topEnd = 28.dp)` → `BiliRadius.sheetTop`）。
4. 加一条**棘轮**：theme 包外 dp 字面量总数（当前约 962）只许减。
   写清当前值与统计口径（哪些目录算在内）。

**验收**：统计脚本存在且可复现；归类结论有代码行证据；棘轮测试会咬人（验证过）；
`testDebugUnitTest` 全绿。

### T4.2 次要文字对比度 —— **只做决策产物，不改默认值**

**关键事实（已核实，不需要你重新论证）**：
`ColorContrastTest` 的类注释已经写明 —— `onSurfaceVariant` 在 iOS 语义里是 **secondary label**，
适用 WCAG **AA 1.4.6 大字号档的 3:1 下限**，而非正文的 4.5:1。
**实测浅色 3.13~3.44:1，已经达标**（Apple 自己的 `systemGray #8E8E93` 在纯白底上是 3.26:1）。
所以**这不是 bug，是刻意对齐 iOS 的设计选择**。

**你要做的**

1. **不要改 `iOSColorScheme` 的默认值。**
2. 提供**数值证明**：在 `ColorContrastTest` 里补一组断言，把候选值算清楚并钉住：
   - 现状：浅色 `0x99`(α0.60) → 3.13~3.44:1
   - 候选 A（正文 AA）：浅色 α `0xB8`(0.72) → 预期约 4.72:1（纯白底）；深色 α `0xAD`(0.68)
   - 每个候选都要在**全部真实背景**（`surface` / `background` / `surfaceContainerLow` 等）
     上算出比值，并写明"在哪个背景上最小"
   - 断言候选值确实 ≥4.5:1（这是可离线证明的）
3. 产出一份**一页纸的决策说明**（放 `docs/`），含：
   - 现状 vs 候选 A 的对比度对照表
   - 各自影响的**视觉范围**（副标题 / UP 名 / 时间戳 / 统计行 / 标签……逐一列出）
   - 保持现状与切换各自的代价
   - **明确写"此项待人工决策，本轮未改默认值"**

**验收**：对比度断言全绿且**会咬人**；决策说明存在；**默认值未变**（用 `git diff` 证明
`iOSColorScheme` 的次要文字颜色没动）。

## T5 · 玻璃链终态 —— **本轮只做 Phase A（分析），不做迁移**

### 先理解问题（这部分是给你的背景，不用写进交付物）

玻璃要采样"自己身后的内容"，就必须有人把背后那部分**录进一个离屏层**。本项目有**两套**
互斥的录制器：haze 的 `hazeSource`（FROSTED 档）与 miuix 的 `layerBackdrop`（LIQUID 档）。

当前有**两个**独立的全屏录制源，各有自己的逐帧 tick：

| # | 位置 | 录什么 |
|---|---|---|
| 1 | `app/.../navigation/AppNavHost.kt:652` `glassRefresher.tick()` | 根 Crossfade —— 整个主 Tab 内容 |
| 2 | `feature/home/.../HomeScreen.kt:224` `homeGlassRefresher.frame` | 首页 HorizontalPager |

而 **#2 在 #1 的子树里面** → 首页滚动时**同一帧录两次全屏**（1272×2800 ≈ 3.5M px ×2）。

**为什么会有第二套（不是疏忽）**：`HomeScreen.kt:200-208` 的注释给了理由 ——
「顶栏是唯一消费者」，而顶栏采样的是 `homeGlassState`（**私有源**），不是根 `glassState`。
建私有源的理由是：**顶栏若采样到含自身的背板 → 自采样鬼影**（反馈回路）。

**终态**：把各 Tab 的悬浮顶栏从 `hazeSource` 子树**提到与 Dock 同级**、共用根 `glassState`、
删掉首页私有源。结构测试的 tick 点数断言 **2 → 1**
（测试名现在就叫 `glassTickSites_currentlyTwo`）。

### ⚠️ 为什么本轮不做迁移

**自采样鬼影正是当初建私有源的理由，而鬼影是纯观感问题，静态断言证明不了它不存在。**
结构测试只能证明"tick 从 2 变成 1"，证明不了没有鬼影。
无设备时做这个迁移 = 拿"可能引入鬼影"换"结构上少一次录制"，而后者你也验证不了。

### Phase A 要交付什么

一份 **`docs/2026-09-22-T5-玻璃链终态-迁移方案.md`**，必须包含：

1. **现状精确描述**（带文件:行号）
   - 两个 tick 源各自的**录制范围**（哪个节点的子树）
   - 顶栏 / Dock / 胶囊**各自采样哪个源**，以及它们的**组合树位置**
     （谁是谁的祖先/兄弟 —— 这决定"拆出去后能否采样到正确内容"）
   - 两套录制器**互斥**的判据（引 `GlassRecordChainStructureTest.hazeAndBackdropSourcesAreMutuallyExclusive`）

2. **自采样鬼影的成因分析**
   - 从**代码控制流**论证：顶栏被录进背板 → 背板被顶栏采样 这条回路在什么条件下成立
   - 拆掉私有源后，**新的回路是否存在**？给出具体推理（哪一行、哪个节点）
   - 明确标注哪些结论是**代码可判定**的、哪些**必须真机才能确认**

3. **迁移方案（不实施）**
   - 精确到"哪个文件的哪一段改成什么"的**diff 草图**
   - 需要同步改的测试（`glassTickSites_currentlyTwo` → 一处的断言）
   - **回退方案**（一个 `git revert` 能回退吗？若不能，说明为什么）

4. **待设备验证清单**（这是本轮最有价值的产出之一）
   - 逐条写"验证什么 / 怎么操作 / **预期看到什么** / **失败长什么样**"
   - 例：「LIQUID 档下滚动首页 → 顶栏玻璃里**不应出现顶栏自身的影子**；
     若出现鬼影，表现为顶栏边缘有一圈与顶栏形状一致的模糊亮边」

**验收**：方案文档存在，含上述 4 节；**代码零改动**（`git diff` 证明）；
结构测试仍断言 2 处（未改）。
