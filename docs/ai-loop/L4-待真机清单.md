## 七、数据库升级与播放连续性（B11 / B12 / B13 新增）

### L4-14 `playback_history` 的 1→2 / 2→3 迁移在真机上真的跑通
- 背景：B11 补了两条真实 Migration 并删掉 `fallbackToDestructiveMigration`。
  SQL 已在**本机 SQLite 3.50** 上回放验证（结构逐字段对比导出 JSON、4 行样本、id 重算规则比对），
  但**Room 侧的迁移执行只发生在设备上** —— 事务包裹方式、`SupportSQLiteDatabase` 行为、
  以及设备上 SQLite 版本差异都未验证。**不得声称已验证。**
- 前置：需要一台**停在旧 schema** 的设备/安装。已在 v3 的设备本次零影响（没有可跑的迁移），
  所以"升级后历史还在"这一条不能拿自己的常用安装验证
- 步骤（有旧包时）：装旧包 → 看几条视频攒出历史 → 备份/记录条数与若干 `aid` →
  覆盖安装新包（**不要清数据**）→ 打开历史页
- 预期 1：历史**条数与内容都在**（这是与旧行为的核心差别：旧包升级会整表清空）
- 预期 2：重看同一条视频 → 进度续上，且历史页**不出现同一视频的两行**（1→2 重算主键是否正确就体现在这里；
  若出现两行 = 主键格式仍与 `PlaybackHistoryKey.videoId()` 不一致）
- 预期 3：logcat 无 `IllegalStateException: Room cannot verify the data integrity` / 无迁移相关崩溃
- 反向确认（刻意做一次）：改一个实体字段 + 升 `version` 但不写 Migration →
  预期**打开即崩**（而不是静默清库），这就是 S6/ST-01 要的失败方式；验完回退该改动
