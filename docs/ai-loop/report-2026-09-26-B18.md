## ST-25 四个文件以 UTF-8 BOM 开头

复核**成立**，实测仍是那 4 个：`OfflineDanmakuSession.kt`、`ListenDetailViewModel.kt`、
`LiveDetailPane.kt`、`SpaceViewModel.kt`（首三字节 `EF BB BF`）。

危害不是编译（BOM 不影响 Kotlin），而是**锚定行首的守卫静默失配**：
`^package` 匹配不到 → 该文件在结构守卫眼里"没有包声明" → 前缀规则对它永久成立。
这正是 B6 那次"4 个文件读不到 package"的根因。

- 剥除方式：**只砍首 3 个字节**，不整文件重写。
  两个文件是 CRLF、两个是 LF，整文件重写容易顺手把行尾与中文一起改掉
  （任务书 §2.3 第一条禁的就是这类 shell 改内容，动机正是中文乱码仍合法 UTF-8 照样编译）。
  所以这一步用字节级操作，并在前后各算一次 sha256 校验还原无损。
- 新断言 `mainSourcesDoNotStartWithABom`（挂在既有 `PackageDirectoryConsistencyTest` 上）：
  扫全部 `src/main` 的 .kt，读**首 3 个字节**而不是文本（BOM 在 `readLines()` 里会变成首字符，
  用文本判断容易看漏）。断言前先看扫到了多少文件（>300），否则又是对空集合成立。
- 破坏性验证：给 `SpaceViewModel.kt` 临时加回 BOM → 该断言 FAILED；
  还原后 `sha256` 与改前**完全一致**（`826800de…edef5`）。

## ST-23 通知权限的"待弹意图"原先存在 Activity 字段里

复核成立但**影响比 BACKLOG 写的轻**：标志丢了不会永久沉默 ——
用户下次再触发后台播放时回调会重新置位，所以是"这一次不问了"，不是"再也不问"。
即便如此，挪动成本只有几行且方向明确，就做了：

- `PlaybackHostState` 新增 `@Volatile var notificationPromptPending`，
  MainActivity 的 6 处读写全部改指它（含 onDestroy 之外的那几处）。
- **只存布尔量**：权限弹窗只能由 Activity 的 launcher 发起，所以刻意不把 Activity/回调塞进单例 ——
  那正是 B2 刚修掉的"单例拖住已销毁 Activity"的形状。这条写在字段 KDoc 里。

## ST-15 单例里的 `CoroutineScope(SupervisorJob())` 没有取消路径 —— 定为设计约束，不加 close()

`PlaybackHostState.scope` 与 `CapsuleIndicatorState.scope` 都是 `@Singleton` 上的进程级作用域。
给它们补 `close()`/`cancel()` 是**错的**：Android 没有"进程即将销毁"的可靠回调，
于是那段代码没有任何合法调用时机，只会变成没人调用的死代码，还会让人以为"取消路径已处理"。
改成在两处写明**约束**：不许把它改成 Activity / ViewModel 作用域（那才会真的漏），
且任何新增的长驻协程必须能容忍活到进程结束。

## ST-22 明确不做（并说明理由）

`ImConversationComposer:51` 的 TODO 是"输入态收敛到 `TextFieldState`"。
这是**状态收敛重构**，收益是"以后少一类 bug"，但：
- 本仓没有能判定"输入态清理时机"的回归测（BACKLOG 的验收标准自己也写了"否则不动"）；
- IME / 无障碍下的输入行为差异只能真机观测，而我们没有设备接在跑；
- 它不属于"让已有功能更稳/更快/更漂亮"里的任何一类可验证改进。
按功能冻结令与 W18 的精神，**留着 TODO 注释、不在这次顺手改**。已在 BACKLOG 标为挂起。
