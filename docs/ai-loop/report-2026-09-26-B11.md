## 复核修正（先于动手，按 W4/W6）

BACKLOG 的两条描述**都低估了**实际缺口，查法与 B0.5 相同（`git log -L '/version =/,+1:<文件>'` + 读旧提交源码）：

1. **ST-01 说"没有 schema 快照"** —— 成立，但根因更结构化：仓库里**已有** `bbspace.android.room`
   约定插件（`build-logic/.../AndroidRoomConventionPlugin.kt`），却**没有任何模块应用它**，
   它自己也只做 `apply("androidx.room") + apply(ksp)`，不设 schema 位置。
   也就是说"导出快照"这件事从来没有归属，5 个 Room 模块各自手写依赖、`exportSchema = false`。
2. **ST-02 说"`PlaybackHistoryDb` 2→3 用了破坏性回退"** —— 成立且已丢过数据，但**缺口不止一处**：
   该库的**出生版本是 1**（`6a24805b` 引入时叫 `LocalHistoryDb`），`6e1469c8` 升到 2、`215575de` 升到 3，
   **两次都只靠 `fallbackToDestructiveMigration` 兜底**。所以停在 v1 的安装同样没有路径。
   只补 2→3 会把 v1 用户从"被清空"变成"打开即崩"——这是必须一起处理的原因。
3. **v1 → v2 不是简单换表名**（BACKLOG 未记）：v1 表是 `local_history`，主键格式
   `uid:video:biz:mainId:cid`，比 v2 起的 `uid:biz:mainId:cid` **多一段 kind**。
   直接 `ALTER`/改名把 `id` 抄过去，会让所有旧行的主键与运行时 `PlaybackHistoryKey.videoId()`
   算出的值对不上 → "继续观看"查不到旧行、重看同一集时插入新行、同一条视频留下两条记录。
   所以 1→2 必须**按 v2 规则重算 id**（PGC 且有 epId 用 epId，biz 一律小写）。

两条迁移都走"建新表 `_new` → 拷贝 → 删旧表 → 改名"。本仓 minSdk 33 其实支持
`ALTER TABLE ... DROP COLUMN`，选重建法是因为它的成立条件更少（DROP COLUMN 在被删列进了索引/视图/触发器时
直接报错，而"这 6 列没被索引"只是当前事实、不是约束），并且它就是 Room 自动迁移自己生成的形态。

## 为什么手写迁移必须有第二重校验

Room 跑完 `Migration` 后只把新的 `identityHash` 写进 `room_master_table`，**不会拿快照去校验建出来的表**。
所以少拷一列 / 写错 NOT NULL 在"打开库"这一刻不报错，而是静默把该列写成 NULL，
或到第一次查询才炸。因此：

1. **`RoomMigrationCopyListTest`** 从 Kotlin 源码里把 `db.execSQL(...)` 的字符串字面量还原成 SQL
   （即"真正会执行的那段文本"，不是另抄一份），与导出的 JSON 逐字对比：CREATE 表结构、
   INSERT/SELECT 拷贝清单、索引定义、以及**链式兼容性**（前一步写的列必须覆盖后一步读的列）。
2. **本机真实 SQLite 回放**（`build/b11_migration_check.py`，Python 3.14 / SQLite 3.50）：
   按 v1 实体建 `local_history`、塞 4 行样本（UGC / PGC 有 epId / PGC 无 epId / biz 大写），
   跑 1→2 断言"行数保全 + 重算 id 与 Kotlin 规则一致"，再跑 2→3 断言
   "列结构/索引与 3.json 逐字段一致、进度未丢、meta 列已删"。全部通过。
