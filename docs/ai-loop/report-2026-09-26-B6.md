# 批次报告 · B6 · 2026-09-26 · 包名/目录一致性守卫，以及它顺手暴露的全仓守卫漏洞

**分区**：D 防回归（连带 ST-24/ST-25/ST-26 三条新台账）｜**级别**：A 级·可机器判定
**为什么做**：B5 建新测试时我**第二次**把目录写成 `com/naammmee/`（本仓包名 `com.naaammme` 极易抄错），
而它照样编译、9 条测试照样跑绿 —— 编译期和测试期都不报这类错。与其记在心里，不如让机器拦住。

## 1. 落地前先量了一遍现状（没有拍脑袋定规则）

先跑 shell 统计全仓 437 个 `src/*/java` 下的 .kt：**39 个文件的目录不等于包名**。
其中 35 个集中在 `core/model` —— 那是**刻意约定**（目录按业务分层 `model/video/Video.kt`，
包名扁平成 `com.naaammme.bbspace.core.model`）。

所以规则不能写"相等"：第一天就红 35 条，接下来必然被加一堆豁免，守卫就变成噪音。
最终规则是**前缀**：`包名的每一段必须按同样顺序出现在路径里`
（`dir == pkg` 或 `dir` 以 `pkg + "."` 开头）。它容忍 `core/model` 的约定，
但 `naammmee` 这种错法一定拦得住。实测当前违规数 = 0。

另外 4 个"读不到 package 声明"的文件，`od -c` 查清是**文件头有 UTF-8 BOM**（`EF BB BF`）：
`OfflineDanmakuSession.kt`、`ListenDetailViewModel.kt`、`LiveDetailPane.kt`、`SpaceViewModel.kt`。
BOM 不影响 Kotlin 编译，但**任何锚定行首的匹配都会在它面前静默失配** ——
这正是结构守卫最隐蔽的假绿来源（上一轮已顺手修过 3 个，还剩这 4 个 → 登记 ST-25，
并明确要求用编辑工具处理，不许 shell 改内容）。守卫本身先做 BOM 容忍，不假装没看见。

## 2. 意外收获：证明了一批守卫**根本没在跑**（ST-26，P1）

做破坏性验证时，我把这个守卫自己 `mv` 到拼错的目录 —— 它应当立刻自检失败。结果：

| 跑法 | 结果 |
|---|---|
| `:app:testDebugUnitTest --tests "*PackageDirectoryConsistencyTest*"` | **BUILD SUCCESSFUL in 22s**（假绿） |
| 同一状态加 `--rerun-tasks` | `declaredPackageMatchesDirectory FAILED`（真判定） |

机制：扫源码型测试是运行时自己 `File().readLines()` 的，**被扫文件不是任务的声明输入**；
`Test` 任务只认 `testClassesDirs` + `classpath`，字节码没变 → 任务直接跳过。
推论很硬：**改注释、改测试自身、改任何不进字节码的文件，都不会让全仓 10+ 个结构守卫重跑。**

也就是说，本会话之前我做的每一次"破坏性验证"都必须额外确认那一轮测试任务真的执行了
（看有没有 `> Task :x:testDebugUnitTest` 而非 `UP-TO-DATE`）。
本轮 B2–B5 的破坏性验证当时都真的打出了 FAILED，所以结论仍然成立；
但 B1 之后那次"`UP-TO-DATE` 为主"的全量绿，只能算"未复跑"。

修法三个选项（代价从低到高），留作下一批决策：
① 只在 CI 的守卫步骤加 `--rerun-tasks`；② `build-logic` 里给 test 任务 `inputs.dir()` 注册被扫目录；
③ `outputs.cacheIf { false }`。改构建链影响面大，**不在本批顺手做**（§2.1）。
