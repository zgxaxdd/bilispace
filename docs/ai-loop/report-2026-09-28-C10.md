## 一、三行结论（先说最重要的）

1. **bbspace 的「当前页起播编排」已经和 BiliPai 打平**：并行 `prepare` + 取流 + 详情 + resume，
   `openId` token 防串台，播放器唯一（BiliPai 是每页持 PlayerView）。**不用推翻重做。**
2. **真正的大差距只有两处**：
   - **相邻页零预热** —— 翻到下一支才发 playurl 请求（多一个 gRPC 往返）；
   - **补货只拉一页** —— 单页去重/UP 多样性后只进 2~4 条，队列很快见底，
     "滑到尽头没有下一个视频"是最高频的体验断点。
3. **观感上最大的"廉价"缺口**是**失败态**：取流失败会撤掉加载层 → 露出"纯黑 + 中央播放键"，
   看起来像卡死（错误详情只在播放器侧栏里，连播页面上看不到）。

## 三、本批落地的六项（含验证）

### 3.1 playurl 进程内 LRU（`PlayUrlCache`）
- 新文件 `core/playback/.../repository/PlayUrlCache.kt`：`LinkedHashMap(accessOrder=true)`，
  **8 条 / TTL 90 秒**，键 = `aid#cid#epId#seasonId` + **影响响应内容的设置摘要**
  （HDR/8K、偏好编码、试看、forceHost）。
- TTL 有意比 BiliPai 的 10 分钟保守：响应里的 `resumePositionMs` 会随观看进度变化，
  缓存太久会让"重新打开同一支"跳回旧进度 —— 我们只需要覆盖"预取→开播"这几秒。
- `VideoPlayerRepositoryImpl.fetchPlaybackSource` 先查缓存（命中即省一个 gRPC 往返并打日志），
  再走原路径并回填 ✓ 正常开播与预取**共用同一份**。

### 3.2 相邻页预取（`preloadPlayUrl` + 两处触发）
- 接口新增 `VideoPlayerRepository.preloadPlayUrl(request): Boolean`（尽力而为、无副作用）。
- 触发（对照 BiliPai）：
  - **拖动**：`PagerState.currentPageOffsetFraction` 跨过 **±0.25** 就预取目标页
    （`SwipePrefetchPolicy.dragTargetPage`，符号约定与 BiliPai 一致：负=往下翻）；
  - **停稳**：`offset == 0f` 时按网络与开关预取 1~3 页。
- 条数矩阵（`SwipePrefetchPolicy.prefetchCount`，与 `resolvePortraitPlayUrlPreloadCount` 同值）：
  WiFi+开关→3、WiFi→2、蜂窝+开关→1、否则 0。
- 新增设置 `prefetchVideo`（默认**开**，播放器侧栏「预加载下一个视频」），
  `AppSettings.setPrefetchVideo` + `VideoViewModel.updatePrefetchVideo` 全链路接好。
- 去重：`prefetchedKeys`（`aid#cid`）保证同一支一次会话只预一次；退出会话清表。
- 网络判据：`core/common/.../network/NetworkTypeProvider.isUnmetered()`（WiFi/以太网才多预）。

### 3.3 补货「凑满」重试（本轮最大体验修）
- `VideoViewModel.loadMoreSwipeQueue` 由"拉一页"改成"最多 3 页、直到净增 8 条"
  （`shouldFetchNextRefillPage`，BiliPai 同值），失败/空页立即停、游标不前进，下轮可重试。
- 日志改为 `more: page=… added=… attempts=… queue=…` → 真机可以直接看"一轮补了几条"。

### 3.4 播完自动翻页幂等
- 加 `lastAutoAdvancedKey`（`swipeKey(currentBvid, currentAid)`）：同一支只自动翻一次，
  防止某些机型连发两次 `STATE_ENDED` 导致**一次跳两支**（对照 `lastAutoAdvancedBvid`）。

### 3.5 失败态：加载层留着 + 重试
- `waitingKey` 的清空条件从 `firstFrameRendered || playbackFailed` 改成**只看出帧**；
- `VideoPlayerPane` 的 `SwipeWaitVeil` 新增 `failed` / `onRetry`：失败时显示
  「警告图标 + 这一支加载失败了 + 重试」，其余区域仍不消费触摸（上下滑/返回照常）；
- 新增 `VideoViewModel.retryCurrentPlayback()`：走 `openVideo(当前目标)`（**不能**用
  `openSwipeTarget`，它对同一支会短路，那是"切页"语义，不是"重试"语义）。

### 3.6 会话内常驻细进度条（信息层第一阶段）
- `VideoPlayerPane` 新增 `SwipeProgressLine`：底部一条轨道（20% 白）+ 已播比例（86% 白），
  只在 `swipePagingActive && !swipeWaitingFirstFrame` 时出现，排在加载层**之前**
  （加载层仍是最后一个子节点，要盖住它）。
- 尺寸全部走**比例**（轨道高 = 屏高 0.0035 ≈ 3dp）：不新增 `.dp` 字面量
  （`DesignTokenLintTest` 的棘轮会把新增字面量判红），且小屏/大屏自然跟随。
- 依据：BiliPai 竖屏页底部常驻细进度（`PortraitFullscreenOverlay.kt:387-394`）；会话内控件
  2 秒自动隐藏，没有它用户完全没有"这支还剩多久"的线索。

### 3.7 队列质量：相似度去重 + 洗牌/相邻不同 UP
- **相似度去重**（`SwipeSimilarity.kt`，移植 BiliPai `PortraitPagerSwitchPolicy.kt:407-497`）：
  标题关键词交集 ≥3、或 ≥2 且时长差 ≤30s、或同 UP 且 ≥1 且 ≤45s → 判"同一支视频"。
  括号段整段丢弃、非中英文数字转分隔符、中文取最长 2~6 字词、英文数字 ≥3 位、
  停用词表（合集/竖屏/完整版…）原样搬过来。
  - **一处必须做的适配**：BiliPai 的 relate 一定带秒，bbspace 的条目经常没有时长
    （解析成 0）。若照搬，"同 UP + 交集 ≥1 + 时长差 0 ≤ 45s"会把**同一 UP 的不同视频**
    大片误杀 → 队列变薄。所以后两条判据要求**两侧时长都已知**才成立（宁可漏杀，不可误杀）。
  - 逐对比较是 O(n²)，关键词抽取结果按条目 key 缓存（BiliPai 的注释也专门点了这件事）。
- **洗牌 + 相邻不同 UP**（`SwipeArrangement.kt`，移植 `PortraitPagerSwitchPolicy.kt:280-330`）：
  去重 → 固定 seed 洗牌 → 相似度去重 → 贪心排布（优先"与上一条不相似且 UP 不同"，
  退化到"只要求不相似"，再退化到取剩余第一条）。
  - **只洗新批次**，已在队列里的页顺序一个不动（pager 以页号为身份，重排会让当前页跳变）。
  - 洗牌前先 `sortedBy { it.key }`：Kotlin 的 `shuffled(Random(seed))` 依赖输入顺序，
    不排序的话"同一批推荐以不同顺序到达"会得到不同结果，可复现性就没了。
  - **不丢 bvid 为空的条目**（BiliPai 的 `filter { bvid.isNotBlank() }` 在 bbspace 会把
    relate 的 aid 条目整页丢掉 —— 正是 C7 的真机事故）。

## 五、真机验收清单（设备到位后执行）

1. **预取生效**：`adb logcat -s PortraitSwipe` 应看到
   `prefetch: key=… count=n`，随后切到该视频时 `playurl cache hit aid=… cid=…`
   → 即"省掉一次 gRPC 往返"；
2. **拖动预取**：按住上滑到约 1/4 屏就松手，日志应已出现目标页的 `prefetch:`；
3. **补货凑满**：连续上滑到倒数第 2 页，日志 `more: … added=… attempts=…` 应出现
   多次 attempts（1→2→3）直到 net 增加 ≥8 或拉满 3 页；
4. **播完不跳两支**：把播放器设为"播完继续下一支"（非单曲循环），等一支播完，
   应只前进 **1** 页，且日志只有一行 `autoAdvance:`;
5. **失败态**：开飞行模式后上滑一支新视频，应看到「这一支加载失败了 + 重试」，
   点重试（恢复网络后）能起播；期间上下滑与返回手势仍可用。
