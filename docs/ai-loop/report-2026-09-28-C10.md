## 一、三行结论（先说最重要的）

1. **bbspace 的「当前页起播编排」已经和 BiliPai 打平**：并行 `prepare` + 取流 + 详情 + resume，
   `openId` token 防串台，播放器唯一（BiliPai 是每页持 PlayerView）。**不用推翻重做。**
2. **真正的大差距只有两处**：
   - **相邻页零预热** —— 翻到下一支才发 playurl 请求（多一个 gRPC 往返）；
   - **补货只拉一页** —— 单页去重/UP 多样性后只进 2~4 条，队列很快见底，
     "滑到尽头没有下一个视频"是最高频的体验断点。
3. **观感上最大的"廉价"缺口**是**失败态**：取流失败会撤掉加载层 → 露出"纯黑 + 中央播放键"，
   看起来像卡死（错误详情只在播放器侧栏里，连播页面上看不到）。

## 三、本批落地的六项（含验证）

### 3.1 playurl 进程内 LRU（`PlayUrlCache`）
- 新文件 `core/playback/.../repository/PlayUrlCache.kt`：`LinkedHashMap(accessOrder=true)`，
  **8 条 / TTL 90 秒**，键 = `aid#cid#epId#seasonId` + **影响响应内容的设置摘要**
  （HDR/8K、偏好编码、试看、forceHost）。
- TTL 有意比 BiliPai 的 10 分钟保守：响应里的 `resumePositionMs` 会随观看进度变化，
  缓存太久会让"重新打开同一支"跳回旧进度 —— 我们只需要覆盖"预取→开播"这几秒。
- `VideoPlayerRepositoryImpl.fetchPlaybackSource` 先查缓存（命中即省一个 gRPC 往返并打日志），
  再走原路径并回填 ✓ 正常开播与预取**共用同一份**。

### 3.2 相邻页预取（`preloadPlayUrl` + 两处触发）
- 接口新增 `VideoPlayerRepository.preloadPlayUrl(request): Boolean`（尽力而为、无副作用）。
- 触发（对照 BiliPai）：
  - **拖动**：`PagerState.currentPageOffsetFraction` 跨过 **±0.25** 就预取目标页
    （`SwipePrefetchPolicy.dragTargetPage`，符号约定与 BiliPai 一致：负=往下翻）；
  - **停稳**：`offset == 0f` 时按网络与开关预取 1~3 页。
- 条数矩阵（`SwipePrefetchPolicy.prefetchCount`，与 `resolvePortraitPlayUrlPreloadCount` 同值）：
  WiFi+开关→3、WiFi→2、蜂窝+开关→1、否则 0。
- 新增设置 `prefetchVideo`（默认**开**，播放器侧栏「预加载下一个视频」），
  `AppSettings.setPrefetchVideo` + `VideoViewModel.updatePrefetchVideo` 全链路接好。
- 去重：`prefetchedKeys`（`aid#cid`）保证同一支一次会话只预一次；退出会话清表。
- 网络判据：`core/common/.../network/NetworkTypeProvider.isUnmetered()`（WiFi/以太网才多预）。

### 3.3 补货「凑满」重试（本轮最大体验修）
- `VideoViewModel.loadMoreSwipeQueue` 由"拉一页"改成"最多 3 页、直到净增 8 条"
  （`shouldFetchNextRefillPage`，BiliPai 同值），失败/空页立即停、游标不前进，下轮可重试。
- 日志改为 `more: page=… added=… attempts=… queue=…` → 真机可以直接看"一轮补了几条"。

### 3.4 播完自动翻页幂等
- 加 `lastAutoAdvancedKey`（`swipeKey(currentBvid, currentAid)`）：同一支只自动翻一次，
  防止某些机型连发两次 `STATE_ENDED` 导致**一次跳两支**（对照 `lastAutoAdvancedBvid`）。

### 3.5 失败态：加载层留着 + 重试
- `waitingKey` 的清空条件从 `firstFrameRendered || playbackFailed` 改成**只看出帧**；
- `VideoPlayerPane` 的 `SwipeWaitVeil` 新增 `failed` / `onRetry`：失败时显示
  「警告图标 + 这一支加载失败了 + 重试」，其余区域仍不消费触摸（上下滑/返回照常）；
- 新增 `VideoViewModel.retryCurrentPlayback()`：走 `openVideo(当前目标)`（**不能**用
  `openSwipeTarget`，它对同一支会短路，那是"切页"语义，不是"重试"语义）。

### 3.6 会话内常驻细进度条（信息层第一阶段）
- `VideoPlayerPane` 新增 `SwipeProgressLine`：底部一条轨道（20% 白）+ 已播比例（86% 白），
  只在 `swipePagingActive && !swipeWaitingFirstFrame` 时出现，排在加载层**之前**
  （加载层仍是最后一个子节点，要盖住它）。
- 尺寸全部走**比例**（轨道高 = 屏高 0.0035 ≈ 3dp）：不新增 `.dp` 字面量
  （`DesignTokenLintTest` 的棘轮会把新增字面量判红），且小屏/大屏自然跟随。
- 依据：BiliPai 竖屏页底部常驻细进度（`PortraitFullscreenOverlay.kt:387-394`）；会话内控件
  2 秒自动隐藏，没有它用户完全没有"这支还剩多久"的线索。

### 3.7 队列质量：相似度去重 + 洗牌/相邻不同 UP
- **相似度去重**（`SwipeSimilarity.kt`，移植 BiliPai `PortraitPagerSwitchPolicy.kt:407-497`）：
  标题关键词交集 ≥3、或 ≥2 且时长差 ≤30s、或同 UP 且 ≥1 且 ≤45s → 判"同一支视频"。
  括号段整段丢弃、非中英文数字转分隔符、中文取最长 2~6 字词、英文数字 ≥3 位、
  停用词表（合集/竖屏/完整版…）原样搬过来。
  - **一处必须做的适配**：BiliPai 的 relate 一定带秒，bbspace 的条目经常没有时长
    （解析成 0）。若照搬，"同 UP + 交集 ≥1 + 时长差 0 ≤ 45s"会把**同一 UP 的不同视频**
    大片误杀 → 队列变薄。所以后两条判据要求**两侧时长都已知**才成立（宁可漏杀，不可误杀）。
  - 逐对比较是 O(n²)，关键词抽取结果按条目 key 缓存（BiliPai 的注释也专门点了这件事）。
- **洗牌 + 相邻不同 UP**（`SwipeArrangement.kt`，移植 `PortraitPagerSwitchPolicy.kt:280-330`）：
  去重 → 固定 seed 洗牌 → 相似度去重 → 贪心排布（优先"与上一条不相似且 UP 不同"，
  退化到"只要求不相似"，再退化到取剩余第一条）。
  - **只洗新批次**，已在队列里的页顺序一个不动（pager 以页号为身份，重排会让当前页跳变）。
  - 洗牌前先 `sortedBy { it.key }`：Kotlin 的 `shuffled(Random(seed))` 依赖输入顺序，
    不排序的话"同一批推荐以不同顺序到达"会得到不同结果，可复现性就没了。
  - **不丢 bvid 为空的条目**（BiliPai 的 `filter { bvid.isNotBlank() }` 在 bbspace 会把
    relate 的 aid 条目整页丢掉 —— 正是 C7 的真机事故）。

### 3.9 补货兜底：拉满页数仍不足 → 用队尾候选的 related 补
- `loadMoreSwipeQueue` 的 3 页循环结束后，若净增仍 < 8（`shouldRunSwipeRefillFallback`），
  取**队尾那一支**（`selectSwipeRefillFallbackTarget`，要求 `aid > 0`）的详情
  `detail.relates`，经同一套去重/排布并进队列 ✓（零新接口 —— 与播放时的接力链同一条）。
- 为什么挑队尾：队尾就是用户**下一个会滑到**的位置，补厚它后面才不会"滑到最后一条就没了"。
- 顺带收益：这次详情请求会被 `VideoDetailRepository` 缓存，用户真滑到那一支时
  标题/简介直接命中缓存。
- 日志：`more fallback: tail=… added=… queue=…`（真机可直接确认兜底有没有生效）。

### 3.10 队列到底的反馈
- 新增 `SwipeQueueTail`（Idle/Extending/Exhausted）+ `resolveSwipeQueueTail(appended)`：
  补货开始置 Extending，结束按"净增是否为 0"落 Idle/Exhausted；
- `PortraitSwipePager` 在**停在最后一页**时于底部居中显示提示：
  「正在为你找更多视频…」/「已经是最后一个了」；
- 以前滑到最后一条**什么都看不到** —— 用户分不清"卡住了"还是"真的没有更多了"
  （BiliPai 的 story 页有明确三态，这是对齐它的最低成本版本）；
- 提示不可点、不消费触摸（上下滑与返回手势照常），间距走 `BiliSpacing` token
  （不新增 dp 字面量，避开 lint 棘轮）。

### 3.11 会话内常驻信息：标题 + UP（信息层第二阶段第一步）
- `VideoPlayerPane` 新增 `SwipeSessionInfoLine`：左下角两行（标题 `titleSmall` 单行省略 /
  `@UP名` `bodySmall` 72% 白），与常驻进度条同一门控（`swipePagingActive && !swipeWaitingFirstFrame`）。
- 为什么：连播时控件 2 秒自动隐藏，用户连"在看谁的作品"都不知道；BiliPai 的竖屏页
  默认常驻信息区 + 互动栏（`PortraitFullscreenOverlay.kt:194-394`）。这里只搬**信息**，
  不搬互动按钮 —— 最小且不打扰的一步（互动栏是下一步，需要复用点赞/评论/收藏/分享的
  既有入口，属独立改动）。
- 只读、不可点（连播时任何可点区域都会和上下滑抢手指）、单行省略（长标题不推高画面）、
  间距走 `BiliSpacing`（不新增 dp 字面量）。

### 3.12 播完行为可配：自动翻下一支（对照 BiliPai 的 `playbackCompletionBehavior`）
- 新增设置 `PlayerPlaybackPrefs.swipeAutoAdvance`（默认 **开**）+ 播放器侧栏开关
  「播完自动下一个」（副标题写明"与单曲循环互斥"）。
- 判据抽到 `shouldAutoAdvanceToNextSwipePage(autoAdvanceEnabled, repeatOne, isLastPage,
  alreadyAdvancedForThisVideo)`：四个入参缺一不可 ——
  以前是"只要不是单曲循环就自动翻"，用户想"看完停在结尾"没有办法；
  而幂等键（同一支只翻一次）也在同一条判据里，避免退化成"跳两支"。
- pager 的 `Player.Listener` 只负责喂参数；`DisposableEffect` 的 key 加上开关本身，
  设置改动即时生效（不需要重进会话）。

### 3.13 会话内互动栏（信息层第三阶段第一步）：点赞 + 分享
- `VideoPlayerPane` 新增 `SwipeSessionActionRail`（右侧中部，纵向两个按钮 + 赞数）：
  - **点赞**：`detail.userState.liked` 高亮 + `detail.stat.like` 计数 + `viewModel.toggleLike()`；
  - **分享**：`ShareUtils.videoUrl(bvid, aid, page = 0)` + `ShareUtils.shareText(context, title, url)`
    —— 与详情页**同一套**链接构造与分享面板，不另写一份。
- 为什么是这两个：它们的"状态/动作/依赖"都现成。收藏要先选文件夹
  （`toggleFavFolder(fid)`）、投币有二次确认交互、评论面板在 bbspace 里是详情 pager 的
  **一页**（`VideoDetailPage.kt:238` 的 `CommentPanel(subject, isActive = pagerState.currentPage == page)`）
  而不是弹层 —— 要在连播里给评论入口，必须**另起一个弹层宿主 + 评论列表状态**
  （`commentListState`/`commentThreadListState` 现在活在详情页作用域里）。
  这是下一个明确的、独立的改动，不做假按钮。
- 触摸：会话覆盖层里的可点区域（除失败态重试按钮），固定在右侧中部，不挡手势起手区。

### 3.15 预取顺带热详情（信息层与预取的收尾衔接）
- `VideoViewModel.prefetchEntry` 里，除了 `preloadPlayUrl`，还调用
  `detailRepository.fetchVideoDetail(ids, src)`（同一个 `toPlayableParams()`，失败静默）。
- 为什么：连播页左下角的标题/UP 直接取 `videoState.detail`，而详情原本是**开播时**
  才并发请求的 —— 只预热播放地址就会"翻过去先空一拍再补上标题"。
  预热后 `StreamPlaybackSessionImpl` 的 `reuseDetail` 短路会命中，
  连"取详情"这次请求都省了（详情仓库自带 LRU）。
- 这条把 §3.11（常驻标题/UP）与 §3.2（相邻页预取）缝在了一起：**预取 = 地址 + 详情**。

## 五、真机验收记录（OPPO PLC110 / Android 16，2026-09-29 补测）

设备接回后按清单跑了一遍，**同时抓到一个只有真机能暴露的实现 bug**（已修 + 已复测）。

### 5.1 真机发现的 bug（已修）

**症状**：进场后**完全没有预取日志**，要等用户先滑一次才预取 —— 等于"相邻页预热"没生效。

**根因（两处叠加）**：
1. 进场那一刻队列还是空的（`available = pages.size - page - 1 = 0`）→ `prefetchCount` 返回 0
   → 第一轮预取空转；
2. 预取 effect 的 key 只有 `pagerState`（没有 `pages`）→ 队列到货后不会重跑；
3. 而且"停稳"分支判的是 `offset == 0f`，真机停稳时 `currentPageOffsetFraction`
   并不精确为 0（浮点残差 / settle 收敛）→ 那一支永远不触发。

**修法**：
- 新增一条**不依赖 offset** 的触发（`LaunchedEffect(pages.size, pagerState.currentPage)`）；
- "停稳"判定改为容差 `|offset| <= SETTLED_OFFSET_EPSILON(0.02f)`；

## 七、真机反馈三问的处理（2026-09-29 第二轮）

### 7.1 「加载动画像盖了一层遮罩」→ 已修：封面铺底 + 轻遮罩 + 小粒子

**原因**：换页瞬间封面页被换成播放器页，而播放器页此刻盖的是**不透明深色渐变** ——
观感是「封面 → 一块黑布 → 视频」。

**修法**（`SwipeWaitVeil` 新增 `coverUrl`）：
- 用**这一页的封面**铺底，且与 `SwipeCoverPage` **同一个 URL/变体/取景**
  （`BiliImageVariant.PlayerPreview` + `ContentScale.Fit` 居中）→ 看到的是同一张图，不是"另一层东西"；
- 遮罩从"不透明深色渐变"改成**轻遮罩**（`WaitVeilScrimTop/Bottom`，约 45%/55% 黑）；
- 粒子缩到 20% 屏宽（有封面时它只是"在加载"的提示；无封面时才回到 34% 的"主角"尺寸）；
- 没有封面（字段为空/失败态）时自动退回原来的深色底。
- 用户原话里的两个选项（"把预览图优化好、完美显示在视频中间" / "学 BiliPai 不加载预览图"）
  选的是前者 —— 封面页在 C9 就已经是"不裁切 + Fit 居中"，所以这一层与它天然连续。

真机证据（切页后 250ms 截图）：整屏是该页封面（上下黑边、居中）+ 中心小粒子；
`docs/ai-loop/shots/veil_new.png` / `veil_t250.png`（shots 目录被 .gitignore 忽略）。

### 7.2 「点刷视频模式先推差不多类型的视频」→ 已对齐 BiliPai：起步改用首页推荐流

**对照证据**：
- BiliPai `StoryViewModel.kt:23` 注释原文：「竖屏视频流：数据源与**首页推荐一致**
  （`VideoRepository.getHomeVideos`），内容更元化」；`:42` 就是 `getHomeVideos(idx = 0)`；
- bbspace 之前用 `x/v2/feed/index/story`（`storyFeedRepository.fetchStoryFeed(aid, bvid)`）
  —— 一个**以种子视频为锚**的竖屏流，天生"跟你刚看的差不多类型"。

**修法**：`bootstrapStorySession` 先用首页推荐流（`feedRepository.fetchFeed(idx = 0)`，
与推荐页同源、同一 App 签名通道），story 竖屏流只在首页流拿不到内容时兜底；
补货继续用 `fetchFeed(idx)` —— 两条腿现在都是首页流。

真机证据：`bootstrap: source=home seeded=9`。

### 7.3 「加载动画有没有故意拖慢加载时间？」→ 没有，有数据

真机时间线（`PortraitSwipe` tag，一次上滑）：

```
08:54:24.020  swipe: page=2                      ← 换页
08:54:24.133  veil: waiting=true  firstFrame=false
08:54:24.549  veil: waiting=true  firstFrame=true   ← 首帧到达（换页→首帧 529ms）
08:54:24.604  veil: waiting=false firstFrame=true   ← 遮罩撤（首帧后 55ms）
```

- **没有被刻意拖慢**：遮罩的清除条件只有"首帧到达"（或这一支出错），没有任何最短展示时长、
  没有 sleep、没有人为延时；首帧一到就撤（本次 55ms；上一轮实测 19ms）。
- 遮罩时长 = **真实加载时长**（本次 471ms，前几次 580~690ms），不是被拉长的。
- 视觉上多出来的只有 200ms 的淡出（`LocalAnimations.medium`），且它是**叠加在已经出画面的视频上**淡出，
  不阻塞播放（时间线里 `firstFrame=true` 时 `state=Buffering`，说明画面已经出来了）。
- 反方向还有收益：预取把 playurl 提前拿到，切页时 `PlayViewUnite: playurl cache hit`，
  省掉一次 gRPC 往返 —— 实测过（§5.2 第 1 条）。
