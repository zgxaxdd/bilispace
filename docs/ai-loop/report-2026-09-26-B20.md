# 批次报告 · B20 · 2026-09-26 · PF-05 选区路径 + PF-06 形状分配（含一条已过期的 BACKLOG 描述）

**分区**：B-流畅｜**级别**：A 级·可机器判定（写法层面；真机帧率不下结论）

## PF-06 复核：**BACKLOG 那句描述已经过期**

原文是"勋章拼图五个 `PolygonShape/StarShape` 在组合体内联构造"。实测：那五个**早就**收在
`UserCollageShapes` 这个文件级 `private object` 里（`feature/user/.../UserCollageSection.kt`），
不在组合体内。所以按原描述动手会去"修一个不存在的东西"。

真正还内联的是**播放器**那一批（用一次性扫描测出来的，不是照抄描述）：

| 文件 | 原先 |
|---|---|
| `VideoScreen.kt` | `val expandedPlayerShape = RoundedCornerShape(BiliRadius.player)`、`val compactPlayerShape = RoundedCornerShape(bottomStart/bottomEnd = …)` |
| `VideoPlayerPane.kt` | `val trackShape`、`val shape`、`val pillShape`、两处 `shape = RoundedCornerShape(20.dp)` 裸字面量、一处 `.clip(RoundedCornerShape(BiliRadius.playerControl))`、一处 `else -> RoundedCornerShape(16.dp)` |

全部提到文件级 `private val`（取值只依赖 `BiliRadius` 里对象上的普通 dp `val`，
**不读主题状态**，所以提升是恒定值 —— 这点先确认过再动，否则就是引入"主题切换不再生效"的 bug）。

它们的实际代价不只是"每次重组新建一份 Shape"：这些值同时被 `clip` / `background` / `border`
和那条 `remember(backdrop, shape, scrim, …)` 的玻璃链当**键**用 ——
键每次重组都是新实例，`remember` 的等价判断就一直判"变了"，等于把 B3/P3 那轮
"remember 住整条链"的优化静默抵消。

## PF-05 选区背景路径

`TextLayoutResult.getPathForRange` **只有返回新 Path 的重载**（javap 查 ui-text 1.11.2 与 1.12.1，
都只有 `getPathForRange(int, int): Path`，没有可复用的 `dest: Path`），
所以"选区变了分配一次"省不掉；能省的是**重绘但选区没变**的那些 —— 原先它写在 `drawBehind` 里，
列表滚动、父级动画、别处失效都会重绘一次、分配一个 Path。改成带 key 的 `remember(textLayoutResult, selection, text.length)`。

## 守卫：把 W7 说的"覆盖面"补上

`ListAllocationStructureTest` 原先只盖 `RoundedCornerShape` 的**变量名含 Shape** 的写法，
`val octagon = PolygonShape(...)`、`Path()`、`Outline.Generic(...)` 全都不在视野内。
新增 4 条断言：

1. `shapeConstantsAreNeverBuiltInsideComposables`：全仓不许在函数/composable 体内就地构造形状。
   **判定不看变量名，看包住这一行的最外层顶层声明**：`private object X {` 里的是文件级常量（正确），
   `fun` 里的是调用期分配。自检用一段合成样例（正反各一例）证明规则抓得到东西 ——
   没有这个自检，"全仓 0 处"完全可能只是正则写错。
2. `collageShapesStayInFileLevelObject`：五个形状常量还得在那个对象里（防回潮）。
3. `pathAndOutlineAllocations_areFrozenAtMeasuredBaseline`：`Path()` / `Outline.*` 按**实测 4 处**冻结，
   全部在 `UserCollageCanvas` 的 `createOutline` / `build*Path` 里（那是 Shape API 要求的分配）。
   这正是 W7 说的"棘轮的覆盖面 = 它真正会红的写法集合"。
4. `selectionPathIsRememberedNotBuiltPerRedraw`：`getPathForRange` 不许回到 drawBehind 里，
   且那个带 key 的 remember 必须还在。

## 验证

```
:feature:video:compileDebugKotlin + :core:designsystem 测试 + 全量（先删 test-results）
  → BUILD SUCCESSFUL in 4m56s，**268 单测 / 0 失败 / 0 错误**（264 → +4）
破坏性验证：
  ① 把一处形状改回内联 → 断言 1 FAILED（精确报出文件与行号）
  ② 把 getPathForRange 塞回 drawBehind → 第一次**没咬**：
     锚点用了 `it.contains("drawBehind")`，而我新写的性能注释里正好有"原先这段在 drawBehind 里"，
     扫描起点被带到 KDoc 上、抓的是无关区块 → 断言永真。
     改成只认代码形态 `^\s*\.drawBehind\s*\{` 后，同一个改坏立刻 FAILED。
  ③ 自检样例本身也抓出过一个真 bug：`Regex.matches`（整行匹配）误当成 containsMatchIn，
     文件级 object 没被放行 → 自检红，修后才对。
```

**②③ 是同一条教训的两次兑现**：文本扫描型断言的锚点必须"只认代码形态"、
并且**每条都要有一个能失败的正例反例对**，否则它绿得毫无意义（W5 / W20 的同类）。

## 边界

- 本批全是"少分配对象"的写法层改动，**没有帧率结论**：PF 类收益要真机 A-B-A ≥5 轮取中位才能说，
  当前无设备接入这一环（记忆里第二轮的结论也提醒过：稳态 jank 0.21% 已达标，
  这类改动在稳态上大概率测不出差异）。
- 没动 `UserCollageCanvas.createOutline` 的 Path 分配：那是 `Shape` API 的形状，
  要省只能按 size 缓存 Outline，属于另一件事且需要真机验证裁剪正确性。
