## 1. 缺陷

`PlaybackHostState` 是 `@Singleton`，上面挂着 `var onPlaybackUiStarted: (() -> Unit)?`。
`MainActivity.onCreate` 把它赋成 `{ pendingNotificationPermission = true }` —— 一个捕获 `this` 的 lambda，
而 **MainActivity 连 `onDestroy` 都没有重写**，所以这条引用永不清理。

为什么平时看不出来：正常重建时，新实例的 `onCreate` 会把字段覆盖掉，泄漏窗口只有几毫秒。
真正漏的是**本仓的核心场景 —— 后台播放**：MainActivity 可以销毁而不再重建
（进程靠播放会话与前台服务活着），此时单例长期持有那个已死的 Activity，
连带整棵 Compose 树与 `ViewRootImpl`（低端机上这类持有正是 OOM 的常见最后一根稻草）。

## 2. 修法

| 位置 | 改动 |
|---|---|
| `MainActivity.kt:96+` | 回调提成 `private val playbackUiStartedCallback`，注册点改为引用它 |
| `MainActivity.kt` `onDestroy` | **新增**：按身份比对清理（`if (hostState.onPlaybackUiStarted === playbackUiStartedCallback) ... = null`） |
| `app/src/test/.../SingletonCallbackLeakGuardTest.kt` | **新增 4 条**结构守卫 |

两个设计细节（都不是顺手，是必需）：
1. **按身份比对而不是无条件置 null** —— 重建时序下新实例可能已经装好它自己的回调，
   无条件清会把它的清掉，通知权限标记从此再也打不上。为此回调必须是 `val` 字段
   （内联 lambda 每次都是新实例，身份比对必然失配）。
2. 清理后 `expand()` / `onVideoDetailStarted()` 的 invoke 变成空操作 —— 这是正确的：
   那个权限对话框只能由活着的 Activity 弹。用户回到前台时 MainActivity 重建，回调重新装上。

**没做的事**（避免超出批次主题）：把 `pendingNotificationPermission` 上移到单例里，
让"权限请求意图"跨 Activity 生存在。那是状态所有权重构，且会改变弹窗时机语义，
留作 BACKLOG 跟进项，不在本批顺手做。

## 4. 顺带修掉的一处自身失误

`B1` 新建的测试文件我按 `com/naammmee/...`（拼错）建了目录，而包名是 `com.naaammme.bbspace...`。
**Kotlin 不强制目录等于包名**，所以它照样编译、9 条测试照样跑绿 —— 这个错误不会被任何门禁拦住。
已 `git mv` 归位（commit `bb0edd3a`，纯移动无内容改动）。
