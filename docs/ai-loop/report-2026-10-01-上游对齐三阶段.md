## 二、阶段二 · 内存 / CPU / 卡顿（P1+P2+P3）

1. **取色不再复制整张位图**：`bitmap.copy(ARGB_8888)`（640×480≈1.2MB、960×540≈2.1MB，
   每张染色卡片一次、无人回收）→ 画进 96² 软件小样（≈36KB）+ finally recycle。
   少两个数量级的大对象 = 滚动期 GC 停顿的来源之一。附带 `Dispatchers.Main.immediate`
   （命中缓存也"先白后有色"晚一帧的那一处）；另两处从 Default 跳回主线程的 `withContext` 不改。
2. **图片宽度夹取**：`Banner` / `PreviewThumb` 原先落到 `thumbnailUrl(url, q)` ——
   **只限质量不限宽度**，图床按原尺寸返回。新增 `widthLimitedImageUrl`，1280w / 480w。
3. **切后台的绝对预算**：`onTrimMemory` 原先只按"派生容量的一半"收，而派生容量来自
   `maxSizePercent(0.25)`，HARDWARE 位图不吃 Java 堆 → 比例约束不了实际占用。
   新增纯函数 `imageCacheTrimTargetBytes`（比例 / 24MB / 容量取最小，已在预算内返回 null 不动）。

**未做并写明理由**：磁盘图片缓存 256MB **不动**（`BiliApplication` 注释里那条
"100MB 在浏览几十屏后就被挤满 → 回看走网络重解码"是真机结论，上游砍到 100MB 是它自己
涨到 680MB 的前提，两边情况不同）；`ComposeFoundationFlags` 全局开关无复现证据前不开。
