**来源**：资源/内存审计第 1 条 → 自己读源码复核为真（全文件 `grep WebView|onDispose|destroy` 只有创建那一行）。

## 1. 缺陷

`feature/auth/.../sms/GeetestDialog.kt` 用
`AndroidView(factory = { ctx -> WebView(ctx).apply { … addJavascriptInterface(bridge, "GeetestBridge") … } })`
造 WebView，**没有 `onRelease`、没有 `DisposableEffect.onDispose`、全文件没有 `destroy()`**。

WebView 不是普通 View：它带自己的渲染进程与 native 堆，组合体离开后"没人引用"并不等于能回收。
每过一次人机验证就泄漏一个，而极验正是在**短信登录失败重试**时被反复触发的那条路径。
桥对象还捕获着 `onResult` / `onDismiss`，于是连调用侧的作用域一起被拖住。

同仓 `WebViewScreen.kt:175-188` 用的是正确写法（`DisposableEffect { onDispose { … destroy() } }`）——
说明约定本来就存在，只是没有机器拦住"漏一处"，所以这一批的重点一半在守卫。

## 2. 改动

| 位置 | 改动 |
|---|---|
| `GeetestDialog.kt` | `AndroidView` 补 `onRelease = { webView -> stopLoading(); removeJavascriptInterface("GeetestBridge"); destroy() }` |
| `app/src/test/.../resource/ResourceReleaseGuardTest.kt` | **新增 3 条**守卫（全仓扫 WebView 创建点） |

两个细节：
- **先摘桥再 destroy**：`onSuccess` 里是 `post { onResult(result) }`，回调可能在视图销毁之后才落到
  主线程；桥不摘就仍然持有整个 composable 作用域的捕获。守卫里把"摘桥必须早于 destroy"也钉住了。
- 选 `onRelease` 而不是 `DisposableEffect`：`AndroidView` 的 `onRelease` 与该 View 一对一绑定，
  不会因为 key 变化而被漏调或重复调。

守卫**不带白名单**（与 B3 不同）：两个创建点都已合规，任何例外只会在下次评审时被顺手加宽。
正则用 `\bWebView\s*\(`，靠词边界把 `navigateToWebView(url)` 这类同名函数排除掉。
