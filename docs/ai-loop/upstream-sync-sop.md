# 上游同步 SOP（BiliPai → bbspace）

> **为什么要有这份文档**：上游同步这件事本仓已经跑通过至少 4 轮（v0.2.3 / v0.2.3.5 / v0.2.4 / 移植批次），
> 但每次都是"重新调研一遍"——重新判断哪些能搬、哪些不能、依据在哪。
> 这份 SOP 把流程固定下来，让下一次变成**可计算的 delta**，而不是重做一次可行性分析。
>
> **适用**：`_ref/BiliPai`（旧基线）或 `_ref/BiliPai-024`（当前基线仓）出现新提交时。
> **不适用**：把上游当"版本升级"直接合代码——两仓模块划分不同源，**不存在可合并的分支关系**。

---

## 0. 两条硬约束（先记住，后面六步都受它们约束）

1. **不许用 `git checkout` 切上游仓**（`FINDINGS` **W1**）。回退工作区会把用户正在看的文件抹掉。
   用 **`git worktree`** 或直接 `git fetch` + 只读的 `git log/show`。
   参考仓（`_ref/*`）**永远只读**，不在里面做任何本地改动。
2. **收口时必须更新基线**。基线没更新 = 下一轮会把同一批提交再"发现"一次，delta 永远算不对。
   基线落在 `docs/ai-loop/PROGRESS.md` 的对应批次里（当前：**`6e6bdce36`** = v0.2.4）。

## 1. 六步流程

### ① 建隔离工作区 + 取新提交

```bash
git -C <上游参考仓> fetch origin            # 参考仓只读，不做本地分支
git -C <上游参考仓> log --oneline <基线>..origin/main
```
- 不要 `checkout`。要读文件就 `git -C <仓> show <ref>:<path>`，或建一个**独立** worktree
  （`git worktree add /tmp/upstream-<sha> <sha>`）读完即删。
- 记录新 tip 的 sha 与 tag（如 `6e6bdce36` / v0.2.4），后面写进报告。

### ② 逐文件 `--numstat -M`，区分"纯搬运"与"行为变化"

```bash
git -C <上游参考仓> log --numstat -M --oneline <基线>..origin/main
```
- `-M`（rename detection）**必须有**：模块重构会让文件"看起来是新增"，实际是搬运。
  历史教训：U1 分析里大量文件其实是纯搬运，只看文件数会把重构误判成功能增量。
- 判据：**新增行里有没有改变行为的代码**？纯搬运（路径变了、内容逐行相同）→ 不算 delta。

### ③ 逐条读上游原函数并写出边界条件

对齐 `FINDINGS` **W4**：交接文档/任务书的断言**必须自己回读源码再采信**。
对每个候选能力，先写下：函数签名、边界条件（空值/极值/失败路径）、调用点。
- 本系列的强制产物：**"与上游的差异点"段落**（见 ⑤）。
- 实证：PT 批次里任务书自己也有两处偏差（`WbiKeyProvider` 的模块归属、`httpsImageUrl()` 不补 `//`），
  都是回读源码才发现的 → 见 `FINDINGS` W30/W31。

### ④ 分级分类（A / B / C）

| 级别 | 含义 | 交付要求 |
|---|---|---|
| **A · 等价移植** | 纯函数 / 自包含 | 逐字对齐上游语义 + 纯 JVM 单测（**含上游边界用例**） |
| **B · 重写适配** | 结构不同构 | 只搬语义/判据；接线重设；写明差异点 |
| **C · 不建议移植** | 架构/产品/跨仓/无 substrate | 归档算法作参考，写理由（**不许用"看起来是死代码"当理由**——先核消费者，S3 的教训） |

"结构不同构"的实证清单在 `docs/2026-10-03-BiliPai移植-执行报告.md` §2 与任务书 §1。

### ⑤ 写任务书（每项固定字段）+ 强制段落

字段固定为：目标｜可行性级别｜上游依据（`BP:<file>:<line>`）｜bbspace 落点（**行号以当前工作区为准**）｜
依赖核查｜要点｜验收（二值）｜风险与回滚｜工作量。

**强制段落：与上游的差异点**。没有这一段，下一轮会把"我们故意没照抄的地方"当成遗漏。
另需在任务书开头写清：**哪些项会改变用户可见默认值**（默认行为不变是底线）。

### ⑥ 执行 + 收口 + **更新基线**

按任务书的轨道划分执行（能无设备的 / 必须设备的）。收口三件套：
1. 逐模块 `--rerun` 全绿（**逐个**调用，见下）；
2. `:app:assembleDebug` 成功；
3. **更新基线**并写进 `PROGRESS.md`；把新识别的未做项/偏离登记进报告。

## 3. 长期注意项（跨轮次，别忘）

1. **WEB 推荐流的映射表必须抓包校准**。`WebFeedMapper` 是照上游 `RecommendItem` 模型写的，
   而**上游模型可能滞后于服务端**（上游仓自己也是这么标注的）。
   2026-10-03 已在真机验证一轮（字段/封面/角标/翻页/路由全部正确，见
   `docs/2026-10-03-下一步-NX-执行报告.md` 的 Track B 小节），但**服务端随时可能改**——
   凡是改 `WebFeedMapper` 的字段，都要重新抓包，不要只跑单测。
2. **"上游有而本仓没有"不等于"应该搬"**。C 级判定的历史案例（插件系统、miuix-navigation、
   折叠屏铰链、Firebase）都是"上游解决的是本仓没有的问题"。
3. **撤销过的项不要重开**：PT-05（后台实例判据）、PT-07（多理由透传）已撤销，理由写在
   `docs/2026-10-03-BiliPai移植-执行报告.md` §4.1。重开前先读那两节。
4. **本仓没有 `CHANGELOG.md`**（与上游不同）。不要按上游习惯"更新 CHANGELOG"。
