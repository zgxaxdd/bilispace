# 批次报告 · B14 · 2026-09-26 · ST-06b 两处 NonCancellable 记账收口

**分区**：A-稳定 P1｜**级别**：A 级·可机器判定

## 收口的两处

| 位置 | 语义 |
|---|---|
| `core/comment/.../CommentRepository.kt`（发评论之后） | 评论**已经发成功**，后面只是把"我的发布"记录写进本地库 |
| `core/live/.../LiveRoomMessageRepository.kt`（发直播弹幕之后） | 同上，弹幕已发送成功 |

两处都从"刻意保留的裸 `runCatching`"升级为：

```kotlin
withContext(NonCancellable) {
    runCatching { publishedRecordRepo.save(…) }.onFailure { Logger.e(…) }
}
```

判据（B8 立的 W14）：这两处**不能**换成 `runCatchingCancellable` —— 那时网络操作已经完成，
传播取消会把一次**成功的发送**改判为失败（表现为"发出去了但输入框不清空/列表不刷新"），
比原缺陷更伤用户。但也不能就这么留着：用户切页/关窗时取消会顺手抹掉这条本地记录，
所以正解是让记账跑在不可取消的上下文里。

## 守卫升级

`CancellationSweepGuardTest.deferredSitesKeepTheirExplanation` 原先只查"解释注释还在 + 有裸 runCatching"。
本批正解落地后，它升级为三条：

1. `publishedRecordRepo.save(...)` 必须落在 `withContext(NonCancellable) { runCatching { … } }` 里；
2. 每个文件"未包 NonCancellable 的 runCatching"数量按登记上限棘轮（comment 0、live 2）；
3. `ST-06b` 标记注释必须还在（那是唯一的防误改说明）。

**第 2 条是被迫加出来的**：我最初把规则写成"这两个文件里每个 `runCatching` 都必须被 NonCancellable 包住"，
第一次跑就红了 —— 它如实报出 `runCatching { JSONObject(text) }`（JSON 解析）与 `runCatching { close() }`
两处**合法**的非挂起站点。规则必须精确到缺陷本身，不能按文件一刀切，
否则下一步就是被逼着加豁免、守卫就此变成噪音（同 B6 前缀规则、B9 上限拍 0 的教训）。

## 边界与未做
