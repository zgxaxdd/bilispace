**级别判定**：**A 级·可机器判定** —— 纯字节函数的正确性，JVM 单测可完全判定，不涉及任何主观观感，

## 1. 缺陷与根因

`SingleFileDashMediaSourceFactory.parseIndex()` 只认 MP4 盒头的**一种**形态：

```kotlin
val size = readUInt32(data, pos).takeIf { it > 0 } ?: return null   // size==0 直接整盘放弃
if (pos + size > data.size) return null
pos += size                                                          // size==1 时按"盒长 1 字节"走
```

ISO/IEC 14496-12 §4.2 规定三种合法形态：`size`（32 位）、`size==1` + 8 字节 `largesize`、
`size==0`（延展到末尾）。后两种被当成非法。

**为什么这不是小事**：解析失败在调用侧不是降级，而是
`buildDashStream` 里的 `error("单文件 dash 索引缺失")`；上层 `Media3PlayerEngine.setSource`
只把它写进 `errorMessage` 并重新抛出，**没有任何 fallback 路径**
（`CdnFailoverDataSource` 只换 CDN 线路，不换封装解析）。
所以"合法但少见的头部形态" = 该视频直接起播失败。

`readUInt32` 还带 `throw EOFException`：目前被循环守卫挡住没炸过，但这是一条
"改一行守卫条件就变成崩溃"的暗线。

## 4. 遗留与边界（诚实记录）

1. **`size==0` 支持属"把语义做对"，不是线上故障修复**：规范上零长度只对"最后一个盒"合法，
   而本扫描器在 `sidx` 处就收尾，实际很少走到。测试注释里写明，不冒充收益。
2. **`sidx` 排在 `moov` 之前仍然判失败，这是刻意的**：init 段定义是"开头到 moov 末"，
   sidx 在前会让两个 Range 重叠、init 缺数据 —— 放宽它等于把"起播失败"变成"花屏/坏帧"。
   已用 `sidxBeforeMoovStaysRejected` 钉住，防止后人顺手"兼容"。
3. **预取窗口 91536 字节未动**：索引超出窗口仍是 `null` → 起播失败。改窗口大小是**网络行为**
   改动，需要真机与抓包判断（B 站真实索引分布未知），已入 BACKLOG B-流畅 + L4 清单，
   不在无设备条件下翻默认值。
4. **B 站 m4s 是否真的存在扩展大小头，未经实测**。本批次只保证"合法形态不再被判非法"，
   不声称修好了某个具体视频的起播 —— 那是需要探针日志确认的第三方行为（任务书 §2.3）。
