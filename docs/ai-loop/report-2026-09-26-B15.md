## ST-09 `ListenDetailScreen` 的 `dragFraction!!`

复核**成立**，而且是真崩溃：`Slider.onValueChangeFinished` 在无障碍 / IME 路径下
可以在**一次 `onValueChange` 都没有**的情况下到达，那时 `dragFraction` 仍是 null。
文件里两处 `!!`：`displayMs` 那处外面包了判空（不崩但白写），
`onValueChangeFinished` 那处**没有判空** → 一触发就是 `KotlinNullPointerException`。

修法是把"拖动目标"抽成纯函数 `listenSeekTargetMs(fraction, durationMs): Long?`
（同文件 internal），两处都改用它：
- `displayMs = listenSeekTargetMs(...) ?: positionMs`
- finished：`listenSeekTargetMs(...)?.let(onSeek)`，然后照常清 `dragFraction`
  —— 没拖过就不 seek，而不是崩或跳到 0。
顺带把 fraction 夹回 `0f..1f`（越界一次就会 seek 到负数或超过总时长）。

抽成纯函数的真正收益是**能上 JVM 测**：不需要 Compose 语义树也不需要设备。
`ListenSeekTargetTest` 4 条（无拖动 / 时长未知 / 线性映射 / 越界夹紧）。

## ST-10 `ImageSaver` 的 `as HttpURLConnection`

**严重度经复核下调**（BACKLOG 写的是"逃出 API 契约"，方向对但不是崩溃）：
- `(URL(rawUrl).openConnection() as HttpURLConnection)` 确实写在 `runCatching` **之外**，
  scheme 又来自服务端可控的 `originImageUrl`（取不到就用原串，原串可能空/怪）。
- 但唯一的调用方 `PreviewImageGrid` 把整个 `saveUrl` 包在 `runCatching` 里，
  所以 CCE **不会崩给用户**。
- 真正的用户可见伤害是：那个调用方把 `err.message` 直接弹进 Toast ——
  于是用户看到的是一行 `sun.net.www...FileURLConnection cannot be cast to java.net.HttpURLConnection`，
  而该说的是"这个地址存不了"。

修法：新增 `internal fun openImageConnection(rawUrl)`，只做协议判定与超时配置，
非 http/https 抛 `IllegalArgumentException("不支持的图片协议")`、
解析不了抛 `IllegalArgumentException("无效的图片地址", cause)`；
`saveUrl` 的连接建立移进 `runCatching` 之内，并用 `try/finally` 保证 `disconnect()`
（原先挂在 `.also { }` 上，靠的是"异常也被 also 吃掉"这种隐式顺序）。

`ImageSaverUrlTest` 4 条，全部纯 JVM（`openConnection` 只建对象不联网）。

## 一条新的平台差异坑（写测试时踩到）

`content://` 在 **JVM 上没有协议处理器**，`URL(...)` 直接抛 `MalformedURLException`
（走"无效的图片地址"那条）；在 **Android 上它有 handler**，会返回非 Http 的 connection
（走"不支持的图片协议"那条）。我最初按具体 message 断言，第一次跑就红。
**结论**：跨平台行为差异下的测试要断言**契约**（受控失败、绝不是 ClassCastException），
不要断言走了哪个分支 —— 已记 FINDINGS **W19**。
