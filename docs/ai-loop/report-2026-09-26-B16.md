## ST-11 下载：删行与删文件不成对，孤儿目录无人清

复核**成立**，而且产生路径写在代码注释里（`delete()` 里那段 D1 审查说明）：
drain 抢占窗口内 `runTask` 会带着已删实体继续 `mkdirs` 并写完整个下载，
终态 `dao.update` 对已删行是静默 0 行更新 → 产出**几百 MB 的无主目录**，
而启动恢复只按 DB 驱动，没有任何机制会再去看这些目录。

修法：
- 新增 `internal fun sweepOrphanTaskDirs(root, liveTaskIds): List<String>`（纯 `java.io.File`，
  不需要 Android、不需要 Robolectric）。
- 规则**刻意保守**：只删"名字能解析成 Long 且与规范 id 写法一致 + 确实是目录 + DB 里没有行"的直接子项。
  认不出的一律不碰 —— 漏删一个目录的代价远小于误删用户的缓存。
- DAO 加 `allIds()`（只问 id，不读整表）。
- 挂在启动路径 `recoverRunningTasks()` 之后、`ensureDrain()` 之前，
  并且 **fail closed**：`runCatchingCancellable { dao.allIds() }` 拿不到就 `return`，
  绝不把"查询失败"当成"没有任务"（那会删光用户所有缓存）。

## ST-12 IM 的按账号 prefs 文件不随账号删除回收

复核**成立**：`ImRepository.getDeviceId` 为每个 mid 建一个
`SharedPreferences("IMFieldsCache$mid")`，而 `AuthStore.removeAccount` 只删
`account_$mid` / 用户信息两个 key → 那个 xml 永久留在 `shared_prefs/` 里。

修法与依赖方向：
- `core:common` 新增 `PerAccountDataCleaner` 接口。
  不能让 `core:auth` 直接依赖 `core:im`（那些模块本来就依赖 auth，会成环），
  所以接口放在两端都看得见的 common，实现由 Hilt `@IntoSet` 多绑定注入。
- `core:im` 新增 `ImFieldsCache`（缓存名**唯一定义处**）+ `ImFieldsCacheCleaner`
  （`deleteSharedPreferences`，不是 `edit{clear()}` —— 后者只清空内容、文件还在）。
- `AuthStore` 构造注入 `Set<PerAccountDataCleaner>`，`removeAccount` 逐个调用，
  单个清理器抛错只记日志（不能因为某个模块缓存清不掉就让用户删不了账号）。

### 验收方式按实测改了（不假装做到了原计划）

BACKLOG 原验收是"JVM 测（fake Context）：`removeAccount(mid)` 后该文件必须不存在"。
做不到：要 fake 的是 `android.content.Context` 整套抽象类，本仓单测没有 Robolectric，
也没有网络可以现装依赖。**写一个假装成 Context 的巨型桩，测的是我自己写的桩**，
所以改成钉住真正会坏的三件事：
1. 缓存名的字面量只许有一个定义处（两边各写一份 = 改一次命名清理就静默失效，正是本缺陷的形状）；
2. `removeAccount` 确实遍历清理器、且清理器确实 `@IntoSet` 绑定；
3. 依赖方向不许反过来（`core/auth/build.gradle.kts` 里不许出现 `:core:im`）。
真机上"删账号后 `shared_prefs/IMFieldsCache$mid.xml` 不该存在"另列 **L4-20**。

## 一条新的假绿形状（W20）

接线断言第一版写成 `code.indexOf("sweepOrphanTaskDirsSafely()") > 0` ——
**它匹配到了 `private suspend fun …() {` 那行函数定义**。
于是"把 init 里的调用删掉"这种回归实测照样 BUILD SUCCESSFUL。
改成 `(?m)^\s*名字\(\)\s*$`（独占一行的调用，前面不许挂 `fun`、行尾不许有 `{`）之后，
同一次改坏立刻 FAILED。
**推论**：扫源码型断言必须先想清楚"它在文本里会不会别处也成立"，
并用改坏来证明它咬 —— 只跑一次绿的守卫，可能只是没扫到东西。

## 未做与边界

- 孤儿 GC 只在**启动时**跑一次，不做定时/前后台切换触发（那需要新的生命周期钩子，
  收益只是延后几小时回收）。
- 没有改 `delete()` 的"先删行再删文件"顺序：注释里 D1/D11 已论证过顺序与 `stopRunningTask`
  的仲裁关系，动它是高风险改动；GC 是从另一侧兜住同一个后果。
- 真机确认项：**L4-19**（清完孤儿目录后缓存视频仍可正常播放、列表数量不变）、
  **L4-20**（删账号后 prefs 文件消失）。
