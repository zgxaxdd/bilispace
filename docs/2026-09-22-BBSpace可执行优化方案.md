## 3. P0 方案（Phase 1）

### B1 封面取色回退请求与卡片显示请求缓存键不一致 → 同一封面双份下载/解码/缓存

**问题描述**：启用卡片动态染色时，每张卡片除显示请求外，还额外发起一次同 URL 的 Coil 图片请求（取色回退路径）。两条请求的缓存键不同，导致同一封面被下载两次、解码两次，内存与磁盘缓存各写两份。

**原因分析（含证据）**：
1. 取色键用**未解析的原始封面 URL**：`feature/home/src/main/java/com/naaammme/bbspace/feature/home/video/HomeVideoPage.kt:345`
   `val coverTintKey = item.cover.orEmpty()`；回退调用在 `HomeVideoPage.kt:367-384`：
   `VideoCardCoverColorStore.requestExtraction(cacheKey = coverTintKey, url = biliImageUrlForVariant(item.cover, feedCoverVariant(singleColumn)), ...)`。
2. 回退请求把**显式缓存键**设成那个原始 URL，而 `data` 是解析后的变体 URL：
   `core/designsystem/src/main/java/com/naaammme/bbspace/core/designsystem/color/VideoCardCoverColorStore.kt:76-84`
   `.data(url) ... .memoryCacheKey(cacheKey) .diskCacheKey(cacheKey)`。
3. 卡片显示请求**不设显式键**，Coil 按 `data` 派生键：
   `core/designsystem/src/main/java/com/naaammme/bbspace/core/designsystem/component/BiliAsyncImage.kt:71-78`
   （`CoverImage.kt:30-40` 转发；预加载 `HomeVideoPage.kt:214-249` 也用 `data` 派生键）。
4. **判断依据**：Coil 的 memory/disk 键在未显式指定时由 `ImageRequest.data` 派生、显式 key 覆盖之。这正是本仓已论证并修过一次的语义（`HomeVideoPage.kt:144-151` 注释、`docs/2026-09-22-BBSpace性能UI优化-执行报告.md` §4.1：URL 不同 → 键不同 → 预加载 100% 白做）。据此可静态推出：取色回退请求对缓存**必双 miss**，重新走网络 + 解码，并以另一个键写回缓存。
5. 触发面：`LocalHomeCardDynamicTintEnabled` 默认 `true`（`core/designsystem/.../color/VideoCardAdaptiveTintPolicy.kt:216`，全仓无 `provides` 覆盖）；`HomeVideoPage.kt:369` 仅判 `coverTint != null`，冷缓存与每一页新卡**每张都触发**。

**修复步骤**：
1. `VideoCardCoverColorStore.requestExtraction` 删除显式缓存键，让键回到 `data` 派生（与显示/预加载同源）：

```kotlin
// VideoCardCoverColorStore.kt  requestExtraction 内
val request = coil3.request.ImageRequest.Builder(appContext)
    .data(url)                       // 键由 data 派生 = 与卡片/预加载同键
    .size(sizePx.first, sizePx.second)
    // 删除这两行：
    // .memoryCacheKey(cacheKey)
    // .diskCacheKey(cacheKey)
    .memoryCachePolicy(coil3.request.CachePolicy.ENABLED)
    .diskCachePolicy(coil3.request.CachePolicy.ENABLED)
    .build()
```

注意：**只改 ImageRequest 的缓存键，不改 `colorCache` 的键**（仍用 `item.cover`），保证同一封面在单/双列取到同一颜色。
2. `requestExtraction` 增加 in-flight 去重（同键只允许一个取色任务，避免同封面多卡并发时重复请求）：

```kotlin
private val inFlight = java.util.concurrent.ConcurrentHashMap<String, kotlinx.coroutines.Job>()

fun requestExtraction(...) {
    if (cacheKey.isBlank() || url.isBlank()) return
    getCachedColor(cacheKey)?.let { cached ->
        if (onExtracted != null) scope.launch(Dispatchers.Main) { onExtracted(cached) }
        return
    }
    if (inFlight.containsKey(cacheKey)) return          // 已有同键任务在跑
    val job = scope.launch(Dispatchers.Default) { /* 原有逻辑 */ }
    inFlight[cacheKey] = job
    job.invokeOnCompletion { inFlight.remove(cacheKey, job) }
}
```

3. 保留 `HomeVideoPage.kt:679-704` 的 `extractColorAsync`（onSuccess 复用已解码位图、零额外请求）为主路径；`requestExtraction` 退为兜底（可加 500ms 延迟再触发，进一步压掉与显示请求的并发窗口）。

**预期收益**：每张新卡片少 1 次网络请求 + 1 次解码 + 1 份内存/磁盘缓存写入；浏览期带宽约减半；memoryCache 有效容量上升（现被重复条目挤占，上限为 25% heap，`app/src/main/java/com/naaammme/bbspace/BiliApplication.kt:204-208`）；滚动期解码抖动减少。

**潜在风险**：若误把色键也改成变体 URL，同一封面在单/双列会算成两个颜色（轻微视觉差异）；in-flight 去重需保留卡片复用时的防串色校验（`activeCoverTintKey`，`HomeVideoPage.kt:353,381-383`）。

**验证方法**：
- 行为测试（照 `core/designsystem/src/test/.../component/CoverPreloadUrlTest.kt` 的写法）：断言「取色请求键 == 显示请求派生键」「≠ 原始 URL」「同键并发只发一次」。
- 真机：OkHttp `EventListener`/抓包，连续滚动 20 张，确认每张封面仅 1 次请求。
- 内存：`adb shell dumpsys meminfo com.naaammme.bbspace`，对比深滚 30s 后 TOTAL PSS。

**验收标准**：`:app:assembleDebug` + `testDebugUnitTest` 全绿；新增测试已做「故意破坏会 FAILED」验证（把显式 key 加回去应有测试变红）。

### B2 播放页玻璃 tick 循环永不停止（暂停/读评论也每帧重录）

**问题描述**：`VideoPlayerPane` 的玻璃帧 tick 协程只要面板在组合中就永远每帧执行，暂停、缓冲、播完、在播放器下方读评论时也不例外，每帧强制重绘视频节点并重录背板。

**原因分析（含证据）**：`feature/video/src/main/java/com/naaammme/bbspace/feature/video/player/VideoPlayerPane.kt:446-456`

```kotlin
LaunchedEffect(state.playWhenReady) {
    // 注释称「key 翻转取消本协程」是终止手段
    while (true) { withFrameNanos { }; videoGlassTick++ }
}
```

`LaunchedEffect(key)` 的语义是 **key 变化 → 取消旧协程并立即启动新协程**，新协程不读 key 的值照样执行循环体；翻转到 `false` 只是**重启**循环。循环体无任何退出条件 ⇒ 只要 `VideoPlayerPane` 在组合中就每帧 +1。
消费链：`LocalVideoGlassTick provides { videoGlassTick }`（:463）→ `drawWithContent { videoGlassTick; drawContent() }`（:496-499）→ AndroidView 视频节点每帧失效重绘；`.layerBackdrop(videoBackdrop)`（:500）每帧重录；控制条玻璃（`playerControlGlass`，:297-303）每帧重采样。

**修复步骤**：

```kotlin
LaunchedEffect(state.playWhenReady) {
    if (!state.playWhenReady) return@LaunchedEffect   // 暂停/缓冲/未起播：不 tick
    while (true) {
        withFrameNanos { }
        videoGlassTick++
    }
}
```

同时更正 :448-451 的注释（原注释描述的终止机制不成立，保留会误导后人）。
进阶（可选，Phase 3 之后再做）：仅当存在玻璃消费者（控制条可见 / 胶囊可见）时 tick，门控写法参考 `feature/home/.../HomeScreen.kt:200-208`（`GlassSourceRefresher { ... }` 在 nestedScroll 回调里读 snapshot state）。

**预期收益**：暂停/缓冲/读评论期间的每帧 GPU/CPU 归零（每帧省一次视频层离屏录制 + 多个玻璃面重采样）；发热与耗电改善；不再把静止页当持续渲染。

**潜在风险**：暂停瞬间控制条玻璃可能停在上一帧——但视频画面本身静止，采样结果不变。需回归「暂停后立刻弹控制条」「暂停中切清晰度」两条路径；若出现玻璃滞后一帧，在停止 tick 前补一帧（`videoGlassTick++` 一次后再退出）。
**不要**顺手改 `LocalVideoGlassTick` 的 `() -> Int` 形态（`VideoPlayerPane.kt:226-238` 记录了它防的是「每秒重组 60 次」）。

**验证方法**：
- tick 循环内 debug 打点统计每秒次数：播放中 ≈ 帧率，暂停后 = 0。
- `adb shell dumpsys gfxinfo com.naaammme.bbspace framestats`，对比「播放→暂停后 10s」窗口的 frames 与耗电。
- `adb shell dumpsys batterystats` 前后差分（同条件 A/B）。

**验收标准**：暂停 30s 的 tick 计数为 0；暂停窗口的 `Total frames` 与空白对照页相当；播放中玻璃观感无回退（无冻结/鬼影）。

### B3 玻璃节点每重组一次就失效一次绘制缓存（playerControlGlass / glassBadgeSurface）

**问题描述**：播放页控件玻璃、卡片角标玻璃在**每次调用方重组**时都让 miuix 丢弃并重建模糊绘制缓存；而重组在播放中每秒 2 次、取色动画期每帧发生。

**原因分析（含证据）**：
1. `VideoPlayerPane.kt:281-330` `@Composable fun Modifier.playerControlGlass` 每次执行新建 `drawBackdrop(...)` 与 4 个 lambda（shape/effects/highlight/onDrawSurface）；`feature/home/.../HomeVideoPage.kt:844-859` `Modifier.glassBadgeSurface` 是普通函数，每次调用即新建（调用点 :826，每卡 2 个角标）。
2. **字节码证据**（反编译 `miuix-blur-android 0.9.4-rc01` 的 `top.yukonga.miuix.kmp.blur.DrawBackdropElement`）：
   - `equals()` 对 `shape/effects/highlight/onDrawBehind/onDrawBackdrop/onDrawSurface/onDrawFront` 逐个 `Intrinsics.areEqual` —— 对不同 lambda 实例返回 false；
   - `update(node)` **末尾无条件 `node.invalidateDrawCache()`**。
   ⇒ 调用方每重组一次、产生新 lambda，该玻璃节点的 blur/sharp/crossfade 缓存整体作废重建。
   同一事实已记录在 `core/designsystem/.../glass/LiquidBackdrop.kt:40-49`，`liquidGlassSurface` 因此 `remember(...)` 住整条链；`playerControlGlass`/`glassBadgeSurface` 没有照做。
3. 触发频率：`infra/player/.../Media3PlayerEngine.kt:558-575` 进度 500ms 轮询 → `VideoPlayerPane.kt:1021` `collectAsStateWithLifecycle` → `PlayerCtrlBarHost/PlayerCtrlBar/PlayerProgressBar` 每秒重组 2 次 → 进度轨玻璃（:1290）与滑块玻璃（:1360）缓存每秒重建 2 次；卡片侧 `animateColorAsState` 350ms 过渡（`HomeVideoPage.kt:386-391`）期间每帧重组 → 角标玻璃缓存每帧重建。

**修复步骤**：
1. `playerControlGlass` 内缓存整条链（照 `LiquidBackdrop.kt:64-94` 的写法与理由）：

```kotlin
@Composable
private fun Modifier.playerControlGlass(shape: Shape, scrim: Color, shapeHeightPx: Float): Modifier {
    val backdrop = LocalVideoBackdrop.current
    val tick = LocalVideoGlassTick.current
    val enabled = LocalVideoControlsBlur.current
    val material = LocalVideoControlsMaterial.current
    val strength = LocalGlassConfig.current.strength.coerceIn(0.5f, 2f)
    val isLiquid = material == GlassMaterial.LIQUID
    if (!enabled || backdrop == null || material == GlassMaterial.OFF) return this.background(scrim, shape)
    val refractionDp = (shapeHeightPx / 3.5f).coerceIn(2f, 10f)
    // remember 住整条链：miuix 的 DrawBackdropElement.equals 对 lambda 做引用比较，
    // 每次重组新建 lambda → update() → 无条件 invalidateDrawCache()（已反编译核实）。
    val chain = remember(backdrop, shape, scrim, refractionDp, isLiquid, strength, tick) {
        Modifier
            .drawWithContent { tick(); drawContent() }
            .drawBackdrop(
                backdrop = backdrop,
                shape = { shape },
                effects = { /* 原逻辑 */ },
                highlight = { if (isLiquid) Highlight.GlassStrokeBigLight else null },
                onDrawSurface = { drawRect(scrim); if (isLiquid) drawRect(Color.White.copy(alpha = 0.05f)) }
            )
    }
    return this.then(chain)
}
```

   - 陷阱：`tick` 是 `{ videoGlassTick }` 形态的 provider lambda（读的是 `mutableIntStateOf` 委托值），被 remember 捕获旧实例仍能读到最新值，**可以安全进键**；但若日后把它改成捕获局部变量的写法，必须改用 `rememberUpdatedState`。
2. `glassBadgeSurface` 同理：改为 `@Composable` 并 `remember(backdrop, shape) { ... }`（或在 `CoverBadge` 内 remember 后 `then`）。
3. 结构守卫：在 `core/designsystem/src/test/.../core/perf/GlassRecordChainStructureTest.kt`（或新建）加断言：`drawBackdrop(` 的调用点必须位于 `remember(` 块内；上限按现状记账并写明理由。

**预期收益**：玻璃模糊重算从「每次重组」降到「真实参数变化」；播放中每秒省 2 次 × 多个玻璃节点的 blur 重算；取色动画期角标重算归零。B7（进度插值）落地后重组频率上升也不再放大此开销。

**潜在风险**：remember 键漏记会出现「改设置但玻璃不变」（切材质/强度后仍是旧模糊）——按上面清单逐项进键；`isLiquid` 由 `material` 派生，不要重复进键导致无谓重建。

**验证方法**：
- debug 下在 `DrawBackdropNode.invalidateDrawCache` 打点（临时），统计每秒失效次数，改前/改后对比。
- `dumpsys gfxinfo` 对比 `Number Slow UI thread` 与 `Number Slow issue draw commands` 两列（口径见 `docs/2026-09-22-BBSpace性能UI优化-执行报告.md` §5-A）。
- 观感回归：播放页切「磨砂/液态」、拖动玻璃强度滑杆，控件模糊必须实时跟随。

**验收标准**：结构测试绿；改坏（去掉 remember）能让新断言 FAILED；播放中玻璃失效次数从 ≥2/秒降到 ≈0/秒（参数未变时）。

### B4 取消语义三种写法并存，裸 `runCatching` 把「取消」当「失败」

**问题描述**：「取消不能被当失败」这一语义在仓内有三种处理（`runCatchingCancellable` / 显式 `catch (CancellationException) throw` / `runCatching` + `isActive` 自补丁），仍有 20+ 处裸 `runCatching`、`catch (e: Exception)` 无守卫，取消会被记成「加载失败 / 发送失败」。

**原因分析（含证据）**：
- 项目自带 `core/common/src/main/java/com/naaammme/bbspace/core/common/coroutines/RunCatchingCancellable.kt`，并在 `feature/video/.../VideoViewModel.kt:518-524` 写明理由（标准库版把取消吞成 failure → 假提示、在已清理的 VM 上继续写状态）；但 `feature/video/src/test/.../VideoLogicGuardTest.kt:207-232` **只对 3 个播放文件**断言「不得再有包挂起调用的 runCatching」。
- 现存裸写法（逐处可查）：
  - `feature/comment/.../CommentViewModel.kt:154,292,345,379,458,592,621,670,703`
  - `feature/dynamic/.../DynamicViewModel.kt:209,249`
  - `feature/rank/.../RankViewModel.kt:91,143`
  - `feature/im/.../ImConversationViewModel.kt:122`
  - `feature/bbspace/.../PublishedRecordViewModel.kt:81,123`
  - `feature/space/.../SpaceNoteViewModel.kt:79,99`
  - `feature/home/.../HomeViewModel.kt:127,173,206,238`（`catch (e: Exception)` 同样吞取消）
- 同仓对照写法（说明这是口径不一致，不是取舍）：`feature/download/.../DownloadViewModel.kt:123,212` 与 `feature/bbspace/.../CommentSearchViewModel.kt:163-165` 显式重抛取消；`feature/favorite/.../FavoriteViewModel.kt:107-108,158-159` 用 `if (!isActive) return@launch` 兜底。
- 后果链（发评论为例，`CommentViewModel.kt:621-650`）：`publishReply` 被取消/超时 → `runCatching` 记为 failure → 提示「发送评论失败」，而请求可能已生效 → 用户重发 → **重复评论**。其余场景为假错误提示 + 在已清理 VM 上写状态。

**修复步骤**：
1. 上述 20+ 处统一换 `runCatchingCancellable`（纯解析、不可取消的 `runCatching { JSONObject(...) }` 保留，参照 `core/playback/.../RemotePlaybackReporter.kt:64-68` 的既有判断）。
2. `catch (e: Exception)` 一律改为：

```kotlin
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    _uiState.update { it.copy(errorMessage = UserFacingError.logAndMessage(TAG, e, "加载失败")) }
}
```

```kotlin
// 伪代码：按 wall-clock 自增 + 真实值到达时校正
class PlaybackClock {
    private var base = 0L; private var baseAt = 0L; private var playing = false
    fun onReal(positionMs: Long, isPlaying: Boolean) { base = positionMs; baseAt = SystemClock.elapsedRealtime(); playing = isPlaying }
    fun now(): Long = if (playing) base + (SystemClock.elapsedRealtime() - baseAt) else base
}
```

**预期收益**：进度条/时间连续平滑，主观流畅度明显提升。

**真机测试发现的两个实现问题（已修）**：
1. 镜像只在"写设置"时创建 → 从不改设置的用户每次冷启动仍走 `runBlocking` 兜底，快路径形同虚设；
   改为 `themeConfig` 首读即回填镜像。
2. 首版把镜像读盘放在首帧主线程（SharedPreferences 首次访问=读盘+解析 XML）→ 冷启动比基线**慢约 5%**；
   改为构造期后台线程加载、首帧只读 volatile 字段（`peekThemeConfigBlocking()` 变纯内存读）后持平。
   本机冷启动本就 ~170ms，`runBlocking` 的实际成本是个位数毫秒（300ms 是**上限**不是常态），
   所以 B6 在本机的绝对收益接近 0，它的价值是把"主线程阻塞上限 300ms"从关键路径上结构性移除。
