### 3.1 修掉的 6 条

### 3.2 判为**不成立**的 1 条（未改，并写明理由）

任务书 #1："`submitFav` 挂起前抓 `_favSheet.value` 快照，`onSuccess` 用它算乐观更新 →
提交期间用户改勾选会导致结果与实际发出不一致。修法：`onSuccess` 内重读"。

**这条反了。** 服务端应用的是 `addIds`/`delIds`，而这两个集合正是由那份快照算出来的，
所以"服务器现在的状态"**就等于**快照的 `selectedIds`，用快照算才是对的。
若按建议改读实时 state，用户在请求期间改了勾选，就会把**从未发出去**的选择
当成已生效去更新收藏态与 favDelta —— 那才是真 bug。

已把这段推理写进代码注释，防止后人"照任务书修好"。

### 3.3 只显式化、不改行为的 1 条

## 4. T1 · 首屏预加载：二值问题有确定答案

任务书要求必须先查清"预加载的 ImageRequest 与卡片实际请求的 memory cache key 是否一致"，
并说这是"要么完全没用、要么有用"的二值问题。**答案：完全没用，而且比不做更贵。**
但根因不是任务书猜的那个。

### 4.1 真因：URL 不同 → 键不同

- 卡片请求的是 `.../abc.jpg@640w_480h_1e_1c_85q.webp`（`coverUrlFor` 按档位加后缀）；
- 预加载传的是**未解析的 `item.cover`**，即原图地址。

Coil 的 memory 与 disk cache key 都从 `ImageRequest.data`（这里就是这个 URL 字符串）派生。
两个字符串不同 → 两个键不同 → 预加载解出来的位图卡片永远查不到，
**预加载 100% 白做**；而它下载的还是原图，所以是"白做 + 多下一张大的"。

修法：把"变体 → URL"抽成**纯函数** `biliImageUrlForVariant()`，卡片与预加载共用；
再加 `feedCoverVariant(singleColumn)` 锁住与 `CoverImage` 分支的对应关系。
之前这件事只有 composable 内部知道，预加载只能自己猜 —— 抽出来才谈得上不分叉。

### 4.2 纠正任务书对成因的假设（反编译查证）

任务书怀疑"`.size(640,480)` 与卡片布局尺寸不同 → memory key 不同"。
反编译 `coil-core 3.6.2` 的 `MemoryCacheService.newCacheKey` 字节码：

```
if (transformations.isNotEmpty())
    extras["coil#size"] = options.size.toString()
```

即**只有带 transformations 的请求才会把 size 写进 key**。本仓两个请求都没有
transformations，所以 size 根本不进 key；尺寸差异是之后由
`isCacheValueValidForSize` 拿已缓存位图的**实际宽高**去比的。

结论：size 仍需满足"预加载 ≥ 卡片"（否则判不可用、重新解码），
但那是**第二个独立问题**，不是键不一致。
顺带发现单列大图（`BiliCoverSize.Large` = 960w_540h）原先沿用双列的 640×480，
正是这个坑 —— 已按档拆成两组常量。

### 4.3 第二个静默失效：`debounce(180)` 在连续滚动下等于"永远不发射"

`snapshotFlow` 每帧产出新值 → debounce 每帧被重置 → **只有停下来才入队**；
再叠上原先"滚动中直接 return"的门控，等于整段快速 fling 一个都不预取。
而那恰恰是唯一需要预取的时刻（冷缓存首几轮滚动的 jank 就来自这里）。

改为按滚动态取超时：滚动中 `0L`（立即入队、跟上节奏），静止时仍 `180L` 合并抖动；
并取消滚动门控（解码始终在 Coil 的 IO 调度器上，不占主线程）。
`COVER_PRELOAD_AHEAD` 4 → 8：双列一屏约 4 张，4 张只够半屏缓冲。

## 5. 新增测试台账（19 条）与"是否验证过会咬人"

| 文件 | 条数 | 类型 | 咬人验证 |
|---|---|---|---|
| `core/common/.../coroutines/RunCatchingCancellableTest.kt` | 4 | **行为** | 未单独验证（helper 语义直白，且它本身是所有替换的前提） |
| `feature/video/.../VideoLogicGuardTest.kt` | 8 | 结构 | ✅ 已验证：把 fav-sheet 守卫改回无条件弹 → `favSheetOnlyOpensWhenItCanLoad` FAILED |
| `core/designsystem/.../component/CoverPreloadUrlTest.kt` | 7 | **行为** | 断言"解析结果不得等于原图"，即本 bug 的直接反命题 |

三道设计说明：

1. **T1 的测试是行为测试而非结构断言。** URL 解析是纯字符串变换，所以能直接断言
   "预加载 URL == 卡片 URL"、"不等于原图"、"解析幂等（保证缓存键稳定）"、
   "已有档位后缀被替换而非叠加"。这比文本形状强一档。
2. **`RunCatchingCancellableTest` 是本轮补的。** 两轮一共换了 12+ 处调用点，
   而"换了就等于修好取消语义"这个前提此前**从未被验证**。它含一条子类断言
   （`TimeoutCancellationException` 那类机制也是取消），因为若只判
   `::class ==` 就会把超时当成真实失败。
3. **写测试时自己踩到一个会让守卫静默失效的 bug**：`blockBody` 用
   `i > start && depth <= 0` 判函数结束，对**多行签名**的函数（参数各占一行、
   `) {` 在几行之后）会在 depth 仍为 0 时立刻截断，函数体只剩签名两行、
   里面当然什么都找不到。已改为"必须见过 `{` 才开始判结束"。
