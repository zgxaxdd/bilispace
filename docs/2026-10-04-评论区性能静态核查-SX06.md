| 5 | **嵌套滚动里的状态抖动**（滚动位置/展开态每帧写 state → 整表重组） | ✅ **已收口** | `CommentPanel.kt:122-136`：「该不该加载更多」是 `derivedStateOf { listState.layoutInfo… }`，**不是**在组合期直接读 `layoutInfo`；`CommentPanel.kt:141 LaunchedEffect(uiState.items.size)` 只在**列表长度变化**时重启（不是每帧），另有 `LoadMoreGrowthGuard`（`CommentPanel.kt:140`）挡空页/全重复页。这两条已被 `LoadMoreGrowthStructureTest` / `LoadMoreGrowthGuardTest` 钉住。 |
| 6 | **表情/富文本的分配** | ✅ **已记忆化** | `CommentRichText.kt:42 remember(text, emotes) { parseCommentText(...) }`（解析不随重组重跑）；`CommentRichText.kt:55 remember(parsed.emotes, baseSize) { … InlineTextContent … }`（inline content 映射表也不重建）；无表情时**早退**直接给 `Text`（`:45-52`）。另 `CommentReplyCard.kt:148 remember(reply.rpid) { derivedStateOf { isReplyBusy(...) } }` 是 AP-19 的"卡片自己查自己"（busy 集合变化只让自身翻转的那张卡重组）；`:149 remember(reply.pictures)` 同理。 |

**结论**：任务书列的 6 类嫌疑，**静态核查全部为"已处理"**，没有找到一条可以**独立于测量**就正当化的改动点。
⇒ SX-06 剩下的部分（"改什么"）**只能由测量来指向**，这正是它被阻塞的原因。

## 4. 测量协议（真机一连上就照这个跑，不用再设计）

**前置**：只在**调试包**（`com.naaammme.bbspace.debug`）上做；先确认刷新率上下文并写进记录。

```bash
# 0) 刷新率上下文（必须写进报告；同一台机前后必须一致）
adb shell dumpsys display | grep -i "refreshRate\|fps"

# 1) 清空并进入刷视频会话 → 打开评论面板 → 连续上/下滑 30s（含一次快速 fling）
adb shell dumpsys gfxinfo com.naaammme.bbspace.debug reset
# …手动操作 30s…
adb shell dumpsys gfxinfo com.naaammme.bbspace.debug framestats > r1.txt
# 重复 3 轮（r1/r2/r3），每轮之间 reset

# 2) 取中位：对每轮算 p50/p90/p99 帧耗时与 janky 帧占比，三轮取中位
#    （口径见 docs/performance-baseline.md）
```

**判定**：改动后的**中位数**不得劣于改动前（同机、同刷新率、同操作脚本、≥3 轮）。
**≥3 轮取中位、写清刷新率**是任务书 §1 铁律 4 的硬要求，不满足就不写数字。

**已知干扰项（跑之前先记录）**：
- `Logger.d/i/w` 是 debug 门控的（`core/common/…/Logger.kt:13-22`），**debug 包本身比 release 慢**；
  前后对照必须在**同一个变体**上做。
- SX-12 新加的 `android.util.Log.i("FeedRepository", "MERGED 档：web=…")` 是 **release 也可见**的，
  但它只在取流时打一行，不在滚动路径上，可忽略。
