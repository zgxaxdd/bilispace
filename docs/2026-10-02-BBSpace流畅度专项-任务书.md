## 0. 一句话目标

在**不引入功能回归、不改默认行为**的前提下，把 BBSpace 的**滚动期绘制/离屏录制成本**与**起播串行延迟**这两处结构性开销砍掉，把**待机常驻动画数量**收敛到与可见元素数量一致，并补齐四处已有动画的缺口；同时把 4 条「只有真机才能测出来」的空洞守卫，换成 4 条**现在就能红**的结构守卫。

**不做**：不改任何用户可见的默认行为；不为了数字改视觉；不碰没有设备就无法验证的东西。

## 3. 铁律（工作纪律，违反会造成难以发现的损坏）

1. **绝不用 PowerShell 改文件内容。** 历史上用 `Set-Content -Encoding UTF8` 把 `VideoPlayerPane.kt` 的中文写成乱码——**仍是合法 UTF-8、能编译、极难发现**。一律用 `edit` / `write` 工具。若必须用 PowerShell：`[System.IO.File]::ReadAllText($f,[Text.Encoding]::UTF8)` + `WriteAllText($f,$c,(New-Object System.Text.UTF8Encoding($false)))`，**并验证中文存活**。
2. **pwsh 的 `cd` 不跨调用保持**；`[System.IO.File]::*` 的相对路径基准是进程 CWD，**一律用绝对路径**。
3. 每完成一项就跑单测，**必须全绿**才算完成：
   ```powershell
   cd D:\111j\c\_ref\bbspace
   $env:GRADLE_USER_HOME="D:\env\gradle-home"; $env:JAVA_HOME="D:\env\jdk17"
   .\gradlew.bat :app:assembleDebug --console=plain
   .\gradlew.bat testDebugUnitTest --console=plain
   ```
4. **扫源码型守卫会被 Gradle 判 UP-TO-DATE / FROM-CACHE 静默跳过**（`BACKLOG.md` ST-26 已实测：把守卫 `mv` 到拼错目录仍 BUILD SUCCESSFUL）。改完守卫**必须**用 `--rerun` 单任务粒度确认真跑过；本地看到 `> Task :x:testDebugUnitTest` 而非 `UP-TO-DATE` 才算证据。
5. **每一条 P0/P1 修复都必须配一条"破坏性验证"**：先把代码改坏 → 守卫/测试必须 **FAILED** → 还原后 sha256 一致。写不出破坏性验证的"守卫"等于没写。
6. **不许在没有设备时写任何帧率/内存/耗时数字**。定量的位置一律写「待真机」+ 预期信号 + 取证命令。
7. **改棘轮上限必须同 PR 写明理由**（`FrameBudgetLintTest` 的设计意图就是让这个动作显眼）。

## 4. 本轮输入与"已被推翻的结论"（**不看这节会踩雷**）

本轮分析由 2 个 DeepSeek 子代理 + 3 个 Step 5 Preview 代理产出 5 份报告，并经 Lead 逐条回读源码**交叉复核**。以下两条子报告结论**已被推翻**，**不要照着改**：

| 被推翻的结论 | 真相 | 复核证据 |
|---|---|---|
| 「弹幕 `sync` 被 `positionMs` 每 500ms 重启，去掉 LaunchedEffect 的 key 即可」（原列为 P0） | `LaunchedEffect` 的 key 是 `sourceKey / window?.id / danmakuConfig / isPlaying / speed / seekEventId / hasSource` **七个，不含 `positionMs`**（它只是 `:173` 的实参）。`sync` / `windowSignature()` **不在 500ms 节拍上**（只在 key 变化时调用）。按原结论改代码是无效动作 | `DanmakuOverlay.kt:161-179`、`DanmakuOverlayState.kt:244-293` |
| 「`dockCapsuleShape()` 无 `remember` → 玻璃 remember key 全失效 → miuix 模糊缓存重建」 | `RoundedCornerShape` / `CornerBasedShape` **实现了结构化 `equals`**，Compose `remember(key)` 走 `equals` 比较 → 新实例但相等**不会**使 key 失效，模糊缓存**不会**因此重建。剩下的真问题只是"每帧重组期多分配几个小对象 + 绕过分配棘轮" → 已降为 FL-04 的 P2 卫生项 | `LinkedBottomDock.kt:194,379` |

同时被**降级**的一条：原 P0「封面预加载整段 fling **每帧**入队」——`distinctUntilChanged()` 在其上，只有 `lastVisible` 变化才发射，快滑时是**每秒数次~十几次**，不是每帧。真问题（缺已入队水位 + 每次重建 8 个 `ImageRequest`）不变，级别为 **P1**。

**已被确认、可以照做的高危结论**：见 §5 各任务。全部行号已由 Lead 回读源码核对。
