### PB-01 ★★★ 修「重试命中陈旧 playurl 缓存」（本次闭环核查发现的真实缺陷）

#### 目标

让"重试"真的是一次**全新的取流尝试**，而不是命中 90 秒内的陈旧缓存。

#### 缺陷事实（已核实，静态可判）

| 链节 | 证据 |
|---|---|
| 重试入口的 KDoc 声称"全新的取流尝试" | `feature/video/.../VideoViewModel.kt:936-938` 原文："走 `openVideo(当前目标)` … `openVideo` 内部会自增 `openId`，等于一次全新的取流尝试。" |
| 实际动作 | `VideoViewModel.kt:955-960` `retryCurrentPlaybackInternal`：`swipeSession.retry()` + `playbackController.openVideo(target)` |
| 取流入口**缓存优先** | `core/playback/.../repository/VideoPlayerRepositoryImpl.kt:47-53`：`playUrlCache.get(cacheKey)?.let { return cached }` |
| 缓存 TTL | `PlayUrlCache.kt:71` `TTL_MS = 90_000L` |
| 自动重试退避 | `core/swipe/.../SwipeErrorPolicy.kt:34` `longArrayOf(1_000L, 3_000L)`，上限 `:31` `MAX_AUTO_RETRIES = 2` |
| 自动重试调用点 | `VideoViewModel.kt:860-864`（`delay(delayMs)` 后 `retryCurrentPlaybackInternal(fromAuto = true)`） |
| 接口没有失效/强刷能力 | `core/playback/.../VideoPlayerRepository.kt:6-30` **只有** `fetchPlaybackSource` / `preloadPlayUrl` / `clearPlayUrlCache`；`clearPlayUrlCache()` 全仓唯一真实调用点是内存 trim（`BiliApplication.kt:198`，被 `MemoryTrimRegistrationTest.kt:112-114` 钉住） |

**结论**：自动重试的两次退避（1s、3s）**必然落在 90s TTL 内** → 对"URL 失效/403/404/签名过期"这类失败，重试**结构性地不可能成功**（拿回同一份失效签名 URL）。手动重试同理（除非用户等到 90s 后）。

#### 范围

**只改播放地址缓存的失效能力 + 重试路径接线**，不动 TTL、不动容量、不动 `flavorOf` 键构成、不动 `preloadPlayUrl` 语义。

#### 前置条件

1. `PlayUrlCache` 键 = `aid#cid#epId#seasonId#flavor`（`PlayUrlCache.kt:78-87`）→ **前缀失效可行**（`aid#` 前缀即可覆盖同一视频的所有 flavor）。
2. `PlayUrlCache` 目前只有 `get/put/clear/size`（`:39-56`）→ 需新增按键/前缀失效方法。
3. 失效必须在 **`openVideo` 之前**调用，否则取流已发生。

#### 实施步骤

1. `PlayUrlCache` 新增 `invalidateByPrefix(prefix: String): Int`（遍历 `lru.keys` 删除匹配项，返回删除数）+ 纯 JVM 单测。
2. `VideoPlayerRepository` 接口新增 `fun invalidatePlayUrl(request: PlaybackRequest)`；`VideoPlayerRepositoryImpl` 实现为按 `keyOf` 前缀（`"${request.ids.aid}#"`）失效。
3. `VideoViewModel.retryCurrentPlaybackInternal`（`:955-960`）在 `openVideo(target)` **之前**调用该失效；`fromAuto` 与手动走同一处即可。
4. 修正 `:936-938` 的 KDoc（写明"重试会先失效该视频的播放地址缓存，确保拿到新签名 URL"）。
5. **同步检查**：`MemoryTrimRegistrationTest.kt:112-114` 的注释里写着"`PlayUrlCache.clear()` 全仓唯一真实调用点"——本项**不调用 `clear()`**（用新方法），该守卫断言的是 `applyTrimPlan` 里含 `clearPlayUrlCache()`，**不受影响**；但需把该注释里"唯一调用点"的措辞核对一次，若已不成立则一并更正。

#### 验收标准（二值）

| # | 断言 | 判定 |
|---|---|---|
| 1 | 纯 JVM 单测：同一 key 在 TTL 内 `put` 后 `invalidateByPrefix("aid#")` → `get` 必须返回 null | 通过/失败 |
| 2 | 纯 JVM 单测：前缀不匹配的条目**不被误删** | 通过/失败 |
| 3 | 结构断言：`retryCurrentPlaybackInternal` 函数体内 `invalidatePlayUrl(` 的出现**早于** `openVideo(` | 通过/失败 |
| 4 | 结构断言：自动重试路径（`fromAuto = true`）与手动路径都经过同一 `retryCurrentPlaybackInternal` | 通过/失败 |
| 5 | 破坏性验证：把失效调用从 `openVideo` 之前移到之后 → 断言 3 必须红 | 被观测到红 |
| 6 | `:core:playback`、`:feature:video`、`:app` 单测全绿（逐模块 `--rerun`） | 全绿 |
| 7 | 默认行为不变：`preloadPlayUrl`、TTL、容量、键构成均未改（结构断言或 diff 复核） | 一致 |

#### 风险与回滚

- **风险低**：新增方法 + 一处调用。唯一可感知变化是"重试真的重新取流"，即**多一次 gRPC 往返**（这是修复的代价，也是目的）。
- 回滚 = 撤销单个提交。

#### 证据等级

**A（直接读源码可判）**：缺陷链每一节都有 `文件:行号`；结论不依赖真机。

### PB-02 ★★ seek 走关键帧（**限定用户主动 seek**）

#### 目标

用户拖动进度条 / 跳段时走**关键帧 seek**（更快落点），**但续播与自动跳段仍走精确 seek**，避免污染续播位置与历史记录。

#### 范围

上游依据（已核实）：`PlayerSettingsCache.kt:43` `seekFastEnabled = prefs.getBoolean(KEY_SEEK_FAST, true)`（**默认 true**）→ `VideoPlayerState.kt:1026,1072-1075`：
```kotlin
if (seekFastEnabled) SeekParameters.CLOSEST_SYNC else SeekParameters.DEFAULT
```

bbspace 现状：`SeekParameters|CLOSEST_SYNC|seekFast|关键帧` **全仓 0 命中** → 吃 Media3 默认 `EXACT`（精确 seek）。

#### 闭环判定（R1 结论）

- `ExoPlayer.Builder` **全仓仅 1 处**：`Media3PlayerEngine.kt:336`（番剧/直播/小窗/后台/听视频/离线都注入同一单例引擎）→ **一处改动即全覆盖**。
- `setSeekParameters` 属 **ExoPlayer 运行时 API**（非 LoadControl）→ 可在不重建 player 的前提下改。
- **但设置层不闭环**：`Media3PlayerEngine.kt:179` 早退 `if (next == playerConfig && exoPlayer != null) return` → 走 `PlayerConfig` 只能"下次 prepare 生效"；且 `PlayerEngine` 接口（`PlayerEngine.kt:23-51`）**没有** `setSeekParameters`。实时通路先例 = repeatMode（`StreamPlaybackSessionImpl.kt:138-148` + `PlayerEngine.kt:40-45` + `Media3PlayerEngine.kt:255-273`）。

#### 前置条件

1. **必须逐处审查 bbpace 的 5 个 seek 落点**（`StreamPlaybackSessionImpl` 的 `:225` 续播 / `:245` / `:283` 用户 / `:310` / `:392` 恢复），确认哪些是"用户主动"。**续播与恢复不得使用关键帧 seek。**
2. 明确本项**不引入用户可见设置项**（若引入，改动面从 1 文件涨到 7 文件且需实时通路，见 §5）。

#### 实施步骤（推荐方案：调用点成对设置，不改接口）

1. 新增纯函数（放 `core/playback` 或 `infra/player`）：
   `resolveSeekParametersForUserSeek()` → `CLOSEST_SYNC`；`resolveSeekParametersForPreciseSeek()` → `DEFAULT`（或 `EXACT`，与 Media3 默认一致）。
2. 在**用户主动 seek 的调用点**前后成对：`player.setSeekParameters(CLOSEST_SYNC)` → `seekTo(...)` → 恢复 `DEFAULT`；或在 `Media3PlayerEngine` 内封装一个 `seekUserInitiated(positionMs)` 方法，把配对逻辑收在一处（**推荐**，便于守卫锚定）。
3. **不改**续播（`resolveStartMs` 路径）与 `recoverSession` 的 seek。
4. 修正/补齐注释，说明为什么续播不走关键帧。

#### 验收标准（二值）

| # | 断言 | 判定 |
|---|---|---|
| 1 | 纯 JVM 单测：两个 resolver 返回值正确（`CLOSEST_SYNC` / `DEFAULT`） | 通过/失败 |
| 2 | 结构断言：`Media3PlayerEngine` 内 `setSeekParameters(CLOSEST_SYNC)` 与恢复 `DEFAULT` 在**同一函数内成对出现**（锚在调用本身） | 通过/失败 |
| 3 | 结构断言：**续播路径**（`resolveStartMs` 所在的 seek 调用）**不**出现 `CLOSEST_SYNC` | 通过/失败 |
| 4 | 结构断言：`recoverSession` 的 `setSource(source, positionMs, …)` 路径不含 `CLOSEST_SYNC` | 通过/失败 |
| 5 | 破坏性验证：把续播路径也改成 `CLOSEST_SYNC` → 断言 3 必须红 | 被观测到红 |
| 6 | 既有 `PlaybackResumePolicyTest` / `PlayerEngineOwnershipGuardTest` / `PlaybackRestoreStateTest` 全绿 | 全绿 |
| 7 | 逐模块 `--rerun` 全绿（至少 `:infra:player`、`:core:playback`、`:feature:video`） | 全绿 |

#### 风险与回滚

- **中**。三个已知风险点（R1 已给出）：
  1. **续播被吸附回暖并写回历史**：`StreamPlaybackSessionImpl.kt:561-571` 直读 `player.currentPosition` → `PlaybackReporter.kt:145` → `LocalPlaybackHistoryRecorder.kt:36`。**这正是本项限定"仅用户主动 seek"的原因**——不改续播路径即规避。
  2. **SponsorBlock 向后吸附一次性重入**：`VideoViewModel.kt:379` `seekTo(seg.endMs)` 若向后吸附，`containsMs` 仍为 true → 会重入一次，靠 `skippedUuids`（`:341,:381-388`）防死循环。**本项不改 SB 路径即不受影响**；若要改，必须先加"实际位置是否已离开片段"的校验。
  3. `durationMs` 与 manifest 时长口径不一致（`SingleFileDashMediaSourceFactory.kt:76-78` vs `PlaybackResumePolicy.kt:71-74`）会放大吸附边界——属既有问题，本项不扩大。
- **明确不受影响**（已核实）：弹幕（6 分钟窗口，`VodDanmakuModels.kt:5-9`）、95% 看完判定。
- 回滚 = 撤销单个提交。

#### 证据等级

**A**（`TAG` 待定）——机制与改动面均由源码判定；**收益量级需真机**（见 §6）。

### PB-03 ★★★ SimpleCache 媒体字节缓存

#### 目标

播放过的媒体字节跨会话复用：回看/拖动回退不再重新下载。

#### 范围

上游依据：`core/player/PlaybackMediaCache.kt` —— **128MiB** LRU（`:34-36`，注释写明 512MB 曾涨到 500MB+ 被下调）、目录 `cacheDir/playback_media_cache`、`CacheKeyFactory` 丢 query（`:53-64`、`:216-223`）、`ResolvingDataSource` 在 `CacheDataSource` 之外（`:97-108`）。

#### 闭环判定（R3 结论：⚠️需补链路，但**无需新依赖**）

- **依赖：0 行 gradle 改动**（多层硬证据）：`media3-datasource-okhttp-1.11.0.pom` 把 `androidx.media3:media3-datasource:1.11.0` 声明为 `scope=compile`；该 aar 的 classes.jar **同一个 jar 同时含** bbpace 已在用的 `androidx/media3/datasource/{DataSource,DataSpec,DefaultDataSource,TransferListener}.class` **与** `androidx/media3/datasource/cache/{SimpleCache,CacheDataSource,CacheKeyFactory,CacheWriter,LeastRecentlyUsedCacheEvictor}.class`。**最省时间的复核**：`./gradlew :infra:player:dependencies --configuration debugCompileClasspath | findstr media3-datasource`。

#### 前置条件（**必须全部满足，否则会出 bug**）

1. **插入位置在最外层**。当前链（请求流方向）：
   - SingleFileDash：`CdnFailoverDataSource → PrefetchedDataSource → DefaultDataSource → OkHttpDataSource`（`SingleFileDashMediaSourceFactory.kt:161-167`）
   - Progressive/Live：`CdnFailoverDataSource → DefaultDataSource → OkHttpDataSource`（`Media3PlayerEngine.kt:511-516`）
   
   `CacheDataSource` 必须在 `CdnFailoverDataSource` **之上**。依据：`CdnFailoverDataSource.kt:43-48` 是唯一 URI 改写点，`CacheDataSource` 用 open() 收到的 DataSpec 算 key；bbspace 上层从未 `setKey`（检索 `.setKey(|DataSpec.Builder` = 0 命中）。
   
   **禁止套在里面**：套里面时 `setUri(backup)` 无 key → 默认 key = 备用线路 URL → 同一分片在主/备线各存一份（重复下载 + 碎片 + 换线即命中率归零）。

2. **必须自定义 `CacheKeyFactory`**。bbspace 有两个换线维度：① `CdnFailoverDataSource` 换 host；② `VideoCdnMode` 有 20+ 镜像 host（`PlaybackCdnSelector.kt:36-41`、`PlayerSettingsModels.kt:73-89`，`rewriteUriHost` 保留 path 只换 host）。**若 key 含 host，用户切 CDN 线路 = 缓存全废。**
   - 推荐：键 = `media:<video|audio>:<path>`（丢 scheme/host/query；B 站 upgcxcode path 内容寻址；query 是签名/时效）。
   - 保守备选（照抄上游）：`scheme://host + rawPath`（丢 query），代价仅"换 host 不命中"。

3. **单例 + 懒建 + 工作线程**。`SimpleCache` 有静态目录锁（同目录第二个实例抛 `IllegalStateException("Another SimpleCache instance uses the folder: ")`）；构造器带 `@WorkerThread`（两参构造器在 1.11.0 **已 @Deprecated**）。落点：`infra/player/.../di/PlayerModule.kt:12-19` 加 `@Provides @Singleton`。**DI 图在 `Application.onCreate` 主线程**（debug 开 StrictMode detectDiskReads/Writes）→ 必须懒建 + `Dispatchers.IO`。

4. **scheme 闸门**：`LocalMerged` 是 `file://`（`DownloadPlaybackControllerImpl.kt:146-152`）→ 只缓存 `http/https`。

5. **不要在内存 trim 里清磁盘缓存**：`BiliApplication.kt:139` 明文"不清磁盘缓存"；`MemoryTrimPolicy` 的 `NetCacheAction` 是内存级语义，冲突 → 不动它。

#### 实施步骤

1. `infra/player` 新增 `PlaybackMediaCache`（对齐上游命名）：
   - `@Singleton`、懒建 `SimpleCache(File(cacheDir,"playback_media_cache"), LeastRecentlyUsedCacheEvictor(128MiB))`，构造在 `Dispatchers.IO`。
   - 暴露 `buildCachedDataSourceFactory(upstreamFactory, cacheKeyFactory)`（内部按 scheme 闸门决定是否包 `CacheDataSource`）。
2. 新增 `PlaybackCacheKeyFactory : CacheKeyFactory`，实现前置条件 2 的键策略。
3. 在 `SingleFileDashMediaSourceFactory.buildDataSourceFactory`（`:150-168`）与 `Media3PlayerEngine.kt:511-516` 两条链的**最外层**套上缓存工厂（保留 `CdnFailoverDataSource` 在内侧）。
4. 设置页挂"清理播放缓存 + 显示占用"：`PrivacySettingsScreen.kt:195-227`（既有"缓存管理"区块）+ `PrivacyViewModel.kt:90-102` + `CacheManager.kt:88-103`。
5. **清理时加播放中守卫**：判据 `Media3PlayerEngine.currentSource != null`（`:62-63`）→ 播放中不允许 release+删目录（否则抽掉正在读的文件）。
6. 不要设 `FLAG_BLOCK_ON_CACHE`（预取写入与起播读取并发时阻塞播放）。

#### 验收标准（二值）

| # | 断言 | 判定 |
|---|---|---|
| 1 | 纯 JVM 单测：`PlaybackCacheKeyFactory` 对同一 path 但**不同 host/query** → **同键**；不同 path → 不同键 | 通过/失败 |
| 2 | 纯 JVM 单测：scheme 闸门 — `file://` 不包缓存，`https://` 包 | 通过/失败 |
| 3 | 结构断言：`CacheDataSource` 的包装位置在 `CdnFailoverDataSource` **之外**（两条链都要） | 通过/失败 |
| 4 | 结构断言：`SimpleCache` 只有一处构造（单例），且构造发生在 IO 调度器上下文内 | 通过/失败 |
| 5 | 结构断言：`MemoryTrimPolicy` 未被改动（磁盘缓存与内存 trim 解耦） | 通过/失败 |
| 6 | 破坏性验证：把 key 改成含 host → 断言 1 必须红 | 被观测到红 |
| 7 | 破坏性验证：把 CacheDataSource 移到 `CdnFailoverDataSource` 内侧 → 断言 3 必须红 | 被观测到红 |
| 8 | `:infra:player`、`:core:playback`、`:feature:video`、`:app` 逐模块 `--rerun` 全绿 | 全绿 |
| 9 | `:app:assembleDebug` 成功 | 成功 |
| 10 | 编译期确认无需新依赖：`libs.versions.toml` / `build.gradle.kts` **无改动** | 无改动 |

#### 风险与回滚

- **中**。风险点：① 清理时播放中 release（已加守卫）；② 不 release 时索引在进程被杀后是否丢条目（待真机）；③ 预取写入与起播读取并发（不设 `FLAG_BLOCK_ON_CACHE`）。
- 新增 128MiB 磁盘占用 → **必须**同时在设置页给出"清理"与"占用"，否则是静默吃磁盘。
- 回滚 = 撤销提交；缓存目录残留可手动删（不影响功能）。

#### 证据等级

**A**（依赖与插入位置为硬证据）/ **收益量级 B**（需真机）。

### PB-04 ★★ 起播头部字节预热（依赖 PB-03）

#### 目标

竖屏连播切页时，在**真正开播之前**把视频/音频头部若干字节写进 PB-03 的缓存，缩短起播等待。

#### 范围

#### 闭环判定（R3 结论：⚠️需补链路）
