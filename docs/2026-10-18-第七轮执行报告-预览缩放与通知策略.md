## 2. 图片预览：双击缩放 + 修掉一个真实 bug（用户可见）

### 修掉的 bug
原实现用 `clickable` 处理点击：`scale > 1` 复位、否则关闭预览。**双击等于两次单击 ⇒ 第一次就把预览关掉了**，而"双击放大"根本不存在。改成 `detectTapGestures`（`onTap` + `onDoubleTap`）后：双击 = 1x ⇄ 2.5x，单击才关闭。代价是单击要等双击超时（约 300ms），这是双击语义的固有成本。

### 新增
- 双击放大**以点击点为锚点**：手指下的那一点在放大过程中不动；
- 放大/复位都用 `LocalAnimations.morph` 的时长与曲线（不是生硬的瞬变），且动画期间有新的手势会立即取消进行中的缩放（不会两个源同时写 scale）；
- 平移上限由缩放倍率推出（`容器 × (s−1) / 2`），缩回 1x 时**强制归零**（否则复位后图会"偏一点"，留下残影）。

### 抽成纯判据的原因
这三条（循环倍率、锚点数学、平移上限）都是纯算术，但错了**在无设备条件下只能"感觉怪"**。已抽到 `component/PreviewZoomPolicy.kt`，14 条 JVM 单测钉死，其中两条是**把第一版实现打回重写的**：
- `zoomInThenOutAroundSamePointReturnsToOrigin`：第一版写成 `offset + tap*(s−s')/s`（只在 `offset == 0` 时成立），放大再缩小后图回不到正中；
- `clampPanWithZeroBoundsAlwaysReturnsZero`：`coerceIn(-0f, 0f)` 会返回 `-0.0f`，而 `Offset` 是位打包比较 ⇒ `Offset(0f, -0.0f) != Offset(0f, 0f)`。

### 未做（如实）
上游同提交的**拖动惯性**（松手后按速度继续滑）未做：`transformable` 不提供手势结束时的速度，要拿到它得把手势层整体换成 `detectTransformGestures` 的手写循环，会牵动"拖拽关闭预览"的交互，风险大于收益。下一轮若要做，需先划一个不冲突的交互窗口。

## 3. 通知策略移植（上游 A 级，仅库）

**先做链路判定**：本仓只有 media3 的**播放通知**（`PlaybackService` 的 `PlayerNotificationManager`），**没有消息通知的 Service / Worker / Notifier / 状态存储** ⇒ 本轮只交付纯策略，不硬接 app。

`core/model/.../notification/MessageNotificationPolicy.kt`（约 380 行，纯 Kotlin）+ 15 条单测：
- **去重**：会话键 + msgKey 去重、有界 seen 记忆；
- **漏报**：未读基线缺失时静默建立（不把"首次读到"当增长）、pending 跨轮保留、候选补报；
- **误清**：只有"通知仍在系统栏"才因归零而取消；动态通知要"作者级已读"才撤（缺失快照不算已读证据）；
- **轮询预算**：单类目 5 条、预览 3 条、动态扫描并发**固定 16 worker**（钉住上游 `9037354d4` 的 W8 反例：修复前是"每个关注 UP 一个协程"）、linear 5min 退避、15/60 与 30/120 两档 + 空闲 15min 下限；
- 直播开播转移、动态 ID 字符串比较（避免 Long 溢出）、预览列表上限。

**接线方案**（未执行）：消息源 Repository → 纯 Poller → WorkManager/前台服务（两档 + idle floor）→ Notifier（分组 + 群摘要）→ DataStore 状态；`activeKeys` 由系统通知栏反查喂给 pending 收敛。五步全在 app/feature 写域，需要单独批准。

## 4. 玻璃采样稳定化：判定"不需要搬"，并上锁

上游 `a6288fe48` 的根因是：把**逐帧动画的主题背景色**当成了 `remember` 键 ⇒ 每帧重建 backdrop source + modifier 链 ⇒ `drawBackdrop` 引用比较每帧判不等 ⇒ 每帧失效重录。

**本仓结构上不可能发生**：`rememberChromeBackdropSource()` 无参、`remember` 键只有两个稳定实例、主题背景画在录制子树内部（子层失效 → contentLayer 重录，不重建 source）、重采样本就有滚动增量门控 + 可见性谓词 + 预算 + jank 守卫。**加延迟反而是缺陷**（24dp 折射依赖逐帧重录，延迟 = 滚动残影）。

⇒ 本轮**零 production 改动**，但补了一条**结构性守卫** `ChromeBackdropSourceStructureTest`（3 条）：`rememberChromeBackdropSource` 必须无参、文件里不许出现 `recordingBackground`。理由很实际：这条不变式没有任何编译期检查，而将来"顺手把主题色传进去省一次重组"就会把上游的坑重踩一遍，症状（轻微抖动）在无设备时发现不了。
