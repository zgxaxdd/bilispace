### 1.3 纠正二：面板**锁在 60Hz**，不是 120/144Hz

报告 §5-A 说"面板实际跑在 120/144Hz，红线不可比"。**看错了指标。**

| 指标 | 值 | 含义 |
|---|---|---|
| `peak_refresh_rate` | 120.00001 | **上限**（用户设置允许的最高） |
| `supportedModes` | 含 120/144 | **硬件支持列表** |
| **`mActiveRenderFrameRate`** | **60.0** | **实际渲染帧率** ← 只有这个算数 |
| `mActiveModeId` | 4 | 60Hz 模式 |

连续读 3 次都是 `60.0`。**任务书的 60Hz 假设是对的，jank ≤0.80% 红线可比。**

> **教训**：帧率要看 `mActiveRenderFrameRate`，不是 `peak_refresh_rate`。

### 1.4 纠正三：那个 1.0~1.8% 是**测量流程的预热效应**，不是代码差异

用 **worktree**（报告自己建议的正确做法，它却用了 `git checkout` 把报告文件从磁盘搞没了）
在 `63d750fb` 建了 `D:\111j\c\bbspace-before`，做了 **A-B-A** 对照，全部 release / 60Hz / 6 轮：

| 组 | r1 | r2 | r3 | r4 | r5 | r6 |
|---|---|---|---|---|---|---|
| **A**（优化后，热数据） | 0.31% | 0.10% | 0.00% | 0.21% | 0.00% | 0.10% |
| **B**（优化前 `63d750fb`，新装） | 1.41% | 1.15% | 1.05% | 0.00% | 0.21% | 0.21% |
| **A2**（优化后，重装） | **1.80%** | 0.42% | 0.21% | 0.21% | 0.21% | 0.21% |

**关键**：A2 与 B 形状相同，且 **A2 的 r1（1.80%）比 B 的 r1（1.41%）还高**。

## 2. 任务清单

### T1 ★★★ 查清并优化「首屏预热路径」——唯一还有 jank 的地方

**现象**：任何一次**冷图片缓存**的首轮滚动都是 1.0~1.8% jank，第 4 轮起降到 0.21%。
这是用户**第一次打开应用**就会遇到的路径，**有真实用户价值**。

**已知事实**
- 封面预加载**已存在**：`HomeVideoPage.kt:175-215`，`snapshotFlow + debounce(180) +
  AHEAD=4 + .size(640,480)`。
- 但 `AHEAD=4` 且 debounce 180ms → **跟不上快速 fling**；且**首屏没有预取**。
- 卡片封面请求：`BiliImageVariant.CardCover43` → `@640w_480h_1e_1c_85q.webp`。

**要查的第一件事（可能是真 bug）**
> **预加载的 `ImageRequest` 与卡片实际请求的 memory cache key 是否一致？**
>
> Coil3 的 memory cache key **包含解码尺寸**。预加载用 `.size(640, 480)`，
> 而卡片走 `BiliAsyncImage` → `rememberBiliImageRequest` **没有显式 `.size()`**
> （Coil 会用 composable 的**布局尺寸**）。
> 若两者尺寸不同 → **memory cache key 不同 → 预加载的解码结果卡片用不上，预加载完全白做。**
>
> 验证方法（无设备可做）：读 Coil3 的 `MemoryCache.Key` 构造逻辑（解包 AAR + `javap`，
> 仓库里有先例：`LiquidBackdrop` 的注释记录过对 miuix 的反编译查证），
> 或写一个 JVM 单测直接构造两个 `ImageRequest` 比较 key。
> **这是一个"要么完全没用、要么有用"的二值问题，必须先查清再谈优化。**

**要做**
1. 先查上面那个 key 一致性问题。若不一致 → 修成一致（这是**最大的单点收益**）。
2. 首屏预取：进入首页时对**前 N 张**（覆盖首屏 + 1 屏）主动 `enqueue`，不等用户滚动。
3. 提高 `AHEAD`（4 → 6~8）并考虑按**滚动速度**自适应；快速 fling 时 debounce 应更短。
4. 考虑**降采样预取**：首屏用更小的尺寸先出图（`allowRgb565(true)` 目前**未开**），
   确认是否有收益。

**验收（无设备）**：单测断言"预加载请求的 size 与卡片请求的 size 一致"（这是可断言的！）。
**验收（有设备）**：冷图片缓存下 r1 的 jank 从 1.0~1.8% 降到 ≤0.8%；≥5 轮取中位。
**注意**：测这个必须**每次清图片缓存**（`pm clear` 会清掉登录态，谨慎），
或用 `adb shell am send-trim-memory <pkg> RUNNING_CRITICAL` 触发清缓存后立即测。

### T4 ★★ UI/UX 质量收口

**T4.1 全局 dp/sp 收敛的**正确**做法**
上一轮**刻意没做**全局替换（理由充分：语义不同的尺寸塞进同一 token = 制造回归）。
本轮做**有语义依据**的那批：
- 报告发现 **`6.dp`(111 次) 与 `10.dp`(80 次) 是高频值但 `BiliSpacing` 里没有档位**。
  先判断这两个值分别是什么语义（内边距？图标？分隔线？），再决定是否加档位。
  **不要**因为"出现次数多"就加 token。
- `962` 处 theme 包外 dp 字面量的棘轮**只许减**。

**T4.2 次要文字对比度（需要设计决策）**
浅色 `onSurfaceVariant` 实测 **3.13~3.44:1**，不满足正文文字 WCAG AA（4.5:1）。
- 这是**刻意贴 iOS secondary label** 的结果（Apple `systemGray #8E8E93` 纯白底 3.26:1），不是笔误。
- 若要修：浅色 alpha `0x99`(0.60) → 约 `0xB8`(0.72)（纯白底 4.72:1）；深色 → 约 `0xAD`(0.68)。
- **这会明显改变全站次要文字深浅。有设备时截图对比再定；无设备时不要擅自改。**

**T4.3 3 处小触控目标**（上一轮冻结未改）
`IconButton` 显式 `size<48`：胶囊播放/关闭 32dp、移除图片 20dp。
有设备时放大到 48dp 验证"胶囊不撑高、缩略图角标不重叠、相邻按钮命中区不互抢"。

**T4.4 视觉一致性巡检**
- 深浅色下所有卡片/弹层/胶囊的圆角是否来自同一套 token
- 字重梯度是否真的分层（`iOSTypography` 已做 300–900，核查落地）
- 玻璃（FROSTED/LIQUID）两档下控件对比度是否都够
