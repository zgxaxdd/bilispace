## 1. 播放器控制行：三级层级（用户「文字太单调」的直接解）

| 级 | 件 | 底 | 前景 | 形状 |
|---|---|---|---|---|
| **L1 主操作** | 播放 / 暂停 | 白 **18%** 常驻圆底 | 白 1.00（实心圆角图标） | `CircleShape`，直径 = 行高 34dp |
| **L2 档位组** | 画质 / 倍速（多音轨时 + 音轨） | 白 **12%** **连体**胶囊底（段间距 0、无竖线） | 当前 1.00 / 非当前 0.60 | `BiliRadius.playerControl` 17dp |
| **L3 只读信息** | 时间 `0:12 / 19:17` | **无底** | 白 **0.92** + `lightTabularLabelSmall()`（11sp Light + tnum） | — |
| 贴角 | 全屏 / 退出全屏 | **无底** | 白（`Icons.Outlined.*` 线性） | 22dp 字形（与 10808 基线可比） |

**对比度**（白芯片是**提亮**合成 ⇒ `a_eff = 0.88 × (1 − X)`，`d-ios11` §1′）：
常驻 0.12 ⇒ dim 0.60 = **5.28:1** ✅；圆底 0.18 ⇒ 图标 1.00 = **9.29:1** ✅；
**按压态**再叠 0.18 ⇒ 合成 0.2778 ⇒ dim 只剩 **3.55:1** ❌ ⇒ **按压期间把字提到 1.00**（6.58:1）。
这条"按压提亮"是本次唯一为对比度做的行为改动，写在 `CtrlBtn` 的 KDoc 里，**不要改成压暗底**（实测降底救不回来）。

**码率下线**：`64K / 132K / 192K` 只在**多音轨**时渲染（单音轨点开也只有一条，是纯技术黑话）。

**拖动气泡**（原「滑块被气泡盖住、只剩 12×30px 白弧」）：改成**优先放滑块左侧、起点放不下翻右侧**，
偏移量 = `thumbOuter + gap + bubbleW`，其中 `thumbOuter = thumbPx/2 × thumbScale`（拖动态放大 1.18 自动自洽）。
⚠️ 规格 `d-ios11` §4.5.2 给的 `thumbW/2 + gap ≈ 19px` **数学上不可行**：气泡宽 52dp≈182px，
只偏 19px 必然整块盖住 42px 滑块 —— 规格的解本身自相矛盾，故按"目标"（滑块可见、气泡文字不被啃）实现。

**图标风格**：主操作 Rounded（实心）、次要动作 Outlined（线性）。与 `控件体系规范` §4「全 Outlined」有偏，
理由：动作与档位是两类语义，主操作靠"实心 + 圆底"承担层级，全线性会让播放键在圆底上显得发虚。

## 2. 播放链路：用户症状的因果链与修复（`perf` 交付）

**症状**：长视频播一段时间后卡住，缓冲停在约 5 秒不再前进。

根因不是单点，而是**四个结构性缺陷叠加**：

| # | 缺陷 | 证据（修复前） |
|---|---|---|
| D1 | **所有周期性维护挂在「只在 READY 时跑」的轮询里** ⇒ 一进 BUFFERING 全冻结：不再喂 `CdnTransferRuntime.playback()`、不再续期 CDN 路由（TTL 10 分钟）、不复查预取、无卡顿看门狗 | `Media3PlayerEngine.updateProgressPolling()` |
| D2 | **一次窗口异常 = 本会话并行下载永久关闭**（`fallback(); parallel=false`）⇒ 缓冲掉到 5s 以下本该"升 3 连接抢时间"（`CdnTransferPolicy`），但并行已死，救援分支永远进不去 | `CdnPlaybackDataSource.read()` catch |
| D3 | **并发槽位不是异常安全的**：槽位由 OkHttp 回调异步归还，窗口失败只 cancel 不等待 ⇒ 下一窗口 `tryAcquire` 瞬时失败 ⇒ 又落进 D2 | `downloadWindow` |
| D4 | **没有播放中途卡顿看门狗**：只有起播首帧超时；`onPlayerError` 不触发（"卡住"多数不报错） | — |

修复：
- **A 观测**：`StallDiag` 诊断行（2s 限频，仅 BUFFERING/静默时输出）：`pos/buf/remain/silent/stage/permits/parallel/routeFresh/lastWindow/lastError`。
- **B 解冻**：轮询改成唯一自适应循环（READY 500ms / BUFFERING 2s），仍是 1 循环 0 新线程；"稳定期清零重建预算"补 `isPlaying` 显式条件，防 3.3s 重建活锁复发。
- **C 降级可恢复**：并行降级后按"冷却 15s ∧ 缓冲 ≥10s ∧ Wi-Fi ∧ 设置开"重升；槽位 `tryAcquire(count, 300ms)` 有界等待；异常路径归还槽位；空切分不再返回全零窗口。
- **D 看门狗**：`StallRecoveryPolicy`（新）—— position 与 buffered 连续 8s 无进展 ⇒ `FLUSH → SEEK_TO_SELF(降权 host) → REBUILD(复用 60s/3 预算) → REPORT_ERROR`，档间冷却 4s、每档一次、有进展即复位。
- **对照 BiliPai**：其"进 BUFFERING 后 10s 看门狗 + 换线"与"维护轮询 BUFFERING 不停"是同一思路（本仓做成 4 级阶梯，因候选表在数据层）；`FirstQuarterAwareLoadControl` 等 4 项**不移植**（理由见执行报告）。注意：**上游同样是 `parallel=false` 永久降级**，本仓 C 是超出上游的修复。

**量化**：BUFFERING 期可执行维护动作 0→7；恢复阶梯 0→4 级；并行重升路径 0→1；槽位泄漏路径 1→0；测试 128→141（+13，0 失败）。

> ⚠️ `RebuildThrottle`「额度双取」经查**不是 bug**：`tryAcquire` 全仓唯一记账点在 `recoverSession()`（工作区 10-16 的修复已在），`onPlayerError` 各分支统一经它。交接书 P2 那条可结案。

## 5. 独立评审后的修复（第二轮，2026-10-17 23:0x）

由第三个代理做**只读评审**，确认/纠正如下（评审意见按严重度逐条给，修复只挑「确定是缺陷」的）：

| 编号 | 问题 | 修复 |
|---|---|---|
| A1 | 卡顿阶梯的 `REBUILD` 触发 `recoverSession` → `resetRuntimeState` 把阶梯清零 ⇒ 同一段卡死反复烧 3 次整会话重建、约 74s 才落错误态 | `resetRuntimeState(keepStallLadder)` + `StallRecoveryPolicy.onSessionRebuilt()`（保留档位、只作废读数基线），重建后直接升 REPORT |
| A4 | 缓冲**回退**（自己 FLUSH 的 seek 会造成）后仍拿旧高位基线判"无进展" ⇒ 恢复期被误判成停滞 | 回退时把基线一起下调；补单测 `buffer regression lowers the baseline instead of faking progress` |
| A5 | `tryAcquire(count)` 但 `splitCdnRange` 会被区间长度夹小 ⇒ 尾窗永久漏 permit（单向泄漏） | 先判空切分，再按 `pieces.size` 占位；异常路径按 `pieces.size − launched` 归还 |
| A3 | "降级→重升"只有 15s 冷却、无次数上限 ⇒ 弱网下周期性 12s 零交付 | 单实例最多重升 2 次（`MAX_PARALLEL_RESTORES`） |
| A6/A7/A8 | 恢复 detail 文案自相矛盾；重升时给被掐断的 delegate 记"成功"；并行模式下 `currentServingHost()` 恒 null 使"换线"退化成重复 FLUSH | 文案改中性；记 `canceled=true`；兜底改"避开近期失败最多的 host" |
| A9 | REPORT 之后诊断行仍 2s 一行，长期灌 logcat | 终态降频到 10s（`STALL_DIAG_DONE_MS = 间隔 × 5`，避开 `10_000L` 字面量守卫） |
| B1 | `StateMessageCard` 轻态判定没排除 `isError` ⇒ 10 处错误态退化成一屏红字；轻态 `fillMaxSize()` 顶部对齐 | 错误态永远走重态；轻态改 `Box` 居中 |
| B4 | 连体胶囊内每段自带 17dp clip ⇒ 中段按下"胶囊套胶囊" | 段内叠色改直角 + 不缩放，外轮廓交给宿主整块 clip |

**评审提出但未采纳**（附理由）：
- **A2「终态只写 errorMessage，VOD UI 不读它 ⇒ 没有出口」**：属实，但修它要改会话层→`PlaybackError`→`SwipeErrorPolicy` 的整条链路（跨 module，且会改变错误态语义），无设备无法验证"重试浮层"观感。**列为下一轮第一优先**，本轮先保证"不会因为反复重建把会话烧坏 + 有日志可定位"。
- **B2「FilledTabRow 反白胶囊在大面积种子色/玻璃顶栏下可能过重」**：本机用户是 iOS 档（走 segmented 分支），Material 分支非当前观感；等真机走查再看，不为此回滚。
- **B3「窄屏时间会被省略」**：算术成立，但旧版同样的位置也会省略（`19…`/`10…`）；给档位组加约束会改变"贴角右对齐"的既有布局约束，风险 > 收益。**待真机确认后按需再改**。
- **perf 建议的「弹幕 500ms 订阅可删」与「pager 无条件 graphicsLayer 可门控」**：两处源码里都已有明确注释说明**为什么不能那样改**（前者会导致 sync 用旧 progress、弹幕跳回旧段；后者回弹发生在松手后，摘层会跳回 0）。**未采纳，并在报告里记录以免下一轮重复提**。
