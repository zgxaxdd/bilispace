# 性能四族：度量设施与审计结论（2026-10-18 夜）

> 覆盖用户第 5~8 条：内存管理 / 垃圾回收 / UI 渲染管线 / 网络与 I/O 与线程调度。
> 纪律：**没有设备就不许说"优化了"**。本文件只记录三件事：① 新增了什么读数；② 哪些是源码级可证实的结论；③ 哪些必须真机才能判。

## 1. W5 内存管理

### 1.1 新增读数：`MemoryDiag`（`app/.../memory/MemoryDiag.kt`）
- 触发点：**既有** `onTrimMemory` / `onLowMemory` 回调（不新建线程、不新增定时器）。
- 一行内容：`level/reason + heap used/max(%) + alloc + img cache used/max(%) + threads + gc count/time + blockingGc + uptime`。
- 纯判据在 `MemoryDiagPolicy`（JVM 单测 6 条）：`LOW_MEMORY` 必报；`RUNNING_*`/后台吃紧档必报；常规 `UI_HIDDEN` 只在图片缓存 ≥60% 时报（否则每次切后台都刷屏）。
- 为什么用 `Debug.getRuntimeStat("art.gc.gc-count"/"art.gc.gc-time"/"art.gc.blocking-gc-count")`：ART 自带进程级计数，不需要设备、不需要 perfetto；把它和堆占用放同一行，才能判"卡顿是不是 GC 造成的"。

### 1.2 既有能力（已核实，不重复造）
- `MemoryTrimPolicy`（纯函数 + 单测）：按 trim level 分级 → 图片缓存 trim/clear、封面色缓存、无缝封面软件位图 LRU（4×960×540 ≈ 8MB）、详情/播放地址/DNS 缓存。
- Coil：内存缓存 `maxSizePercent(0.25)`（Coil 默认口径）、磁盘 256MB（有注释解释为什么不是 100MB）。
- 明确不做：**不清磁盘缓存、不碰播放器缓冲**（清了立刻卡顿/费流量），这条写在 `BiliApplication` 的 KDoc 里。

### 1.3 本轮未做（下轮，需要跨模块写域）
- `VideoCardCoverColorStore` 当前**没有数量读数入口**（只有 trim/clear）⇒ 想在 MemoryDiag 里报"封面色缓存条数"，需要 designsystem 加一个只读 `size()`（本轮避开与 ui-shell 的写域冲突）。
- `Coil` 缓存上限按 `ActivityManager.memoryClass` 分档（低端机降到 15~20%）——**有利有弊**（缓存变小 ⇒ 解码次数上升 ⇒ CPU/卡顿可能变差），必须有真机 A/B 才能定，本轮不动。

## 2. W6 垃圾回收

**结论先行**：本仓已有三道静态棘轮把"每帧分配"的高频形态钉住了，本轮静态扫描**没有再发现未受守卫的明显热点**：

| 扫描项 | 实测 |
|---|---|
| 内联 `MaterialTheme.typography.x.copy(`（每次重组新建 TextStyle） | **0 处真正的代码命中**（其余全是注释/测试） |
| `String.format` / `"%.2f".format` 热路径 | 0 处 |
| `RoundedCornerShape(` 具名实参（每次重组新建 Shape） | 12~13 处，已由 `ListAllocationStructureTest` 冻结（上限 16） |
| `drawWithCache` 使用（把 Stroke/Brush 提到缓存） | 27 处（正向写法） |
| `animate*AsState` | 10 处（棘轮 10/10 满） |

新增：`FrameJankMonitor` 的读数行里带 **`gc=次数/耗时ms`（窗口增量）**，与 `MemoryDiag` 的累计值互相对照 —— 这是"GC 是否在拖帧"的唯一可离线落地判据。
未做：不引入任何显式 `System.gc()`（全仓已确认 0 处）；不调 GC 参数（Android 不可控）。

## 3. W7 UI 渲染管线

### 3.1 新增读数：`FrameJankMonitor`（`app/.../perf/`）
- 挂在 `Choreographer`（主线程 vsync），**每帧零分配**（IntArray 直方图 + 整数运算），10s 输出一行 `FrameDiag`。
- 只在 `DiagnosticLog.enabled`（debug 包或用户打开现场诊断）时启动；界面全部不可见时 `stop()`。
- 口径：名义 16.67ms；`jank` > 32ms；`freeze` > 700ms；报 `fps/jank/freeze/p95/worst + gc 增量`。
- 意义：本仓**此前完全没有"界面滑动卡不卡"的读数**（`PlaybackWatch` 只覆盖播放链路），交接书里"零帧率测量能力"指的就是这件事。

### 3.2 源码级审计（不涉真机也能定论的部分）
| 位置 | 现状 | 结论 |
|---|---|---|
| `PortraitSwipePager` 页级变换层 | 已按 `isScrollInProgress` 门控（一次滑动只翻转 2 次） | 正确，不动 |
| `PortraitSwipePager` 越界 `graphicsLayer` | **无条件挂载**，源码已写明理由（回弹发生在松手后，摘层会跳回 0） | 正确，不动（评审曾建议门控，已驳回并记录） |
| 刷视频会话 `allowSurfaceView=false` | 因为页级变换会挖空 SurfaceView，刻意用 TextureView | 正确，不动 |
| `VideoPlayerPane` 的 500ms 弹幕进度订阅 | 源码写明"必须 collect 不能直读".value""（否则 sync 用旧 progress，弹幕跳旧段） | 正确，不动（评审建议已驳回） |
| 列表 `items(` | 68 处；`ListKeyIntegrityTest` 已有守卫 | 待补的只有 3 处 `items(count=)` 的异步场景，风险低 |

### 3.3 需真机才能定的项
- 玻璃面 4→6 后的采样开销（`GlassDrawChainStructureTest` 只能守结构，守不了 GPU 时间）；
- TextureView 路径的应用侧合成开销（Perfetto/RenderThread 才有数）；
- `FrameDiag` 的实际读数（**用户跑一次 debug 包即可提供**）。

## 5. 用户真机取数（3 行命令，10 秒）
```bash
adb logcat -s FrameDiag    # 每 10s：fps / jank% / p95 / worst / gc 增量
adb logcat -s MemoryDiag   # 内存吃紧时：heap、图片缓存水位、线程数、GC 累计
adb logcat -s StallDiag    # 播放卡住时：缓冲剩余、槽位、并行、路由新鲜度、最后错误
```
三行合起来能区分「卡在渲染 / 卡在解码 / 卡在 GC / 卡在 CDN」——这是本轮对"流畅度"最实质的贡献。
