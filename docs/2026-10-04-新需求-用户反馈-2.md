## N-1 · 刷视频模式里，横屏视频没有悬浮的「横屏」按钮 —— **代码已完成 / 真机未能验证**

**用户原话**：「刷视频模式中，横屏视频下方没有悬浮的横屏按钮，必须在图三中的顶栏点击横屏」。

### ① 实现（在 `PortraitSwipePager` 里，与互动栏同一层）
```kotlin
if (!isPortraitVideo && !landscapeForced && currentVideoAspect != null &&
    !playbackSheetVisible && !showComments && !showFavSheet) {
    BoxWithConstraints(Modifier.fillMaxSize()) { … SwipeLandscapeFab(onClick = onToggleLandscape) … }
}
```
- **触发**：当前页是**横屏视频**（复用本文件已有的 `isPortraitVideo`，同源于 `currentStream`）
  且**还没被手动横屏**（`!landscapeForced`）且**宽高比已知**（`currentVideoAspect != null`
  —— 这一条同时兜住了"取不到流"的情况：那时 `isPortraitVideo` 会算成 false）。
- **点击**：复用**顶栏那颗胶囊的同一条通路** `onToggleLandscape`（→ `swipeLandscape` 取反 →
  方向 effect 走 `SENSOR_LANDSCAPE`）。**没有新造任何转屏状态**。
- **自隐藏**：点完 `landscapeForced` 变 true ⇒ 本按钮条件立刻不成立 ⇒ 自己消失，不会重复出现、
  也不与"退出横屏"的顶栏胶囊抢语义。
- **让位**：与互动栏**同一条显隐判据**（播放设置侧栏 / 评论卡 / 收藏面板在场时一起收），
  不会浮在评论面板之上。
- **视觉**：与 SX-03 的「全屏」胶囊同一套语言（`surface.copy(alpha = .86f)` + 轻投影 +
  `CircleShape` + **零模糊**），文案是「横屏」（两个入口语义不同：这里进手动横屏，那里进全屏形变）。
  另起一个 `SwipeLandscapeFab` 而不复用 `LandscapeFullscreenFab` 的原因写在 KDoc 里：
  后者的守卫**钉住了它的调用点数量与无障碍文案**，参数化会迫使放宽那条守卫。

### ② 位置：由"画面下沿"推出（**基于实测，不是猜**）
会话里视频是 letterbox 且**垂直居中**的 —— 这是我上一轮在真机上量出来的：
`1920×886` 的流，画面带 **1110→1690**，中心 **1400 = 屏高的一半**。
于是：`画面高 = min(屏高, 屏宽 / 宽高比)`、`画面下沿 = (屏高 + 画面高) / 2`，
按钮贴在**画面下沿 + 一个小间距**、左对齐。

**自检（用那次实测反代公式）**：`1272 / 2.167 = 587px`，与量到的 **590px** 一致（差 3px）；
`(2800 + 587) / 2 = 1693`，与量到的下沿 **1690** 一致 ✓ ⇒ 公式与实测互相印证。

**碰撞分析（对全部画幅）**：

| 对象 | 位置 | 与按钮的关系 |
|---|---|---|
| 互动栏（rail） | x≈1010–1220（贴右） | 按钮**左对齐**（x≈56–250）⇒ 横向不重叠 |
| 底部信息层（@名/标题/标签） | y≈2400+ | 按钮下沿最大 ≈2232（正方形画幅时）⇒ 不重叠 |
| 弹幕/字幕 | 渲染在**画面矩形之内**（1110–1690） | 按钮在画面下沿**之下** ⇒ 不压内容 |
| 加载 veil | 逐页、在 `VideoPlayerPane` 内（**z 序在按钮之下**） | 按钮会浮在 veil 之上 —— 与互动栏既有取舍一致（该文件注释明写"常驻件的常驻性优先于加载层期间让位"） |

### ③ 守卫与破坏性验证
- **新增** `swipeSessionOffersFloatingLandscapeEntryForLandscapeVideos`：钉住
  ①判据形态 ②`onClick = onToggleLandscape`（复用既有通路）③**位置必须由宽高比算出**
  （跨行公式锚点，防止有人换成固定 dp / 固定 alignment）④与互动栏同一显隐判据

- **形态更新（W27，三处，均写明理由）**：新按钮改变了几处"整文件计数"的前提 ⇒
  ①`swipeSessionOffersFavorite` 的 `&& !showFavSheet == 1` 改为锚**互动栏那一行**；
  ②`swipeSessionOffersManualLandscape` 的 `remember(playbackState.currentStream) == 1`
  改为锚 **`val isPortraitVideo = remember(...)`**；③`swipeCommentCardIsTranslucentAndBlurFree`

  `swipeSessionOffersFloatingLandscapeEntryForLandscapeVideos` **红**

  （`1D06CA6897D31B78F5D2E9BA283FB4B2FD5B33D609D1FC79B223C89BFFBE0E58`）。

### ⑥ 优化（用户给出**抖音**的参照：那颗是画面下方**居中**的「全屏观看」）

用户看了第一版（左对齐、亮面 pill）之后发了抖音的截图：「这是抖音的解决方案，你的还需要优化」。
两处实质差异，都改了：

| | 第一版（被否） | 现在 |
|---|---|---|
| 位置 | 左对齐（`TopStart` + start padding） | **水平居中**（`TopCenter`），仍贴在画面下沿 |
| 观感 | 亮面 pill（`surface.copy(alpha=.86f)` + 深色字） | **深色半透明 + 发丝白描边 + 白图标/白字** |

**为什么第一版不对**：这颗挂在**黑边区**里，亮面 pill 在黑底上像一块白斑，比视频还抢眼；
抖音用"深色半透明 + 白描边"把它压回背景里。位置同理 —— 居中才读得出"这是这画面的入口"，
左对齐更像一个工具栏按钮。

**线宽怎么来的（不是随手写）**：`BiliSpacing.xs / 8` = **0.5dp**，与仓内发丝描边
`biliDarkHairlineBorder` 同值。**不写 `0.5.dp` 字面量** —— `DesignTokenLintTest` 的 dp 棘轮
已无余额；也不直接复用 `biliDarkHairlineBorder`，因为它只对「iOS 档 + 深色 + `surfaceContainer*`
容器」生效，本 pill 是半透明黑，走进去会返回 `null`（等于没描边）。

**真机复核（2026-10-04 13:49）**：居中 + 深色描边版在**另一支横屏视频**（影视飓风，
`选哪个？iPhone 18 Pro&Duo深度上手`）上同样出现、位置正确 ⇒ 不只对一支视频成立。
证据：`docs/evidence-sx/n1_restyled.png`。

## N-2 · 横屏观影：清屏 + 侧滑返回切回竖屏 + 按钮参与防烧屏 —— ✅ **真机验证通过**

**用户给的口径（2026-10-04，三条）**：
1. 「横屏的按钮应该与点赞的逻辑相同，也应该加入防烧屏设计」；
2. 「点横屏后应该清屏（不显示任何东西，沉浸观影）」；
3. 「在横屏模式观影时侧滑返回应该切回竖屏播放」。

### ① 按钮参与防烧屏（要求 1）
- 加 `.applyBurnIn(LocalSwipeChromeBurnIn.current)` —— 与互动栏、底部信息层用**同一个**
  `chromeBurnIn`（静置变暗 + 缓慢像素漂移），不再是个"不参与常驻策略"的孤件；
- 点击它的 lambda 里先 `lastChromeInteractionMs = SystemClock.elapsedRealtime()` 再转屏 ——
  与"打开评论 / 打开收藏 / 打开侧栏"**同一口径**：点它也算一次会话交互，常驻件立刻回满亮。

### ② 横屏清屏（要求 2）
`if (!landscapeForced)` 两处（单 token 前缀，不改任何既有 `visible` 表达式 ⇒ 竖屏行为逐字不变）：
- 底部信息层（`SwipeSessionInfoLine` + 底部暗角那一整块）；
- 右侧互动栏（含 UP 头像）。

**真机实测（2026-10-04 14:14，`浅谈iPhone 18 Pro` = 1920×886 = 2.17:1）**：
点「横屏」后屏幕 2800×1272，`uiautomator` 的文本节点**归 0 条**、截图里互动栏/头像/标题层/
顶栏**全部不在**（只剩视频本体）⇒ 清屏成立。证据 `docs/evidence-sx/q2_landscape_clean.png`。

### ③ 侧滑返回 = 切回竖屏（要求 3）
`BackHandler(enabled = landscapeForced || …)`：横屏态下**优先吃掉**这一次 back
（含系统侧滑返回手势），只调 `onToggleLandscape()` 把手动横屏收回去 —— 与会话内顶栏那颗
胶囊**同一条通路**；会话与当前视频原地保留。竖屏态下一律走原来的面板/宽限逻辑。

**真机实测**：横屏下返回 → 屏幕回到 **1272×2800（竖屏）**，`uiautomator` 里互动栏计数
（190616 / 25258 / 44919）、底部信息层（@极客湾Geekerwan + 标题 + 标签）与「横屏」按钮
**全都在**，且无任何会话退出事件 ⇒ **切回竖屏播放、没有退会话** ✓。

### ④ 守卫与破坏性验证
- **新增** `landscapeInSessionClearsChromeAndBackReturnsToPortrait`：钉住 ①`applyBurnIn` 同源 +
  点击重置计时；②两处 `if (!landscapeForced)` **且既有 `visible` 表达式保持 1 处不变**；
  ③`BackHandler` 的 `landscapeForced ||` 前置项与横屏优先分支。
- **形态更新（W27，两处，均写明理由）**：①`swipeSessionOffersFloatingLandscapeEntryForLandscapeVideos`
  里"点击 = `onToggleLandscape`"的锚点（改 lambda 后锚到"调用了 `onToggleLandscape()`"）；
  ②`swipeBackClosesSheetsBeforeLeavingSession` 里 `BackHandler(enabled = …)` 的锚点
  （多了 `landscapeForced ||` 与横屏优先分支）。**两条的意图都不变**。
- **破坏性验证**：把信息层的门改回恒真（`if (!false) Box(`）⇒ 新守卫 **红**；
  还原后脚本核对 sha256，再跑三门禁。
- **⚠️ 要求 1 的"肉眼可见"部分未单独取证**：防烧屏是"静置 15s 后压到 55% 亮度 + 缓慢漂移"，
  需要一段受控的静置观察；本轮只做了**结构验证**（与信息层同一个 `applyBurnIn` + 点击重置计时），
  没有拍"变暗前后"的对照图。若需要，下次插线时补一次 30s 静置对照。

## N-3 · 部分视频尺寸较小 → 屏幕下方出现黑色部分 —— **✅ 已定位并修复（2026-10-04）**

**用户原话**：「由于部分视频尺寸较小，会出现图中的情况：屏幕下方出现黑色部分」。

### ① 现象
**详情页**，横屏视频 ⇒ 页面下方露出一条**黑色带**（卡片/正文是浅色主题，底部却是黑的）。

### ② 定位（读代码 + 真机取证，不猜）
根因是**算术**，就在 `VideoScreen.kt` 的紧凑分支：

- 详情区**背景层**（主题背景色）旧写法：
  `.height(detailBaseH + BiliRadius.playerCompact)`，其中
  `detailBaseH = maxHeight − compactPlayerSpaceH`（`VideoScreen.kt:785`）；
- 该层还 `.offset` 下移 `bandMorphHeightPx() − r`；
  ⇒ **下沿 = `band + maxHeight − compactPlayerSpaceH`**；
- 而 `compactPlayerSpaceH = statusTop + 16:9 高度`（`:488-489`）、
  `band = statusTop + 视频当前高度`（`:811-813`）。

⇒ 只要视频**比 16:9 更宽**（`targetVideoPx < baseVideoPx` ⇒ 播放带比预留矮），
下沿就比屏幕矮 **`compactPlayerSpaceH − band`**，根层的 `background(Color.Black)`
（`:818`）从底部透出来。**视频越扁漏得越多** —— 与用户"尺寸较小的视频才出现"完全吻合。

**真机取证（用户报的那支视频）**：`浅谈iPhone 18 Pro`（花生說），
`logcat` 里 `PlayViewUnite: Stream … W: 1920, H: 886` ⇒ 比例 **2.17:1**。
按上式：`baseVideoPx = 1272 × 9/16 = 715.5`、`targetVideoPx = 1272 / 2.167 = 587`
⇒ 缺口 **≈128px**，与用户截图里那道黑带同量级 ✓。

### ③ 修法
背景层改为 `.fillMaxWidth() + .fillMaxHeight() + .offset{…}`：
起点仍是 `band − r`（月牙区照旧被盖住），但**下沿永远越过屏幕底、由窗口裁掉**
⇒ 与播放带当前高度**无关**地盖到底。对 16:9 / 竖屏视频**零行为变化**
（那两种情形原本下沿就已 ≥ 屏幕底），只有"比 16:9 宽"的视频从"漏黑"变成"盖住"。

### ④ 真机验收（同一支视频，修复后实测）
逐行采样底部像素（1272 宽，取 x=100…1172 的均值）：

| y | 修复前（用户截图） | 修复后（实测） |
|---|---|---|
| 1750 | 黑 | **RGB(203,203,209)** |
| 1800 | 黑 | **RGB(242,242,247)** |
| 1850 | 黑 | **RGB(255,255,255)** |

⇒ 底部已是**主题背景 / 卡片色**，黑带消失 ✓。

### ⑤ 守卫与破坏性验证
- **新增** `detailBackdropCoversToTheScreenBottomRegardlessOfBandHeight`：
  ①断言 `fillMaxWidth() + fillMaxHeight() + offset{…}` 这条链存在（正则跨行邻接）；
  ②**回归防护**：`height(detailBaseH + BiliRadius.playerCompact)` 计数必须为 **0**。
- **形态更新（W27，一处）**：`playerSeamUsesThemeStrokeAndCoverLightSpill` 里
  "背景层高度"那条锚点随修法失效 —— 该条的**意图**（背景层与光晕层是两个独立层、
  都靠 `.offset` 上移一个圆角半径）**不变**，只把锚点换成新形态并写明理由。
- 破坏性验证：把背景层改回 `.height(detailBaseH + BiliRadius.playerCompact)` →
  **两条守卫同时红**（`…:329` / `…:2044`）；还原后 `VideoScreen.kt` sha256 一致
  （`3E3A29CE46BD45184C322C510C2A1C2BC7BBB5C86581C4F8D7DEFECF13827060`）。

## 与本批 12 项的关系

三条都**不在** SX 任务书的 12 项里，是用户上手后的新反馈。
N-1/N-2 是 SX-03/SX-05 能力在**刷视频会话**上的延伸（同一套语言、同一批组件）；
N-3 是本批**未覆盖**的一条视觉缺陷（SX-03 只处理了"横屏时的悬浮按钮"，
没处理"内容撑不满时底部漏黑"）。
实现顺序建议：**N-3（可见缺陷）→ N-1 → N-2**，每项一提交、各配守卫与破坏性验证。
